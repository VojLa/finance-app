# 5G-B1 – Deterministic investment event and movement plan

## Metadata

- Milestone: `0.1 - Architecture Locked`
- Parent: `5G-B - canonical investment posting foundation`
- Dependency: Step 5G-A, merged as `385e83ae14e45d91644cd471197f57dd2c3e98b6`
- Size: M
- Source of truth: persisted investment posting intent, pure classifier and canonical SQLAlchemy column contracts

## Goal

Add a pure, immutable and deterministic investment posting-plan layer.

For one valid classified investment row, 5G-B1 must:

1. validate the complete import-row posting boundary;
2. remove workflow metadata from a copy of normalized JSON;
3. re-run the pure classifier and require exact stored-intent equality;
4. harden investment classification so every successful intent has enough explicit evidence to be posted without inference;
5. build one immutable event plan, optional asset-resolution plan and ordered movement tuple;
6. reject values that cannot be represented exactly by canonical `QUANTITY` and `TIMESTAMP` columns;
7. perform no database write.

5G-B1 does not resolve database assets or create ledger entities. Those belong to 5G-B2
and 5G-B3.

## Input boundary

The pure builder accepts an `account_id`, one batch and one row already selected by a
future caller.

Common requirements:

```text
batch.account_id = account_id
batch.status = processing
row.import_batch_id = batch.id
row.normalized_data is an object
row.normalized_data.deduplication = {schema_version: 1, status: unique}
row.normalized_data.posting_intent is an object
row.deduplication_key is a non-blank string
row.validation_errors = null
row.error_message = null
```

First-plan state:

```text
row.status = pending
created_transaction_id = null
created_investment_event_id = null
```

Replay-plan state, needed by 5G-B3:

```text
row.status = imported
created_transaction_id = null
created_investment_event_id is a non-blank string
```

Reject every other status or created-ID combination.

## Stored intent revalidation

Treat persisted JSONB as untrusted.

Before constructing any plan:

```python
canonical = copied_canonical_payload(row.normalized_data)
fresh = classify_import_row(
    source=batch.source,
    normalized_data=canonical,
).model_dump(mode="json")
```

Require:

```text
fresh == stored posting_intent
fresh.schema_version = 1
fresh.target = investment_event
```

Then validate through `InvestmentEventPostingIntent`.

Do not replace a mismatched stored intent. Raise generic `ImportPostStateError` with:

```text
code = import_post_state_invalid
status = 409
message = The import batch is not available for posting.
```

The message must not include account IDs, row IDs, provider identifiers, asset symbols,
notes or financial values.

## Classifier hardening

The existing classifier can produce some successful investment intents that cannot be
mapped safely into the inherited canonical schema. 5G-B1 must close these gaps in the pure
classifier so a successful `investment_event` intent is plan-buildable without guessing.

Use bounded structured review errors. Exact enum names may follow existing conventions,
but tests must distinguish at least these conditions:

```text
missing_asset_symbol
missing_asset_direction
unsupported_embedded_conversion
incompatible_investment_fields
```

### Asset symbol

The inherited movement and listing models require a source symbol/currency identity.
For actions that reference an asset, a non-blank canonical symbol is required. ISIN-only
rows become `needs_review`; do not use an ISIN as a symbol.

Asset-bearing actions:

```text
buy
sell
dividend
asset_transfer
staking_reward
airdrop
```

### Asset-transfer direction

Every asset transfer requires explicit `asset_direction` equal to `in` or `out`.

- Anycoin standalone deposits/withdrawals already provide this evidence.
- Trading212 `asset transfer`, `internal transfer` and `portfolio transfer` rows do not
  currently prove direction and must become `needs_review`.

Never infer direction from sign, raw action text, account type or description.

### Embedded conversion

A non-null conversion section is supported only when:

```text
action = currency_conversion
```

A trade or other event carrying conversion legs becomes `needs_review` in this step. The
schema cannot safely prove whether those legs replace or supplement the event cash total,
so creating both could double-count cash.

### Realized P/L

`realized_pnl` is allowed only for `sell`. A value on any other action becomes review.
It remains signed and is event metadata, not a cash movement.

### Promotional flag

`is_promotional = true` is valid only for `airdrop`. A promotional flag on another action
becomes review.

### Fee event

For `action = fee`, the primary `total` is the fee amount. A second non-null `fee` section
would be ambiguous and must become review rather than create two fee movements.

## Strict action field matrix

All omitted optional objects are serialized as `null` according to the established
investment intent contract.

### Buy

Require:

- asset symbol;
- positive quantity;
- positive total;
- optional positive price;
- optional positive fee.

Require null:

- conversion;
- realized P/L;
- asset direction.

### Sell

Require:

- asset symbol;
- positive quantity;
- positive total;
- optional positive price;
- optional positive fee;
- optional signed realized P/L.

Require null:

- conversion;
- asset direction.

### Dividend

Require:

- asset symbol;
- positive total;
- optional positive fee.

Require null:

- quantity;
- price;
- conversion;
- realized P/L;
- asset direction.

### Interest, cash deposit and cash withdrawal

Require positive total and allow an optional positive fee.

Require no non-empty asset identity and null:

- quantity;
- price;
- conversion;
- realized P/L;
- asset direction;
- order ID.

### Currency conversion

Require:

- positive `from` and `to` legs;
- distinct currencies;
- optional positive exchange rate;
- optional positive fee.

Require no non-empty asset identity and null:

- quantity;
- price;
- realized P/L;
- asset direction;
- order ID.

A non-null `total` is allowed only when its amount/currency exactly matches either the
`from` or `to` leg. It is redundant provider evidence and does not create a third movement.

### Asset transfer

Require:

- asset symbol;
- positive quantity;
- explicit direction `in` or `out`;
- optional positive fee.

Require null:

- price;
- total;
- conversion;
- realized P/L.

### Fee

Require positive total.

Require no non-empty asset identity and null:

- quantity;
- price;
- fee;
- conversion;
- realized P/L;
- asset direction;
- order ID.

### Staking reward and airdrop

Require:

- asset symbol;
- positive quantity;
- optional positive total as valuation;
- optional positive price;
- optional positive fee.

If price is present, total must also be present. Require null:

- conversion;
- realized P/L;
- asset direction;
- order ID.

## Immutable plan contracts

Use frozen dataclasses or frozen Pydantic models. Equivalent names are acceptable, but the
semantics must include the following contracts.

### InvestmentAssetResolutionPlan

```text
symbol: uppercase non-blank string
isin: uppercase string or null
name: bounded string or null
asset_type: AssetType
provider: PriceSource
provider_symbol: same canonical symbol
exchange: source value (`trading212` or `anycoin`)
listing_currency_hint: uppercase currency or null
asset_currency_hint: uppercase currency or null
```

Provider mapping:

```text
trading212 -> PriceSource.broker
anycoin    -> PriceSource.exchange
```

Asset type mapping uses only explicit hint evidence:

```text
stock, stocks, equity, equities, share, shares -> stock
etf, exchange traded fund                     -> etf
crypto, cryptocurrency, cryptoasset, token    -> crypto
commodity                                     -> commodity
bond                                           -> bond
cash                                           -> cash
other, missing, unknown                        -> other
```

Anycoin asset plans must resolve to `AssetType.crypto`; a conflicting Anycoin hint fails
closed.

Currency hints:

- buy/sell: listing currency is price currency when present, otherwise total currency;
- dividend: no listing-currency hint is inferred from payout currency;
- crypto transfer/staking/airdrop: symbol may be used as listing and asset currency hint;
- non-crypto transfer/staking/airdrop without price evidence has no currency hint;
- asset currency hint is symbol for crypto, otherwise the listing-currency hint.

B2 may use an existing compatible listing when hints are absent. It must not create a new
non-crypto listing without currency evidence.

### InvestmentMovementPlan

```text
kind: InvestmentMovementKind
direction: MovementDirection
quantity: positive Decimal
currency: uppercase string
requires_asset: bool
price_per_unit: positive Decimal or null
value_amount: positive Decimal or null
value_currency: uppercase string or null
source_symbol: canonical symbol or null
source_asset_type: AssetType or null
note: bounded string or null
```

`requires_asset = true` means B3 must attach both the B2-resolved asset and listing.

### InvestmentEventPostingPlan

```text
account_id
import_batch_id
source_row_id
event_type
date
source
external_id
order_id
description
realized_pnl
realized_pnl_currency
asset_resolution: InvestmentAssetResolutionPlan or null
movements: non-empty tuple[InvestmentMovementPlan, ...]
```

The plan contains no database-generated IDs.

## Event metadata mapping

```text
account_id = batch.account_id
import_batch_id = batch.id
event_type = intent.investment_event_type
date = deterministic canonical timestamp
source = intent.source
external_id = intent.external_id
order_id = intent.order_id
realized_pnl = intent.realized_pnl.amount or null
realized_pnl_currency = intent.realized_pnl.currency or null
archived/deleted = null later in B3
```

Event description is the first non-blank value from:

```text
asset.name
asset.symbol
raw_action
note
```

Do not infer accounting semantics from that text.

Use the intent note as movement note consistently for every generated movement. The note is
metadata only and must not alter movement kind, direction or amount.

## Ordered movement mapping

The tuple order is binding.

### Buy

1. asset `in`:
   - quantity = intent quantity;
   - currency = asset symbol;
   - price per unit = optional price amount;
   - value amount/currency = total;
   - requires asset = true.
2. cash `out`:
   - quantity = total amount;
   - currency = total currency;
   - value amount/currency equal the cash quantity/currency;
   - requires asset = false.
3. optional fee `out` last.

### Sell

1. asset `out` with quantity, optional price and total valuation;
2. cash `in` from total;
3. optional fee `out` last.

### Dividend

1. cash `in` from total with `requires_asset = true` so the payout remains associated with
   its source asset/listing;
2. optional fee `out` last.

### Interest

1. cash `in` from total;
2. optional fee `out`.

### Cash deposit

1. cash `in` from total;
2. optional fee `out`.

### Cash withdrawal

1. cash `out` from total;
2. optional fee `out`.

### Currency conversion

1. source cash `out` from conversion `from`;
2. destination cash `in` from conversion `to`;
3. optional fee `out`.

Do not create a movement for the optional redundant total or exchange rate.

### Asset transfer

1. one asset movement using explicit direction and quantity;
2. optional fee `out`.

### Fee

1. one `fee` movement `out` using total amount/currency.

### Staking reward and airdrop

1. one asset movement `in` using quantity, optional price and optional total valuation;
2. optional fee `out`.

### Fee movement

An auxiliary fee always maps to:

```text
kind = fee
direction = out
quantity = fee amount
currency = fee currency
requires_asset = false
value_amount = fee amount
value_currency = fee currency
price_per_unit = null
```

## Exact representability

Use canonical SQLAlchemy types, not duplicated constants:

```text
TIMESTAMP = PostgreSQL TIMESTAMP(3), timezone=false
QUANTITY = NUMERIC(28,10)
```

Before returning a plan:

- timestamp must survive UTC conversion without sub-millisecond truncation;
- every movement quantity, price and value must equal its scale-10 representation exactly;
- realized P/L must equal its scale-10 representation exactly;
- absolute numeric values must remain below `10 ** (precision - scale)`;
- all decimals must be finite;
- no `float` conversion is permitted.

`conversion.exchange_rate` has no canonical column in the inherited event/movement model.
Validate that it is finite and positive through the classifier, but do not invent a field or
movement for it. The unchanged posting intent remains its audit source.

## Purity and mutation rules

The B1 builder:

- performs no SQL query;
- accepts no session;
- creates no model entity;
- calls no commit or rollback;
- mutates neither normalized JSON nor nested intent dictionaries;
- changes neither row nor batch;
- produces equal plans for equal canonical inputs.
