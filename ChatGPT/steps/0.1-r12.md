# 0.1-R12 — crash-safe asynchronous import and portfolio completion

## Objective

Replace the browser-bound long import/finalization request with a persisted,
authorized, retryable Python job while preserving exact canonical posting,
account isolation, replay, and atomic snapshot publication.

R12 is limited to R12-A through R12-F. It does not start Version 0.2 product
scope, distributed infrastructure, scheduling, cancellation, notifications, or
general-purpose job administration.

## Observed defect baseline

The clean Trading212 import persisted 1,639 investment events and 2,066
movements, but Holding rebuild produced no rows. The request itself completed
successfully; the failure was not a 64-second timeout. Open positions for the
same listing contain actual settlement principal in both EUR and USD, while the
current Holding projection permits only one cost currency.

The active browser import route also runs every file and finalization stage
synchronously. Its 63.878-second response demonstrates a browser-lifetime
coupling even though every individual Python request stayed within its timeout.

## Financial plan

- Asset movements preserve quoted execution unit price in Listing currency.
- `valueAmount` and `valueCurrency` preserve exact fee-separated settlement
  principal; fee remains a separate movement.
- Holding quantity and quote average remain one position per account/listing.
- Holding cost basis is a canonical currency-to-amount breakdown. Acquisitions
  add exact principal to the matching component. Partial disposal reduces every
  component by the same exact remaining-quantity proportion; full disposal
  removes the position.
- Snapshot valuation converts every cost component directly to the requested
  output currency using persisted approved evidence. No pivot, inverse, zero,
  latest-wrong-source, or silent single-currency fallback is allowed.
- Existing single-currency Holdings are backfilled to one exact component.
- Decimal arithmetic and declared NUMERIC/JSON serialization boundaries remain
  explicit and deterministic.

## Security plan

- Protected assets are raw imports, canonical financial history, job payloads,
  progress, errors, and results.
- Only an authenticated account writer may enqueue or retry an import job.
- Status reads re-check user/account isolation; a job id alone grants nothing.
- The worker reloads the initiating user and re-authorizes the account before
  every attempt.
- Payloads contain bounded identifiers and source metadata, never raw rows,
  credentials, tokens, provider responses, or full financial contents.
- Persisted errors are stable safe codes/messages. Tracebacks and raw provider
  or import data stay out of job records and public responses.
- Claiming uses PostgreSQL row locking and a lease. Expired work is recoverable;
  concurrent workers cannot own one live lease.

## Execution order and acceptance criteria

### R12-A — multi-settlement Holding cost basis

Design:

- add a canonical cost-basis breakdown to Holding and snapshot item evidence;
- keep quote-price average separate from settlement principal;
- define deterministic proportional disposal and migration backfill.

Acceptance:

- the observed mixed EUR/USD Trading212 history rebuilds Holdings;
- snapshot cost basis consumes every native component and approved direct FX;
- single-currency behavior and public money contracts remain compatible;
- invalid/missing component or FX evidence remains fail-closed;
- focused unit and PostgreSQL integration tests pass.

### R12-B — persisted job lifecycle

Design:

- Alembic-owned job table and enums for `queued`, `running`, `completed`, and
  `failed`;
- account/user ownership, kind, bounded payload/progress/result, safe error,
  attempt counters, availability, lease, and timestamps;
- deterministic idempotency key for one account and sorted batch set.

Acceptance:

- clean bootstrap, upgrade, schema artifact, SQLAlchemy parity, constraints,
  indexes, and lifecycle transition tests pass;
- duplicate starts replay one canonical job;
- foreign account/user access is impossible.

### R12-C — Python worker and recovery

Design:

- database-backed claim with `FOR UPDATE SKIP LOCKED` and expiring lease;
- at-least-once idempotent execution of parse → normalize → deduplicate →
  classify → post → one coordinated Holding/snapshot finalization;
- bounded retry with deterministic backoff and startup recovery.

Acceptance:

- two workers cannot execute one live lease;
- process interruption leaves a recoverable job;
- replay cannot duplicate canonical rows;
- permanent financial validation failures remain visible and retryable only by
  explicit authorized action.

### R12-D — authorized async job API

Design:

- enqueue returns HTTP 202 with job identity and status;
- status and retry endpoints expose structured progress/result/safe error;
- generated OpenAPI remains the TypeScript contract source.

Acceptance:

- owner/admin/editor role matrix, viewer rejection, foreign user/account/job,
  invalid payload, replay, retry, and API contract tests pass.

### R12-E — frontend progress and atomic publication

Design:

- thin Next.js adapters only;
- upload/register/enqueue returns promptly after durable acceptance;
- browser polls idempotent status with bounded backoff and resumes after reload;
- portfolio/dashboard keep the last complete snapshot while progress is shown,
  then refresh atomically after completion.

Acceptance:

- the browser is not required to remain open;
- no five-second abort can cancel durable processing;
- queued/running/completed/failed/retry UX and contract validation tests pass;
- TypeScript contains no financial or job-transition authority.

### R12-F — resilience and end-to-end closure

Design and verification:

- PostgreSQL tests cover worker crash, lease expiry, concurrent claim, retry,
  duplicate enqueue, partial provider failure, per-current-member publication,
  and final snapshot publication;
- immediately before final snapshot acquisition, publication reconciles one
  durable `ImportJobPublicationTarget` per current account member. A target
  without a job-linked anchor may move forward on retry even when unrelated
  manual evidence occupies its old minute. A stale unpublished anchor is retired
  after canonical-boundary drift and replaced before completion. A same-user bucket collision
  defers the later job to `retry_wait` without consuming an attempt;
- one exact minute `import_event` anchor is required for every current member.
  Under the account membership lock, the worker sets all target `publishedAt`
  values and transitions the job to `completed` atomically. Until then,
  including failed work, current-value reads remain fenced at the last complete
  baseline;
- a viewer's imported shared account may be internally force-refreshed only by
  that publication target. This changes neither the public API nor the viewer's
  HTTP write authority; unrelated viewer accounts remain reuse-only;
- clean register → account → async multi-file import → mixed-currency portfolio
  → dashboard flow passes;
- complete backend, PostgreSQL, frontend, type, lint, format, OpenAPI, migration,
  and boundary gates pass.

## Remediation rule

Only defects directly preventing R12 financial correctness, job durability,
authorization, retry/idempotency, progress, or atomic publication may be added
as R12 remediation items. Each item must be recorded below before implementation
and closed through the same design → implementation → test → verification loop.
