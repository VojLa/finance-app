# 5G-B3 – Canonical investment event writer

## Metadata

- Milestone: `0.1 - Architecture Locked`
- Parent: `5G-B - canonical investment posting foundation`
- Dependency: 5G-B2 merged as `6c878aa67b081bf379f9223ecc05224e0c571d89`
- Source of truth: B1 posting plan, B2 asset resolution, canonical ledger/import models

## Goal

Implement a caller-transaction-owned writer that consumes one validated `InvestmentEventPostingPlan`, resolves its optional asset/listing through B2, creates exactly one `InvestmentEvent` and its deterministic ordered `InvestmentMovement` set, then marks the locked import row imported with only `created_investment_event_id` set.

The writer must support exact replay. It must never commit, roll back, finalize a batch, expose a public endpoint, or repair mismatched history.

## Scope

Prefer:

```text
backend/python/app/modules/imports/investment_posting.py
```

The writer may:

- lock one import row for update;
- rebuild the B1 plan from persisted JSONB;
- call the B2 resolver when `asset_resolution` exists;
- add one event and the exact planned movement tuple;
- flush;
- set `row.status = imported` and `row.created_investment_event_id`;
- validate exact replay.

It must not:

- commit, rollback or begin a nested transaction;
- change batch status/counters;
- set `created_transaction_id`;
- create `AssetAlias`, holdings, snapshots or logs;
- expose `/post` or perform authorization;
- add migrations or schema DDL.

## Input and lock boundary

The service accepts caller-owned `AsyncSession`, `account_id`, locked `ImportBatchModel` and locked `ImportRowModel` or locks the row itself by exact `row.id + batch.id`.

Require the same B1 posting boundary. First write:

```text
batch.status = processing
row.status = pending
created_transaction_id = null
created_investment_event_id = null
```

Replay:

```text
batch.status = processing
row.status = imported
created_transaction_id = null
created_investment_event_id = non-empty
```

All other states raise generic `ImportPostStateError`.

Rebuild the plan through `build_investment_posting_plan`; never trust a caller-supplied plan detached from the locked persisted row.

## First-write algorithm

1. Validate/lock the exact batch-row boundary.
2. Rebuild B1 plan from persisted normalized JSON.
3. If the plan has asset resolution, call B2 and obtain exact asset/listing.
4. If the plan has no asset resolution, no movement may require an asset.
5. Create one event using a repository-standard string UUID.
6. Use one exact naive UTC `TIMESTAMP(3)` bookkeeping timestamp for event and all movements.
7. Create movements in the exact B1 tuple order.
8. For each movement:
   - `event_id` = event ID;
   - `account_id` = plan account;
   - attach resolved `asset_id` and `listing_id` iff `requires_asset = true`;
   - otherwise both links are null;
   - copy all other canonical movement fields exactly.
9. Flush event/movements.
10. Set row imported and set only `created_investment_event_id`.
11. Do not change batch counters/status.

## Event mapping

```text
id                    new UUID string
account_id            plan.account_id
type                  plan.event_type
date                  plan.date
source                plan.source
external_id           plan.external_id
order_id              plan.order_id
description           plan.description
realized_pnl          plan.realized_pnl
realized_pnl_currency plan.realized_pnl_currency
import_batch_id       plan.import_batch_id
archived_at           null
deleted_at            null
updated_at            exact service timestamp
```

## Movement mapping

Preserve B1 tuple order in insertion and replay signatures. The schema has no ordinal column, so replay must compare a canonical multiset/signature with duplicate counts and deterministic sorting; it must not depend on database return order or UUID order.

Canonical signature includes:

```text
kind, direction, quantity, currency,
asset_id, listing_id,
price_per_unit, value_amount, value_currency,
source_symbol, source_asset_type, note
```

Every planned movement requiring an asset must use the same B2-resolved asset/listing. A movement not requiring an asset must have both links null.

## Exact replay

For imported rows:

1. rebuild the B1 plan;
2. load the referenced event for update;
3. load all movements for update;
4. resolve/validate the expected asset/listing through B2 when required;
5. compare every event field exactly;
6. require `archived_at` and `deleted_at` null;
7. compare exact movement count and canonical signatures including duplicate multiplicity;
8. require row linkage unchanged;
9. return the existing event without writes.

Missing event, extra/missing/mismatched movement, wrong asset/listing, wrong account/batch/source/metadata, or archived/deleted history is corruption and must fail closed. Never repair or append missing rows.

## Timestamp and numeric exactness

Use canonical `TIMESTAMP` and `QUANTITY`. B1 already validates financial/date fields; the B3 bookkeeping timestamp must be normalized to exact `TIMESTAMP(3)` before entity creation. Persisted replay values must compare exactly; do not round database data during comparison.

## Transaction ownership and rollback

The caller owns commit/rollback. A caller rollback after flush must remove new event/movements and revert row transition; any B2-created asset/listing in the same transaction must also roll back.

## Concurrency

Real PostgreSQL tests must prove two independent sessions posting the same pending row cannot create two events. The row lock serializes writers: one creates and commits; the second then performs exact replay and returns the same event ID. Exactly one event and the planned movement count remain.
