# 0.1-R11 — Python backend boundary completion and legacy removal

## Objective

Finish the strict Version 0.1 architecture boundary without weakening any R10
financial, security, lineage, exact-money, replay, or fail-closed guarantee.

The final runtime shape is:

```text
Browser / React
  -> Next.js UI and thin authenticated same-origin adapters
  -> FastAPI Python domain services
  -> PostgreSQL through SQLAlchemy
  -> Alembic-only schema migrations
```

Next.js retains NextAuth JWT session management, generated OpenAPI types,
request allowlisting, safe response mapping, and presentation-only formatting.
It must not retain Prisma, SQL, password verification, provider I/O, finance
calculation, authorization over financial data, or canonical writes.

## Audit base

The implementation starts from `2dc186d` plus the R11 planning/status changes.
The R10-E2 audit closed the historical 92-row Version 0.1 matrix with 91 PASS
and one explicit OUT OF SCOPE. R11 is a stricter cleanup phase: areas previously
tolerated as operational or compatibility TypeScript are now in scope.

Repository inspection found these unfinished runtime groups:

- credential verification, registration, and password change use Prisma/bcrypt
  in Next.js;
- transactions, categories, budgets, and operational dashboard are TS/Prisma
  business implementations used by active pages;
- manual investment posting and symbol detail use TS ledger/Holding/snapshot
  services and Prisma;
- account share/cash and import-preview routes remain registered Prisma
  compatibility surfaces even though the current UI does not consume them;
- portfolio, net-worth, snapshot-recalculate, rates, TS parsers, TS ledger,
  TS rates, and TS snapshot engines remain registered or reachable legacy;
- the active legacy operational dashboard can still create Yahoo FX evidence;
- Python FX evidence lookup is not consistently source-qualified;
- Prisma remains a runtime client/mirror and owns seed/backfill utilities even
  though Alembic is the sole migration owner.

## Provider decision for R11

Twelve Data is the selected single production FX runtime provider for direct
currency pairs. The official individual Basic plan currently states internal
non-display usage and real-time forex access; the official API documents direct
`BASE/QUOTE` currency conversion with optional historical date and a provider
timestamp. R11 will use exact direct pair evidence and will not synthesize
inverse or CZK-pivot rows.

CNB/Yahoo source enum values and historical rows may remain as audit history,
but neither provider remains registered for new production FX acquisition after
the cutover. A future commercial/public deployment must re-check business data
licensing before release.

## Commit policy

Each completed step receives one clear commit (or a short, explicitly grouped
series if a generated contract/migration must be isolated). A step is not
marked complete until its focused tests and applicable PostgreSQL tests pass.
Legacy deletion is always in the same step as, or after, proven replacement.

## Final Definition of Done

- no production TypeScript imports Prisma, SQL, bcrypt, provider SDKs, or a TS
  finance/business service;
- no active Next route owns authorization over finance, canonical writes, or
  finance calculations;
- all active business pages use Python-generated contracts through thin
  same-origin adapters;
- Python exclusively owns identity credentials, accounts, transactions,
  categories, budgets, imports, ledger, Holdings, market evidence, snapshots,
  portfolio, dashboard, and history;
- Twelve Data is the only registered production FX runtime provider and every
  non-identity conversion uses exact direct-pair evidence;
- Alembic is the only executable migration/schema owner;
- the Prisma runtime and legacy TS engines/dependencies are absent;
- clean and upgraded PostgreSQL scenarios reconcile without finance data loss;
- R10 remains PASS and the new R11 audit is PASS.
