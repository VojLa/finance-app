# Step 5M — Snapshot-backed application cutover

Step 5M connects the completed coordinated snapshot refresh and exact
snapshot-backed read APIs without introducing another financial authority.

- **5M-A** — exact refresh read manifest (implemented);
- **5M-B** — typed frontend Python API adapter (planned);

## 5M-A exact refresh read manifest

Every successful non-empty
`POST /api/v1/snapshot-refresh/recalculate` response now contains the exact
read manifest required by both `POST /api/v1/portfolio/snapshot` and
`POST /api/v1/dashboard/snapshot`:

```text
timestamp
granularity
currency
calculationVersion
accounts:
  accountId
  snapshotId
```

The sole manifest authority is the already validated
`ExecuteUserSnapshotRefreshResult`. Timestamp, granularity, output currency,
and calculation version are copied from that result. Account and snapshot IDs
are mapped one-to-one, in their existing deterministic order, from
`required_account_snapshot_identities`. The service does not issue another
database read, rediscover membership accounts, select a latest snapshot, or
repair or sort inconsistent lineage.

For a non-empty result, these five fields form a syntactically valid existing
5L request and the client must carry them unchanged. Account and snapshot IDs
must be nonblank and individually unique; manifest length must equal both the
validated executor lineage and selected-account count; and ordered identities
must match the validated account executions exactly. The calculation version
is the executor result value, not a response constant.

An empty successful result is the explicit no-account state. Its `accounts`
value is exactly `[]`, its selected-account count and every account snapshot
count are zero, and it means that the user has no snapshot-capable account.
This is a complete empty manifest, not a partial manifest, error, fallback, or
latest lookup. The client must not submit it to either 5L endpoint, because the
unchanged 5L request contracts require a non-empty account set. It must not
discover accounts, create a synthetic account selector, or look up a latest
snapshot.

The public change is additive. Existing refresh response fields and error
contracts remain unchanged, and the existing endpoint remains the only manual
refresh route. The public manifest exposes only `accountId` and `snapshotId`;
membership, role, refresh mode, write disposition, selected item lineage,
market evidence, financial breakdowns, and persistence audit fields remain
internal.

Tests prove that selecting the five manifest fields from non-empty public
refresh JSON produces a syntactically valid request for both 5L endpoints
without changing identity, filling a constant, querying the database, sorting
accounts, or using a fallback. Real PostgreSQL bridge tests prove the same
workflow for created, replayed, reused, mixed refresh/reuse-only, investment,
liability, and authorized role scenarios. Empty-user unit and PostgreSQL
evidence proves the successful deterministic empty state and the intentional
5L request rejection.

5M-A adds no frontend integration, endpoint, schema, writer, executor,
financial calculation, history, cache, or scheduler. 5M-B must expose an
explicit discriminated `ready` or `empty` workflow state: `ready` carries the
server-issued non-empty manifest to existing 5L requests, while `empty` calls
neither 5L read endpoint and creates no synthetic selector.
