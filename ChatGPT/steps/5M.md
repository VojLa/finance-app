# Step 5M — Snapshot-backed application cutover

Step 5M connects the completed coordinated snapshot refresh and exact
snapshot-backed read APIs without introducing another financial authority.

- **5M-A** — exact refresh read manifest (implemented);
- **5M-B** — typed frontend Python API adapter (implemented);
- **5M-C** — portfolio page snapshot cutover (implemented);
- **5M-D** — dashboard page snapshot cutover (implemented);
- **5M final audit** — planned.

## 5M-A exact refresh read manifest

Every successful non-empty
`POST /api/v1/snapshot-refresh/recalculate` response now contains the exact
read manifest required by both `POST /api/v1/portfolio/snapshot` and
`POST /api/v1/dashboard/snapshot`:

```text
timestamp
granularity
currency
calculationVersion
accounts:
  accountId
  snapshotId
```

The sole manifest authority is the already validated
`ExecuteUserSnapshotRefreshResult`. Timestamp, granularity, output currency,
and calculation version are copied from that result. Account and snapshot IDs
are mapped one-to-one, in their existing deterministic order, from
`required_account_snapshot_identities`. The service does not issue another
database read, rediscover membership accounts, select a latest snapshot, or
repair or sort inconsistent lineage.

For a non-empty result, these five fields form a syntactically valid existing
5L request and the client must carry them unchanged. Account and snapshot IDs
must be nonblank and individually unique; manifest length must equal both the
validated executor lineage and selected-account count; and ordered identities
must match the validated account executions exactly. The calculation version
is the executor result value, not a response constant.

An empty successful result is the explicit no-account state. Its `accounts`
value is exactly `[]`, its selected-account count and every account snapshot
count are zero, and it means that the user has no snapshot-capable account.
This is a complete empty manifest, not a partial manifest, error, fallback, or
latest lookup. The client must not submit it to either 5L endpoint, because the
unchanged 5L request contracts require a non-empty account set. It must not
discover accounts, create a synthetic account selector, or look up a latest
snapshot.

The public change is additive. Existing refresh response fields and error
contracts remain unchanged, and the existing endpoint remains the only manual
refresh route. The public manifest exposes only `accountId` and `snapshotId`;
membership, role, refresh mode, write disposition, selected item lineage,
market evidence, financial breakdowns, and persistence audit fields remain
internal.

Tests prove that selecting the five manifest fields from non-empty public
refresh JSON produces a syntactically valid request for both 5L endpoints
without changing identity, filling a constant, querying the database, sorting
accounts, or using a fallback. Real PostgreSQL bridge tests prove the same
workflow for created, replayed, reused, mixed refresh/reuse-only, investment,
liability, and authorized role scenarios. Empty-user unit and PostgreSQL
evidence proves the successful deterministic empty state and the intentional
5L request rejection.

5M-A adds no frontend integration, endpoint, schema, writer, executor,
financial calculation, history, cache, or scheduler. 5M-B must expose an
explicit discriminated `ready` or `empty` workflow state: `ready` carries the
server-issued non-empty manifest to existing 5L requests, while `empty` calls
neither 5L read endpoint and creates no synthetic selector.

## 5M-B typed frontend Python API adapter

The Next.js server now owns two bodyless POST workflow routes:

```text
POST /api/snapshot-workflow/portfolio
POST /api/snapshot-workflow/dashboard
```

Each handler validates the existing NextAuth session exactly once and delegates
to one shared server-only workflow. The browser never calls FastAPI directly.
Its NextAuth cookie and browser authorization headers are never forwarded.
Instead, immediately before every FastAPI request, the adapter creates a fresh
short-lived HS256 token containing only the verified user subject, optional
email, issuer, audience, `iat`, `exp`, and unique `jti`. The token and shared
secret remain server-side and are never returned or logged.

FastAPI OpenAPI is the sole source for refresh, selector, portfolio, and
dashboard HTTP types. A deterministic exporter builds the schema directly from
`create_app(...)` without lifespan or database access; `openapi-typescript`
generates the tracked TypeScript contract. The cross-platform check mode
generates only in a temporary directory and fails on drift without modifying
the working tree.

The adapter first calls coordinated refresh exactly once. A valid non-empty
manifest is transferred unchanged and in the same order to exactly one
existing 5L endpoint. The adapter performs no account discovery, latest lookup,
sorting, filtering, repair, FX, pricing, Decimal conversion, or financial
calculation. It validates common response identity plus exact portfolio
account/snapshot pairs or the dashboard account set before returning:

```text
status: "ready"
refresh: safe refresh summary without accounts
data: unchanged generated 5L response
```

A valid empty manifest returns:

```text
status: "empty"
refresh: safe refresh summary without accounts
```

The empty branch calls neither 5L endpoint and exposes no manifest, account ID,
or snapshot ID. Stable Next-owned errors distinguish browser authentication,
configuration, unavailable transport, and incompatible Python contracts; safe
Python 404/409 errors may pass through without request IDs or raw bodies.

5M-B itself did not change the portfolio page, dashboard page, legacy routes,
Python financial code, database schema, or migrations. 5M-C now cuts over only
the portfolio page; 5M-D will separately cut over the dashboard page.

## 5M-C portfolio page snapshot cutover

The portfolio page now obtains all current financial values through the
bodyless, no-store:

```text
POST /api/snapshot-workflow/portfolio
```

Initial load calls the workflow once. The single `Aktualizovat portfolio`
action calls that same workflow once again. The page no longer calls the legacy
current `/api/portfolio` route, rates refresh, legacy snapshot recalculation,
price providers, or account-scoped snapshot routes.

The page owns an explicit `loading`, `empty`, `ready`, or `error` state. An
empty workflow result is shown as the successful no-account state and performs
no fallback request. A ready result uses the generated portfolio response
without exposing the refresh manifest. Safe adapter errors are displayed
without raw bodies, request IDs, URLs, tokens, or tracebacks, and no state
automatically retries.

The page model is a pure presentation adapter over the exact response.
Aggregate cards use the server aggregate summary object. A selected account
uses that account's server summary and positions from the already loaded
response; selector changes make no backend request and never change the
manifest. Decimal strings remain unchanged in view state and table/card
presentation. There is no browser-side total, cost, P/L, return, liability,
allocation, FX, or price calculation and no missing-value financial fallback.

Position rows use only snapshot-backed position fields. Account-local
allocation uses the backend `allocationPct` string, with a presentation-only
conversion isolated at the Recharts leaf. The portfolio response does not
contain a global multi-account position allocation or return percentage, so
the aggregate allocation chart and return card are intentionally absent rather
than reconstructed in the browser.

`GET /api/portfolio/history` remains temporarily for the historical chart and
range selector only. Its latest point never becomes a current value and
history supplies no current cards, positions, allocation, accounts, or
currency. History cutover is outside 5M-C.

The legacy current portfolio route remains in the repository for compatibility,
but the portfolio page no longer consumes it. The separate dashboard cutover is
implemented in 5M-D.

## 5M-D dashboard page snapshot cutover

The dashboard now loads its financial and operational sections through two
independent no-store boundaries:

```text
POST /api/snapshot-workflow/dashboard
GET  /api/dashboard
```

The bodyless snapshot workflow is the sole page authority for total value,
assets, liabilities, cash, investments, investment cost basis, realized and
unrealized P/L, account and position counts, financial account cards,
asset-type allocation, and top positions. Account cards are snapshot-backed,
allocation is calculated by the server, and top positions retain the server's
ranking. Decimal financial strings remain exact in page state and presentation;
only the Recharts leaf converts an allocation percentage for drawing.

The temporary legacy request supplies only operational current-month income,
expenses and net cash flow, budget, expense categories, monthly trends, and
recent transactions. Its `cashValueCzk`, `portfolioValueCzk`,
`liabilitiesValueCzk`, `netWorthCzk`, and `accountBalances` fields are discarded
by the operational adapter and never become page state. The operational
response is not a financial fallback and cannot alter snapshot finance.

Financial and operational loading and error states are separate. Snapshot
`empty` is an explicit no-account financial state while successful operational
widgets may remain visible. A snapshot error never reveals legacy financial
values; an operational error never removes a successful snapshot section.
Initial load issues each request once, while the explicit financial refresh
calls only the snapshot workflow and performs no retry.

The portfolio page remains snapshot-backed. The legacy dashboard route remains
registered only for the temporary operational widgets and is unchanged. The
next step is the 5M final audit.
