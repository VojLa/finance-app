# Step 5M — Snapshot-backed application cutover

Step 5M connects the completed coordinated snapshot refresh and exact
snapshot-backed read APIs without introducing another financial authority.

- **5M-A** — exact refresh read manifest (implemented);
- **5M-B** — typed frontend Python API adapter (planned);
- **5M-C** — portfolio page snapshot cutover (planned);
- **5M-D** — dashboard page snapshot cutover (planned);
- **5M final audit** — planned.

## 5M-A exact refresh read manifest

Every successful `POST /api/v1/snapshot-refresh/recalculate` response now
contains the exact read manifest required by both
`POST /api/v1/portfolio/snapshot` and
`POST /api/v1/dashboard/snapshot`:

```text
timestamp
granularity
currency
calculationVersion
accounts:
  accountId
  snapshotId
```

The sole manifest authority is the already validated
`ExecuteUserSnapshotRefreshResult`. Timestamp, granularity, output currency,
and calculation version are copied from that result. Account and snapshot IDs
are mapped one-to-one, in their existing deterministic order, from
`required_account_snapshot_identities`. The service does not issue another
database read, rediscover membership accounts, select a latest snapshot, or
repair or sort inconsistent lineage.

The manifest is complete or the whole refresh result fails closed. Its account
and snapshot IDs must be nonblank and individually unique; its length must
equal both the validated executor lineage and selected-account count; and its
ordered identities must match the validated account executions exactly. The
calculation version is the executor result value, not a response constant.

The public change is additive. Existing refresh response fields and error
contracts remain unchanged, and the existing endpoint remains the only manual
refresh route. The public manifest exposes only `accountId` and `snapshotId`;
membership, role, refresh mode, write disposition, selected item lineage,
market evidence, financial breakdowns, and persistence audit fields remain
internal.

Tests prove that selecting the five manifest fields from the public refresh
JSON produces a syntactically valid request for both 5L endpoints without
changing identity, filling a constant, querying the database, sorting
accounts, or using a fallback. Real PostgreSQL bridge tests prove the same
workflow for created, replayed, reused, mixed refresh/reuse-only, investment,
liability, and authorized role scenarios.

5M-A adds no frontend integration, endpoint, schema, writer, executor,
financial calculation, history, cache, or scheduler. 5M-B will add only the
typed transport adapter that carries this server-issued manifest to the
existing 5L requests.
