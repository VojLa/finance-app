# Step 5J — Net-worth snapshots

## Roadmap

`NetWorthSnapshot` is a derived user-level read model. It aggregates complete,
coherent `AccountSnapshot` values and never replaces account history, canonical
investment history, Holdings, liability observations, or account snapshots.

Step 5J is split into:

- **5J-A** — pure deterministic net-worth projection (implemented);
- **5J-B** — persisted account-snapshot evidence selection and coverage proof
  (implemented);
- **5J-C** — exact physical `NetWorthSnapshot` persistence projection
  (implemented);
- **5J-D** — atomic database writer (implemented);
- **5J-E** — authorization and public orchestration (implemented after merge).

5J-A through 5J-D are implemented; 5J-E is implemented after merge. No
scheduler or automatic account-snapshot creation exists in the Python
net-worth module.

## Physical schema audit

The inherited physical identity is:

```text
(userId, timestamp, currency, granularity)
```

The physical financial fields are:

```text
cashValue                       NUMERIC(18,6) not null
portfolioValue                  NUMERIC(18,6) not null
liabilitiesValue                NUMERIC(18,6) not null
totalNetWorth                   NUMERIC(18,6) not null
cashValueByCurrency             JSONB null
portfolioValueByCurrency        JSONB null
liabilitiesValueByCurrency      JSONB null
totalNetWorthByCurrency         JSONB null
exchangeRates                   JSONB null
```

Persistence metadata (`id`, `source`, recalculation flag, calculation and
creation timestamps) belongs to later 5J steps. 5J-A uses `user_id`, not a new
portfolio, household, or owner abstraction.

## Pure 5J-A input

`NetWorthProjectionInput` contains:

- user ID;
- exact bucket timestamp and granularity;
- output currency;
- calculation version;
- an immutable tuple of typed account-snapshot evidence.

Each account value contains the physical snapshot identity, account type,
account and snapshot currencies, exact timestamp/granularity, `cashValue`,
`investmentValue`, `liabilitiesValue`, and `totalValue`. Optional typed native
breakdowns preserve persisted cash, investment, and liability evidence where
available. ORM models and caller-computed portfolio aggregates are forbidden.

The complete empty tuple is valid and produces exact zero aggregates. Whether
a persisted user truly has zero eligible accounts belongs to 5J-B.

## Supported account types

5J-A accepts only account snapshots that 5I can physically persist:

| Account type                          | Pure net-worth rule                                            |
| ------------------------------------- | -------------------------------------------------------------- |
| `broker`, `exchange`, `crypto_wallet` | signed cash plus nonnegative investment value; zero liability  |
| `credit_card`, `loan`, `mortgage`     | zero cash and investment; nonnegative liability                |
| `bank`, `cash`, `savings`             | rejected until their physical 5I snapshot contract is complete |

No unsupported account may be silently omitted.

## Financial formulas

For every account:

```text
accountAssets = cashValue + investmentValue
accountNet = accountAssets - liabilitiesValue
accountNet = AccountSnapshot.totalValue
```

For the user:

```text
cashValue = Σ account.cashValue
portfolioValue = Σ account.investmentValue
assetsValue = cashValue + portfolioValue
liabilitiesValue = Σ positive account.liabilitiesValue
netWorthValue = assetsValue - liabilitiesValue
netWorthValue = Σ account.totalValue
```

Both net-worth formulas must agree exactly. Cost basis, deposits, realized or
unrealized P/L, fees, and taxes are not assets and are not aggregated here.

Investment-account cash may be signed. Negative cash reduces assets; it is not
reclassified as liability. Investment value and liability magnitude must be
nonnegative. Liability accounts preserve the 5I convention: positive debt and
negative net contribution. An explicit zero liability still contributes one
counted account and is not equivalent to missing evidence.

## Time, currency, and identity

The requested timestamp must be exact naive `TIMESTAMP(3)` and aligned to
minute, hour, day, ISO-Monday week, or first-day month granularity. Every
account snapshot must match that timestamp and granularity exactly.
Latest-as-of selection is deferred to 5J-B.

Every account currency must be a canonical uppercase three-letter code.
Snapshot currency must equal the requested output currency. Account currency
may differ because conversion belongs to the already-persisted AccountSnapshot
evidence; 5J-A performs no FX selection or conversion.

Account and snapshot IDs are independently unique. Duplicate accounts,
duplicate snapshots, or one snapshot assigned to multiple accounts fail
closed. Contributions are ordered by `(account_id, snapshot_id)` and
account-type aggregates by enum value.

## Currency breakdowns

Native currency breakdowns are immutable sorted tuples with category-specific
numeric contracts:

```text
cashValueByCurrency          MONEY / NUMERIC(18,6)
portfolioValueByCurrency     QUANTITY / NUMERIC(28,10)
liabilitiesValueByCurrency   MONEY / NUMERIC(18,6)
totalNetWorthByCurrency      QUANTITY / NUMERIC(28,10)
```

Cash may be signed, and investment/liability amounts must be nonnegative.
Scalar net-worth values remain MONEY. Native portfolio values preserve all ten
fractional digits, and the total native breakdown uses QUANTITY because it
combines MONEY cash and liability values with QUANTITY portfolio values.
MONEY values are exactly representable by QUANTITY; no rounding or truncation
is permitted.

A category is aggregated only when every account supplies that category's
breakdown. `None` means unavailable and propagates to the aggregate; it is
never converted to an empty exact breakdown. The only neutral exception is an
unavailable nonnegative portfolio or liability category whose exact scalar
aggregate is zero: it contributes zero to the total-native calculation while
its category output remains `None`. This is required for the physical
AccountSnapshot liability boundary, which has no liability-breakdown column.
When the required native evidence is complete:

```text
totalNetWorthByCurrency =
    cashValueByCurrency
  + portfolioValueByCurrency
  - liabilitiesValueByCurrency
```

5J-A consumes no FX evidence. Selection, conversion audit, and physical JSONB
serialization belong to later steps.

## Persisted 5J-B evidence selection

`NetWorthEvidenceService` accepts only a user ID and server-selected snapshot
identity fields. It loads the persisted User, then every Account reachable
through a persisted accepted `AccountMember` row. Membership has no separate
revoked or active flag, so every persisted membership is current access.

The schema has no historical account activation interval. Consequently 5J-B
uses current state: a consistently archived Account (`isArchived = true` and
an exact `archivedAt`) is excluded regardless of the requested historical
bucket. Contradictory archive fields fail closed. Active bank, cash, or savings
accounts invalidate the complete user result rather than being silently
omitted.

For each eligible active account, one batched query requires exactly one
`AccountSnapshot` matching:

```text
timestamp
granularity
currency
calculationVersion
```

The physical account relation, persisted Account type and currency, snapshot
source, timestamps, all financial scalar fields, and every AccountSnapshot
currency-breakdown JSONB field are validated. The canonical JSONB form is an
object with uppercase three-letter keys and fixed-scale decimal strings:
`NUMERIC(18,6)` fields use six fractional digits and quantity breakdowns use
ten. SQL `NULL` remains `None`; `{}` becomes the exact empty tuple. Floats,
lists, nested values, scientific notation, invalid scale, and overflow fail.
The parsed investment QUANTITY reaches 5J-A unchanged, where portfolio
aggregation and total-native arithmetic retain its exact scale-10 value.

The physical `AccountSnapshot` table has no liability-breakdown JSONB column.
5J-B therefore passes `None` for that optional 5J-A evidence rather than
inventing a breakdown or migration. Liability scalar completeness remains the
single-currency 5I contract.

5J-B invokes 5J-A exactly once and returns the projection plus sorted immutable
account/snapshot identities. A real persisted User with zero current active
accounts produces the exact empty projection. Missing User, unsupported active
account, missing or extra snapshot, mismatched version, or any corruption uses
one generic fail-closed error.

## Transaction and concurrency contract

5J-B owns no transaction and never begins, commits, rolls back, flushes, or
writes. Because User, membership/account discovery, and snapshot selection are
separate queries, the caller must open a `REPEATABLE READ` or `SERIALIZABLE`
transaction first. The service verifies both an active transaction and its
isolation level before evidence reads. This produces one coherent PostgreSQL
snapshot even if another transaction concurrently commits a new membership,
Account, or AccountSnapshot.

`READ COMMITTED` is rejected; a one-sided advisory lock is not used or claimed
as protection. 5J-C remains a pure physical projection, while the later writer
must own the required coherent outer transaction.

## Physical 5J-C persistence projection

`build_net_worth_snapshot_persistence_projection()` accepts only one complete
5J-B result and explicit persistence metadata (`source`, `calculatedAt`,
`createdAt`, recalculation flag). It creates no ORM instance, reads no clock,
performs no I/O, and owns no transaction. Every 5J-A scalar, account
contribution, account-type aggregate, and 5J-B selected account/snapshot
identity is revalidated before a row contract is returned.

The complete physical `NetWorthSnapshot` identity is:

```text
(userId, timestamp, currency, granularity)
```

Its ID is UUIDv5 in a fixed net-worth namespace over the NUL-delimited
canonical identity values. Source, persistence timestamps, calculation
version, lineage IDs, and financial values do not affect identity.
`isRecalculated` is true exactly for `manual_recalculation`; the calculation
version comes only from the validated 5J-A projection.

All physical scalar values use MONEY:

```text
cashValue        = projection.cash_value
portfolioValue   = projection.portfolio_value
liabilitiesValue = projection.liabilities_value
totalNetWorth    = projection.net_worth_value
totalNetWorth    = cashValue + portfolioValue - liabilitiesValue
```

Native JSONB values retain the category-specific precision matrix: cash and
liability use six-place MONEY strings, while portfolio and total native net
worth use ten-place QUANTITY strings. Keys are sorted uppercase currencies;
values are fixed-scale strings, never JSON numbers. `None` maps to SQL NULL,
the exact empty tuple maps to `{}`, and materialization returns fresh mutable
dictionaries without exposing the immutable row contract.

Before serializing JSON, 5J-C rederives `totalNetWorthByCurrency` from the
validated category tuples as cash plus portfolio minus liabilities. Every
intermediate operation uses exact QUANTITY arithmetic, and the supplied total
tuple must equal the rederived tuple exactly, including availability, currency
set, deterministic order, signs, amounts, and preserved zero entries.

The availability rules bind to 5J-A: unavailable cash always makes the total
unavailable, even when its scalar is zero. An unavailable portfolio or
liability breakdown is neutral only when its validated scalar is exactly zero;
the category itself still persists as SQL NULL. Nonzero unavailable portfolio
or liability evidence makes the total unavailable. This validation performs
no FX conversion, rounding, inference, or removal of currencies whose exact
total cancels to zero.

`exchangeRates` is SQL NULL because 5J-A/B consume no FX evidence: they
aggregate already-converted AccountSnapshot scalars and preserve native values
without performing conversion. Selected AccountSnapshot IDs remain in an
immutable non-persisted audit result because the current schema has no lineage
columns. They are not stored in `exchangeRates` or another unrelated field.

The result maps all and only SQLAlchemy `NetWorthSnapshotModel` attributes and
can construct the ORM shape without opening a session. Actual insert, exact
replay, conflict handling, locking, and transaction ownership belong to 5J-D.

## Atomic 5J-D database writer

`NetWorthSnapshotWriter` is an internal transaction-owning boundary. Its
immutable command contains only the user, physical snapshot key, calculation
version, source, recalculation flag, and exact `TIMESTAMP(3)` persistence
metadata. It accepts no financial values, account IDs, source-snapshot IDs,
JSON, or caller-built plans, and it rejects an already active session
transaction.

Every attempt begins with `SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` as
its first SQL statement. It then acquires a transaction advisory lock over the
NUL-delimited physical key:

```text
net_worth:snapshot
user_id
timestamp ISO milliseconds
currency
granularity
```

The signed bigint lock ID uses the established SHA-256 convention. Locks are
key-scoped: different users or timestamps proceed independently.

Inside that same coherent transaction, the writer invokes 5J-B once and 5J-C
once, revalidates command-to-plan identity, and only then loads the physical
key with `FOR UPDATE`. An existing row is a replay only when all 19 physical
attributes match exactly, including metadata, every JSON string, and SQL NULL
versus `{}`. Differences and deterministic-ID collisions are conflicts; the
writer never updates, repairs, overwrites, or upserts.

For creation, one complete ORM row is added, flushed, reloaded with
`populate_existing`, and compared again across all physical attributes before
the outer transaction commits. Any exception rolls back the whole attempt and
source `User`, `Account`, `AccountMember`, `AccountSnapshot`, and
`AccountSnapshotItem` rows remain read-only.

PostgreSQL may establish a SERIALIZABLE snapshot while a same-key request
waits on the advisory lock. Therefore SQLSTATE `40001`, `40P01`, and `23505`
restart the complete transaction, lock, evidence, and projection sequence,
with a strict maximum of three attempts. A unique violation is never treated
as replay by itself. Evidence, projection, command, conflict, constraint, and
other SQL failures are not retried.

The current schema has no persisted source-AccountSnapshot lineage. Current
5J-B/5J-C lineage is still revalidated and returned as counts, but replay can
compare only the exact physical `NetWorthSnapshot` row. Authorization, a
public operation, scheduling, and automatic source-snapshot creation are
separate boundaries; the manual public operation is defined by 5J-E below.

## Authorized manual 5J-E recalculation

The authenticated public operation is:

```text
POST /api/v1/net-worth/snapshots/recalculate
```

It accepts no body, path parameter, query parameter, user ID, currency,
timestamp, account identity, source-snapshot identity, or financial value. The
target is always `AuthenticatedPrincipal.user_id`. The application service
loads that exact persisted User and takes the output currency only from the
canonical uppercase `User.baseCurrency`; it never hardcodes CZK or derives the
net-worth currency from an Account.

Authentication and the manual User lookup share the request session and
therefore autobegin a read transaction. The service commits that read
transaction and verifies an idle session before constructing 5J-D. Validation
failure rolls back the read transaction. Inside the fresh SERIALIZABLE writer
transaction, 5J-B reloads the User with `populate_existing` and requires the
current persisted base currency to equal the command currency. A concurrent
base-currency change therefore fails the complete operation without a stale
snapshot.

One injected clock value is converted to UTC when timezone-aware, stripped to
naive time, and truncated to an exact minute. That same deterministic bucket is
used for snapshot identity, `calculatedAt`, and `createdAt`; the source is
`manual_recalculation`, recalculation is true, and calculation version is the
single server-owned constant. Same-minute exact state replays through the
unchanged 5J-D writer.

The public response exposes only snapshot ID, created/replayed status, bucket,
granularity, currency, account count, and selected source-snapshot count. It
never returns the user ID, account IDs, source AccountSnapshot IDs, projection,
audit tuples, JSONB, or financial totals. Evidence/projection/write-state
failures map to generic `net_worth_snapshot_unavailable` 409 responses;
physical conflicts map to `net_worth_snapshot_conflict` 409. Authentication
errors retain the central auth contract, and unexpected programming failures
remain server errors.

5J-E never creates missing AccountSnapshot rows and never omits an active
supported account. Every current supported account must already have one exact
snapshot at the same minute, granularity, base currency, and calculation
version. Scheduling, background work, automatic source creation, historical
net-worth reads, and persisted source-snapshot lineage remain outside the
manual 5J chain.

## Numeric and failure contract

Every scalar, contribution, type aggregate, and final scalar must be a finite
Python `Decimal` exactly representable by MONEY `NUMERIC(18,6)`. Native cash
and liability breakdowns use MONEY; native portfolio and total breakdowns use
QUANTITY `NUMERIC(28,10)`. Floats, NaN, infinity, over-scale values, precision
overflow, and aggregate overflow fail. There is no rounding, truncation,
quantization policy, clamping, or partial result.

All failures use:

```text
Account snapshots cannot produce a complete net worth projection.
```

The message exposes no account, snapshot, currency, value, or invariant detail.
The function performs no I/O, generates no IDs, reads no clock, and mutates no
input.
