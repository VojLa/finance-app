# Step 5J — Net-worth snapshots

## Roadmap

`NetWorthSnapshot` is a derived user-level read model. It aggregates complete,
coherent `AccountSnapshot` values and never replaces account history, canonical
investment history, Holdings, liability observations, or account snapshots.

Step 5J is split into:

- **5J-A** — pure deterministic net-worth projection (implemented);
- **5J-B** — persisted account-snapshot evidence selection and coverage proof;
- **5J-C** — exact physical `NetWorthSnapshot` persistence projection;
- **5J-D** — atomic database writer;
- **5J-E** — authorization and public orchestration.

Only 5J-A is implemented. No database read, write, endpoint, scheduler, or
automatic snapshot creation exists in the Python net-worth module.

## Physical schema audit

The inherited physical identity is:

```text
(userId, timestamp, currency, granularity)
```

The physical financial fields are:

```text
cashValue                       NUMERIC(18,6) not null
portfolioValue                  NUMERIC(18,6) not null
liabilitiesValue                NUMERIC(18,6) not null
totalNetWorth                   NUMERIC(18,6) not null
cashValueByCurrency             JSONB null
portfolioValueByCurrency        JSONB null
liabilitiesValueByCurrency      JSONB null
totalNetWorthByCurrency         JSONB null
exchangeRates                   JSONB null
```

Persistence metadata (`id`, `source`, recalculation flag, calculation and
creation timestamps) belongs to later 5J steps. 5J-A uses `user_id`, not a new
portfolio, household, or owner abstraction.

## Pure 5J-A input

`NetWorthProjectionInput` contains:

- user ID;
- exact bucket timestamp and granularity;
- output currency;
- calculation version;
- an immutable tuple of typed account-snapshot evidence.

Each account value contains the physical snapshot identity, account type,
account and snapshot currencies, exact timestamp/granularity, `cashValue`,
`investmentValue`, `liabilitiesValue`, and `totalValue`. Optional typed native
breakdowns preserve persisted cash, investment, and liability evidence where
available. ORM models and caller-computed portfolio aggregates are forbidden.

The complete empty tuple is valid and produces exact zero aggregates. Whether
a persisted user truly has zero eligible accounts belongs to 5J-B.

## Supported account types

5J-A accepts only account snapshots that 5I can physically persist:

| Account type | Pure net-worth rule |
| --- | --- |
| `broker`, `exchange`, `crypto_wallet` | signed cash plus nonnegative investment value; zero liability |
| `credit_card`, `loan`, `mortgage` | zero cash and investment; nonnegative liability |
| `bank`, `cash`, `savings` | rejected until their physical 5I snapshot contract is complete |

No unsupported account may be silently omitted.

## Financial formulas

For every account:

```text
accountAssets = cashValue + investmentValue
accountNet = accountAssets - liabilitiesValue
accountNet = AccountSnapshot.totalValue
```

For the user:

```text
cashValue = Σ account.cashValue
portfolioValue = Σ account.investmentValue
assetsValue = cashValue + portfolioValue
liabilitiesValue = Σ positive account.liabilitiesValue
netWorthValue = assetsValue - liabilitiesValue
netWorthValue = Σ account.totalValue
```

Both net-worth formulas must agree exactly. Cost basis, deposits, realized or
unrealized P/L, fees, and taxes are not assets and are not aggregated here.

Investment-account cash may be signed. Negative cash reduces assets; it is not
reclassified as liability. Investment value and liability magnitude must be
nonnegative. Liability accounts preserve the 5I convention: positive debt and
negative net contribution. An explicit zero liability still contributes one
counted account and is not equivalent to missing evidence.

## Time, currency, and identity

The requested timestamp must be exact naive `TIMESTAMP(3)` and aligned to
minute, hour, day, ISO-Monday week, or first-day month granularity. Every
account snapshot must match that timestamp and granularity exactly.
Latest-as-of selection is deferred to 5J-B.

Every account currency must be a canonical uppercase three-letter code.
Snapshot currency must equal the requested output currency. Account currency
may differ because conversion belongs to the already-persisted AccountSnapshot
evidence; 5J-A performs no FX selection or conversion.

Account and snapshot IDs are independently unique. Duplicate accounts,
duplicate snapshots, or one snapshot assigned to multiple accounts fail
closed. Contributions are ordered by `(account_id, snapshot_id)` and
account-type aggregates by enum value.

## Currency breakdowns

Native currency breakdowns are immutable sorted tuples. Values use exact
`NUMERIC(18,6)` semantics, cash may be signed, and investment/liability amounts
must be nonnegative.

A category is aggregated only when every account supplies that category's
breakdown. `None` means unavailable and propagates to the aggregate; it is
never converted to an empty exact breakdown. When cash, portfolio, and
liability breakdowns are all complete:

```text
totalNetWorthByCurrency =
    cashValueByCurrency
  + portfolioValueByCurrency
  - liabilitiesValueByCurrency
```

5J-A consumes no FX evidence. Selection, conversion audit, and physical JSONB
serialization belong to later steps.

## Numeric and failure contract

Every input, contribution, type aggregate, currency aggregate, and final value
must be a finite Python `Decimal` exactly representable by `NUMERIC(18,6)`.
Floats, NaN, infinity, over-scale values, precision overflow, and aggregate
overflow fail. There is no rounding, truncation, quantization policy, clamping,
or partial result.

All failures use:

```text
Account snapshots cannot produce a complete net worth projection.
```

The message exposes no account, snapshot, currency, value, or invariant detail.
The function performs no I/O, generates no IDs, reads no clock, and mutates no
input.
