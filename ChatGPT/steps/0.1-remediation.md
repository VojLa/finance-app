## 0.1-R1 account cutover

The account management page now uses the existing Python `/api/v1/accounts`
contract for active-account list, create, update, and archive. Browser requests
remain same-origin and call thin Next.js routes. Each route verifies the
NextAuth session and uses the shared server-only Python transport to issue a
fresh short-lived internal token for its one FastAPI request.

FastAPI remains the account-domain and authorization authority. Account request
and response DTOs are aliases of the generated OpenAPI schemas. The browser
cannot supply the internal subject, membership, owner role, backend URL, cookie
credential, or internal token.

The Next bridge applies an exact request allowlist before calling Python:
create accepts only `name`, `type`, `currency`, `color`, and `notes`; update
accepts only `name`, `currency`, `color`, and `notes`. Python success responses
are parsed into a new safe object with the exact public account field set.
Unknown fields, unknown enums, invalid currency, or invalid timestamps fail
closed as a Python API contract error.

All nine Python account types are available in the create UI. Account type is
selected only during creation and is immutable afterward. The edit UI exposes
name and currency only. Edit controls are available to owner, admin, and
editor roles; archive controls are available only to owner and admin.
Destructive account deletion was removed from the used route and replaced by
archive; archive preserves the account and its financial data.

The main account page no longer reads legacy cash or calculates FX values.
Cash-by-currency remains assigned to R6 through an approved Python read
contract. Sharing UI is outside R1 and is hidden from the main page. Existing
legacy cash and share route files remain registered as unused compatibility
surfaces and were not modified.

Every production consumer of the account collection—including settings,
import, portfolio manual-add, and transactions—uses the typed account client.
Settings derives its read-only shared-account display from Python
`role`/`relation_type` membership fields. None of these pages interprets a safe
error envelope as an account array or performs a raw account collection fetch.

## 0.1-R2 Raiffeisenbank Python source

Raiffeisenbank now has a source-specific Python parser and normalizer for exact
account-statement and card-statement shapes. File format is detected once from
the complete header; unknown, mixed, malformed, empty, and header-only files
fail closed, while physical blank and column-mismatch data rows remain
persisted evidence.

The normalizer preserves the provider sign in finite exact `Decimal` strings,
supports documented Czech date forms, builds deterministic description and
counterparty values, and uses a provider ID or stable account-scoped SHA-256
fallback. The fallback excludes filename, batch identity, row number, upload
time, and randomness. Ambiguous transfers, zero amounts, and source-type/sign
conflicts go to review. The parser performs no posting or financial
calculation.

Sanitized account and card fixtures pass parse, normalize, deduplicate,
classify, and canonical Transaction posting on PostgreSQL 16. The card fixture
does not infer a credit-card liability. A separate cash-only CZK account
fixture proves exact `9826.55` cash through AccountSnapshot, NetWorthSnapshot,
and the portfolio/dashboard exact reads without price or FX evidence, latest
lookup, synthetic fallback, or post-refresh account discovery.

The browser still uses the legacy import workflow until 0.1-R4. Version 0.1 is
not complete.

## 0.1-R3 investment-source fixture E2E

Trading212 produces the exact deposit, buy, and dividend events and their cash

## 0.1-R4 import frontend cutover

The import page now uses one typed same-origin `POST /api/import` request.
The thin Next.js bridge verifies the NextAuth session once, preserves each
uploaded CSV as exact binary evidence, calculates its SHA-256 checksum, and
runs the existing Python create, upload, parse, normalize, deduplicate,
classify, post, and final-read stages in order. Every FastAPI request receives
a fresh short-lived internal token; the browser receives neither that token nor
the backend URL, cookie credential, raw Python error, or internal identifiers.

Multiple files are processed synchronously and sequentially in browser order.
The public response distinguishes completed, duplicate, and failed files,
includes safe aggregate counters, and retains completed-file evidence when a
later file fails. There is no polling, automatic retry, response cache, account
discovery, or browser-side parser. The page no longer calls the legacy preview
or provider-specific transport routes. Those provider routes remain registered
as thin compatibility wrappers over the same Python workflow.

Python remains the sole parser, normalizer, deduplication, classification,
posting, holdings, and snapshot authority. R4 changes no Python production
code, generated OpenAPI contract, database schema, or source semantics proven
by R2 and R3. Version 0.1 is not complete.

## 0.1-R5-A exact market-evidence foundation

The Python backend now has a provider-independent market-evidence boundary over
the existing `PriceSnapshot` and `ExchangeRate` schema. A read-only
`REPEATABLE READ` planner derives exact price requirements from active nonzero
Holdings and their persisted Listing or single supported AssetAlias identity.
It derives direct snapshot-time FX requirements for current cash, listing,
cost-basis, liability, and account currencies, and separate historical
requirements whose `through` value is the persisted event or transaction
timestamp. Requirements are immutable, deduplicated, and canonically ordered;
the planner performs no provider call, lock, write, clock read, symbol guess,
inverse-rate derivation, or cross-rate derivation.

Injected price and FX provider ports return canonical Decimal observations.
Validation requires exact persisted identities, direct currency direction,
source, physical precision, naive UTC millisecond timestamps, and explicit
freshness. The shared 0.1 policy accepts prices up to 72 hours old and direct
FX up to seven calendar days old, including the exact boundary, while future
or older evidence fails closed. The same policy now constrains subsequent
snapshot evidence selection, including event-date FX. Same-currency conversion
is a structural bypass and creates no `ExchangeRate` row.

After every provider observation has validated outside a database transaction,
one append-only writer owns a bounded `SERIALIZABLE` attempt. It takes
canonically ordered advisory locks, inserts or exactly replays deterministic
UUIDv5 price and FX identities, verifies every inserted physical column, and
rolls back the complete mixed batch on any conflict or failure. It never
updates or repairs evidence. Provider failures write nothing.

Real PostgreSQL 16 acceptance proves persisted User/account/holding/history
planning, fake-provider evidence persistence, exact selected price,
snapshot-FX and historical-FX identities, then the unchanged coordinated
AccountSnapshot and NetWorthSnapshot path. The E2E inserts no `PriceSnapshot`
or `ExchangeRate` directly. R5-A adds no schema, migration, public endpoint,
HTTP provider, scheduler, browser behavior, or generated OpenAPI change.

R5 is still in progress. Production refresh orchestration remains separate
follow-up work in R5-B3.

## 0.1-R5-B1 production CNB FX provider

The production FX registry now contains exactly one provider:
`ExchangeRateSource.cnb`. It serves only direct foreign-currency-to-CZK
requirements and keeps the R5-A price registry empty. For each requirement it
performs one bounded HTTPS request to the official CNB daily XML endpoint with
the exact `through` calendar date in `DD.MM.YYYY` form. It does not use the
system date, try another date, retry, cache, derive an inverse or cross rate, or
fall back to another source.

The server-only transport uses a short-lived `httpx.AsyncClient`, disables
redirect following, sends no authentication or cookies, and bounds timeout and
decoded response size. Configuration requires an absolute credential-free
HTTPS URL, a safe User-Agent, and bounded positive timeout and body limits.
`httpx` is now a production backend dependency.

The standard-library XML parser requires the exact CNB document, table, date,
currency, amount, and published-rate shapes. It rejects duplicate currencies,
locale ambiguity, nonfinite or nonpositive numbers, unsafe XML declarations,
and malformed or deeply nested documents. The canonical direct rate is the
published CZK value divided by its exact amount using `Decimal`; a result that
cannot fit `NUMERIC(18,8)` without rounding is unavailable. The observation
timestamp is midnight on the document publication date. Weekend and holiday
responses may therefore use an older publication date only when the shared
R5-A seven-day freshness policy accepts it.

Mocked-HTTP PostgreSQL 16 acceptance proves that the production registry and
actual R5-A writer persist and exactly replay event-date and snapshot-date CNB
evidence without price rows. The same evidence reaches AccountSnapshot,
NetWorthSnapshot, and unchanged portfolio/dashboard exact reads. Stale or
failed CNB evidence writes no rate and produces no partial snapshot. R5-B1 adds
no endpoint, schema, migration, snapshot algorithm, scheduler, price provider,
or frontend behavior.

## 0.1-R5-B2A production CoinGecko crypto price provider

The production price registry now contains exactly `PriceSource.coingecko`.
It can satisfy a crypto Listing only when the Listing's Asset has one exact
persisted `AssetAlias(provider=coingecko)` identity. The adapter never derives
an identity from the Asset symbol, name, Listing symbol, exchange-specific
provider symbol, a hard-coded BTC mapping, or a `/coins/list` lookup. An
Anycoin-created `BTC` Listing therefore remains unavailable until its Asset
has the explicit CoinGecko alias. Trading212 listed-security prices are not
covered by this provider.

For each exact requirement the adapter performs one bounded HTTPS GET to
CoinGecko `/simple/price` using only `ids`, the lower-case Listing quote
currency, `include_last_updated_at=true`, and `precision=full`. Redirects,
retries, cookies, caches, symbol search, and alternate endpoints are absent.
An optional Demo API key is sent only in `x-cg-demo-api-key` and is represented
as a secret configuration value.

The response crosses a strict standard-library JSON boundary. Duplicate keys,
unexpected coin identity, missing quote or update time, nonfinite/nonpositive
numbers, excessive structure, invalid timestamps, and malformed JSON fail
closed. Price numbers are parsed directly as `Decimal`; values that do not
already fit `NUMERIC(28,10)` are rejected without rounding. The canonical
observation timestamp is the provider's `last_updated_at` Unix time converted
to naive UTC `TIMESTAMP(3)`. It is never replaced or clamped to request,
snapshot, or system time. The shared R5-A policy continues to reject future
evidence and evidence older than 72 hours.

Mocked-HTTP PostgreSQL 16 acceptance proves alias-only planning, exact
`PriceSnapshot` creation and replay, selected price lineage, AccountSnapshot
and NetWorthSnapshot valuation, and portfolio/dashboard exact-read parity.
Missing or ambiguous aliases fail before HTTP. Stale, failed, or zero-price
responses persist neither price evidence nor partial snapshots. R5-B2A adds no
endpoint, schema, migration, alias writer, provider discovery, scheduler, or
frontend behavior, and it is not yet wired into the public refresh or import
workflow.

## 0.1-R5-B2B0 Twelve Data provider identity

The earlier Stooq candidate was rejected because the reviewed public surface

step intentionally treats `AssetAlias.externalId` as one opaque exact string:
it does not split, infer, discover, create, or validate that identity against a
live provider.

The generic planner can project one persisted
`AssetAlias(provider=twelve_data)` into an exact requirement when a Twelve
Data provider is explicitly injected. Production composition still registers
only CoinGecko for prices and CNB for FX, so a Twelve Data alias is unavailable
before any HTTP request. There is no Twelve Data transport, JSON parser, API
key setting, endpoint, retry, cache, or alias-management API in R5-B2B0.
R5 remains in progress; R5-B2B1 owns the official request identity and bounded
HTTP adapter described below.

## 0.1-R5-B2B1 production Twelve Data price provider

The production price registry now contains CoinGecko and Twelve Data, while
the production FX registry remains CNB-only. Listed-security requirements are
eligible only through one exact persisted
`AssetAlias(provider=twelve_data)`. Its `externalId` must be byte-exact
canonical JSON in the form
`{"symbol":"AAPL","mic_code":"XNAS"}`. Neither the Trading212 provider symbol,
Asset symbol, ISIN, Listing MIC, exchange, country, nor another alias can
create, repair, or replace this identity.

The adapter performs one bounded HTTPS `GET /quote` per requirement with the
exact alias `symbol` and `mic_code`, `interval=1min`, `timezone=UTC`,
`format=JSON`, `prepost=false`, and `dp=10`. The server-side API key is sent
only as `Authorization: apikey <secret>` and is absent from the URL, result,
errors, logs, and browser configuration. A missing key is invalid in
production; development and tests fail before HTTP when a Twelve Data
requirement has no configured key.

Strict standard-library JSON parsing rejects duplicate keys, error responses,
invalid structure, identity or currency mismatch, non-string or physically
unrepresentable prices, and incompatible timestamps. The positive exact
`close` string becomes the price. For the one-minute UTC request, `timestamp`
and `last_quote_at` must be equal, minute-aligned, and exactly match the UTC
`datetime`; `last_quote_at` becomes the naive UTC observation timestamp.
Neither time nor price is inferred, clamped, rounded, or converted through
`float`.

Mocked-HTTP PostgreSQL 16 acceptance proves exact AAPL/XNAS planning, request
identity, deterministic PriceSnapshot creation/replay, selected price lineage,
AccountSnapshot and NetWorthSnapshot valuation, and portfolio/dashboard exact

migration, endpoint, import integration, retry, cache, scheduler, or browser
behavior.

## 0.1-R5-B3A market-backed snapshot refresh orchestration

The internal `MarketBackedSnapshotRefreshService` accepts one immutable,
fully validated command and always completes production market-evidence
refresh before invoking the existing `UserSnapshotRefreshExecutor`. The market
projection preserves the exact user, snapshot timestamp, and caller-supplied
creation timestamp. Only after that result has been validated does the
snapshot projection forward every original snapshot command field unchanged.
The service uses no clock, timestamp repair, retry, cache, scheduler, worker,
queue, or background task.

Every handoff requires an idle shared session. The market planner's read
transaction closes before provider HTTP, the append-only market writer commits
before snapshot execution begins, and provider HTTP remains outside every
database transaction. If either dependency leaves a transaction active, the
orchestrator rolls it back, raises an internal runtime error, and does not
start the next stage.

Market and snapshot persistence are intentionally two committed phases rather
than one atomic transaction. Market failure prevents the snapshot executor
call and creates neither a partial market batch nor a snapshot graph. If
snapshot execution fails after a successful market writer, valid
`PriceSnapshot` and `ExchangeRate` evidence remains append-only; the
orchestrator performs no compensation, deletion, or rollback of that committed
phase. An empty market plan is valid and continues to snapshot execution.

The immutable combined result is not a blind dependency pass-through. It
cross-checks user, timestamp, and output currency; canonical unique market
identities and create/replay counts; snapshot dispositions and aggregate
counts; and exact ordered AccountSnapshot lineage. Known market/snapshot state
and conflict errors map to separate generic internal contracts without
provider, payload, SQL, evidence, request, or trace details.

Mocked-HTTP PostgreSQL 16 acceptance exercises the production CoinGecko,
Twelve Data, and ČNB registries together for one CZK user with exact broker and
exchange aliases. It proves selected price, snapshot-FX, historical-FX,
AccountSnapshot, NetWorthSnapshot, portfolio/dashboard parity, replay, HTTP
transaction separation, provider failures, missing/ambiguous aliases, and
snapshot failure after committed market evidence. R5-B3A adds no endpoint,
import hook, manual endpoint change, frontend, OpenAPI change, schema, or
migration. Overall R5 remains in progress.

## 0.1-R5-B3B manual market-backed refresh integration

The unchanged authenticated
`POST /api/v1/snapshot-refresh/recalculate` route now injects the production
`MarketBackedSnapshotRefreshService` from the request-scoped application
settings and the same request-scoped database session used by authentication
and the manual service. Authentication closes its read transaction first.
The manual boundary then reads its clock exactly once, derives the canonical
UTC minute bucket, and projects every server-owned field into one immutable
market-backed command.

Execution remains strictly market evidence first and snapshot execution
second. There is no direct manual fallback to `UserSnapshotRefreshExecutor`.
A market failure prevents the snapshot call and creates no snapshot graph. A
snapshot failure after the committed market writer leaves valid append-only
price and FX evidence in place. The two phases are not one atomic transaction,
provider HTTP stays outside database transactions, and every dependency
handoff requires the shared session to be idle.

The manual boundary requires the combined runtime result, extracts its
snapshot result, and repeats the existing principal, bucket, granularity,
source, version, disposition, count, lineage, NetWorth identity, and output
currency checks. The successful response and generic 409 error contracts are
unchanged. Market IDs, provider identities, requirements, counts, and
diagnostics never cross the public boundary. A completely empty market plan is
valid and still executes snapshots.

Production mixed-currency refresh is supported for a CZK-output user through
exact CoinGecko, Twelve Data, and ČNB evidence. Same-currency and otherwise
empty-FX non-CZK plans remain valid. Unsupported direct non-CZK FX such as
USD-to-EUR fails with the existing generic unavailable response; the endpoint
does not add ECB, inverse, cross-rate, manual-rate, retry, cache, scheduler, or
background fallback.

Mocked-HTTP PostgreSQL 16 endpoint acceptance proves exact provider requests,
HTTP transaction separation, market-before-snapshot persistence, selected
price and historical/snapshot FX lineage, portfolio/dashboard parity, replay,
provider failure rollback, pre-HTTP alias failure, preserved market evidence

change OpenAPI, generated frontend types, schema, migrations, import

## 0.1-R5-B4 exact provider alias onboarding

R5-B4 adds a supported server-operator workflow for creating the exact
CoinGecko and Twelve Data `AssetAlias` rows required by the existing market
planner. The reusable Python application service and CLI are intentionally not
browser-accessible and add no FastAPI, Next.js, OpenAPI, schema, or migration
surface. The operator first uses the read-only unresolved-asset inventory,
obtains the provider identity from an authoritative external process, and then
supplies that exact identity together with the Asset ID and expected symbol,
type, currency, and optional ISIN guards.

CoinGecko accepts only one canonical ASCII provider ID for a crypto Asset.
Twelve Data accepts only canonical JSON
`{"symbol":"AAPL","mic_code":"XNAS"}` for stock, ETF, bond, commodity, or
other Assets. Neither path derives identity from ticker, name, ISIN, broker or
exchange symbol, Listing MIC, exchange, a first alias, or a hard-coded map;
the inventory performs no provider HTTP or identity recommendation.

The immutable create-only writer owns one `SERIALIZABLE` transaction and
canonical advisory locks for both `(asset_id, provider)` and
`(provider, external_id)`. New IDs use UUIDv5 namespace
`b1d66d76-35f0-4db0-b1d9-0f5452d4a27c` with payload
`asset_id + NUL + provider.value`. An exact existing alias replays without
changing its historical ID or `createdAt`; different, repointed, duplicate,
corrupt, or deterministic-ID-colliding state fails closed. SQL retry is
limited to three complete attempts for `40001`, `40P01`, and `23505`, followed
by exact physical reload validation.

Clean PostgreSQL 16 acceptance uses the actual CLI subprocess, not direct SQL
or a test-only alias insert. Trading212 and Anycoin imports first fail
unavailable before provider HTTP, preserve canonical posting and Holdings,
then recover through explicit Twelve Data or CoinGecko onboarding. The
existing public import and manual refresh paths consume the new persisted
alias without orchestration changes and converge on deterministic market and
snapshot replay.

The prior final audit remains an immutable record of the pre-B4 missing state.
R5-B4 is implemented. The later remediation re-audit independently closed
`R5-ALIAS-01`; it does not rewrite the historically correct pre-B4 verdict.

## 0.1-R6-A exact cash/deposit portfolio contract

R6-A exposes the already persisted AccountSnapshot `cashValueByCurrency` and
`netDepositsByCurrency` evidence through the exact single-account and
multi-account portfolio responses. The physical JSONB columns predate R6-A;
this step adds no financial calculation, schema, or migration. The reader
decodes only canonical fixed-scale MONEY strings, rejects missing or malformed
evidence without a scalar fallback, and projects immutable currency/amount
tuples in ascending currency order.

Multi-account summaries add amounts with the same original currency using exact
Decimal arithmetic. They perform no FX conversion, rate lookup, synthetic
output-currency insertion, or reconstruction from Transactions or Holdings.
The net-deposits scalar already existed before R6-A and retains its meaning.
The portfolio contract now serializes both breakdowns as deterministic arrays
of `{currency, amount}` objects. Dashboard responses remain unchanged, and
R6-B owns the visual portfolio presentation.
