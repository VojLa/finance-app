## 0.1-R1 account cutover

The account management page now uses the existing Python `/api/v1/accounts`
contract for active-account list, create, update, and archive. Browser requests
remain same-origin and call thin Next.js routes. Each route verifies the
NextAuth session and uses the shared server-only Python transport to issue a
fresh short-lived internal token for its one FastAPI request.

FastAPI remains the account-domain and authorization authority. Account request
and response DTOs are aliases of the generated OpenAPI schemas. The browser
cannot supply the internal subject, membership, owner role, backend URL, cookie
credential, or internal token.

The Next bridge applies an exact request allowlist before calling Python:
create accepts only `name`, `type`, `currency`, `color`, and `notes`; update
accepts only `name`, `currency`, `color`, and `notes`. Python success responses
are parsed into a new safe object with the exact public account field set.
Unknown fields, unknown enums, invalid currency, or invalid timestamps fail
closed as a Python API contract error.

All nine Python account types are available in the create UI. Account type is
selected only during creation and is immutable afterward. The edit UI exposes
name and currency only. Edit controls are available to owner, admin, and
editor roles; archive controls are available only to owner and admin.
Destructive account deletion was removed from the used route and replaced by
archive; archive preserves the account and its financial data.

The main account page no longer reads legacy cash or calculates FX values.
Cash-by-currency remains assigned to R6 through an approved Python read
contract. Sharing UI is outside R1 and is hidden from the main page. Existing
legacy cash and share route files remain registered as unused compatibility
surfaces and were not modified.

Every production consumer of the account collection—including settings,
import, portfolio manual-add, and transactions—uses the typed account client.
Settings derives its read-only shared-account display from Python
`role`/`relation_type` membership fields. None of these pages interprets a safe
error envelope as an account array or performs a raw account collection fetch.

## 0.1-R2 Raiffeisenbank Python source

Raiffeisenbank now has a source-specific Python parser and normalizer for exact
account-statement and card-statement shapes. File format is detected once from
the complete header; unknown, mixed, malformed, empty, and header-only files
fail closed, while physical blank and column-mismatch data rows remain
persisted evidence.

The normalizer preserves the provider sign in finite exact `Decimal` strings,
supports documented Czech date forms, builds deterministic description and
counterparty values, and uses a provider ID or stable account-scoped SHA-256
fallback. The fallback excludes filename, batch identity, row number, upload
time, and randomness. Ambiguous transfers, zero amounts, and source-type/sign
conflicts go to review. The parser performs no posting or financial
calculation.

Sanitized account and card fixtures pass parse, normalize, deduplicate,
classify, and canonical Transaction posting on PostgreSQL 16. The card fixture
does not infer a credit-card liability. A separate cash-only CZK account
fixture proves exact `9826.55` cash through AccountSnapshot, NetWorthSnapshot,
and the portfolio/dashboard exact reads without price or FX evidence, latest
lookup, synthetic fallback, or post-refresh account discovery.

The browser still uses the legacy import workflow until 0.1-R4. Version 0.1 is
not complete.

## 0.1-R3 investment-source fixture E2E

Committed, fully synthetic Trading212 and Anycoin CSV fixtures now prove the
public staged Python workflow from binary upload through parse, normalize,
deduplicate, classify, canonical investment posting, holdings rebuild,
coordinated snapshot refresh, and the exact portfolio and dashboard reads.
Trading212 continues to use the generic strict CSV parser and schema-version-2
normalizer. Anycoin continues to use the generic parser and deterministic
batch grouping with one imported anchor row and skipped group-member evidence.

Trading212 produces the exact deposit, buy, and dividend events and their cash
and asset movements. Anycoin produces one grouped buy with exact incoming
asset and outgoing cash movements. Same-content uploads, BOM and reordered
variants, posting replay, and cross-account isolation preserve canonical
identity without replacement events or movement sets. Physical issue rows
remain persisted failed or review evidence and never produce canonical rows.

The snapshot E2E uses EUR throughout and inserts one explicit deterministic
test `PriceSnapshot` for each exact listing. This is test evidence only: it is
not a price provider, provider refresh, live-price fallback, or completion of
R5. Without current price evidence the post-processing refresh is unavailable
and creates no partial account or net-worth snapshot. After the exact test
price is present, the refresh manifest is passed unchanged to both exact read
endpoints and their totals, cash, investments, liabilities, positions, and
account sets agree. No exchange-rate evidence or FX fallback is used.

## 0.1-R4 import frontend cutover

The import page now uses one typed same-origin `POST /api/import` request.
The thin Next.js bridge verifies the NextAuth session once, preserves each
uploaded CSV as exact binary evidence, calculates its SHA-256 checksum, and
runs the existing Python create, upload, parse, normalize, deduplicate,
classify, post, and final-read stages in order. Every FastAPI request receives
a fresh short-lived internal token; the browser receives neither that token nor
the backend URL, cookie credential, raw Python error, or internal identifiers.

Multiple files are processed synchronously and sequentially in browser order.
The public response distinguishes completed, duplicate, and failed files,
includes safe aggregate counters, and retains completed-file evidence when a
later file fails. There is no polling, automatic retry, response cache, account
discovery, or browser-side parser. The page no longer calls the legacy preview
or provider-specific transport routes. Those provider routes remain registered
as thin compatibility wrappers over the same Python workflow.

Python remains the sole parser, normalizer, deduplication, classification,
posting, holdings, and snapshot authority. R4 changes no Python production
code, generated OpenAPI contract, database schema, or source semantics proven
by R2 and R3. Version 0.1 is not complete.

## 0.1-R5-A exact market-evidence foundation

The Python backend now has a provider-independent market-evidence boundary over
the existing `PriceSnapshot` and `ExchangeRate` schema. A read-only
`REPEATABLE READ` planner derives exact price requirements from active nonzero
Holdings and their persisted Listing or single supported AssetAlias identity.
It derives direct snapshot-time FX requirements for current cash, listing,
cost-basis, liability, and account currencies, and separate historical
requirements whose `through` value is the persisted event or transaction
timestamp. Requirements are immutable, deduplicated, and canonically ordered;
the planner performs no provider call, lock, write, clock read, symbol guess,
inverse-rate derivation, or cross-rate derivation.

Injected price and FX provider ports return canonical Decimal observations.
Validation requires exact persisted identities, direct currency direction,
source, physical precision, naive UTC millisecond timestamps, and explicit
freshness. The shared 0.1 policy accepts prices up to 72 hours old and direct
FX up to seven calendar days old, including the exact boundary, while future
or older evidence fails closed. The same policy now constrains subsequent
snapshot evidence selection, including event-date FX. Same-currency conversion
is a structural bypass and creates no `ExchangeRate` row.

After every provider observation has validated outside a database transaction,
one append-only writer owns a bounded `SERIALIZABLE` attempt. It takes
canonically ordered advisory locks, inserts or exactly replays deterministic
UUIDv5 price and FX identities, verifies every inserted physical column, and
rolls back the complete mixed batch on any conflict or failure. It never
updates or repairs evidence. Provider failures write nothing.

Real PostgreSQL 16 acceptance proves persisted User/account/holding/history
planning, fake-provider evidence persistence, exact selected price,
snapshot-FX and historical-FX identities, then the unchanged coordinated
AccountSnapshot and NetWorthSnapshot path. The E2E inserts no `PriceSnapshot`
or `ExchangeRate` directly. R5-A adds no schema, migration, public endpoint,
HTTP provider, scheduler, browser behavior, or generated OpenAPI change.

R5 is still in progress. Concrete production providers and production
import/manual orchestration remain separate follow-up work in R5-B.
