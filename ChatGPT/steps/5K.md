# Step 5K — Coordinated user snapshot refresh

Step 5K coordinates the existing account-snapshot and net-worth domains without
moving their calculation or persistence rules into an orchestration layer.

The roadmap is:

- **5K-A** — pure user snapshot refresh plan (implemented);
- **5K-B** — persisted refresh-target and existing-snapshot coverage selection
  (implemented);
- **5K-C1** — pure output-currency valuation contract (implemented after
  merge);
- **5K-C2** — persisted output-currency and FX evidence selection (not
  implemented);
- **5K-C3** — output-currency physical persistence projection (not
  implemented);
- **5K-C4** — writer identity, locking, and replay extension (not
  implemented);
- **5K-C5** — existing manual-orchestration compatibility (not implemented);
- **5K-D** — coordinated refresh executor and resumable failure contract
  (not implemented);
- **5K-E** — authorized endpoint and import/post-processing integration
  (not implemented).

5J-A through 5J-E are complete. No 5K execution, scheduling, import hook, or
background work exists yet.

## Pure 5K-A boundary

`snapshot_refresh` is a cross-domain orchestration-contract module.
`build_user_snapshot_refresh_plan()` accepts complete immutable user, account,
membership, and server-owned snapshot metadata. It returns immutable
declarative account targets plus one final net-worth target. It performs no
database access, ORM construction, transaction work, writer invocation, clock
read, UUID generation, FX lookup, or financial calculation.

All current active accounts must be represented. Broker, exchange,
crypto-wallet, credit-card, loan, and mortgage accounts are supported. One
active bank, cash, or savings account invalidates the complete plan rather than
being omitted. A consistently archived account is excluded; contradictory
archive state fails closed. An empty active account set is valid and still
produces one zero-source net-worth dependency target.

Owner, admin, and editor memberships produce `refresh` targets. A viewer
membership produces `reuse_only`: later evidence selection must prove an exact
existing AccountSnapshot, and the viewer may not trigger its creation or
replacement. Every active account has exactly one accepted membership, and
duplicate account or membership identities fail.

## Currency and dependency contract

The user's canonical base currency is the output currency for every planned
AccountSnapshot and the final NetWorthSnapshot. The account's main currency is
preserved separately. A mismatch sets `requires_fx_conversion`; 5K-A performs
no rate selection or conversion and does not reject an otherwise supported
mixed-currency account.

The current AccountSnapshot writer still emits the account's main currency and
cannot execute a target whose output currency differs. 5K-C must define exact
output-currency evidence and persistence support before coordinated
mixed-currency refresh can run.

The final net-worth target requires every active account ID, including
`reuse_only` targets, in deterministic account-ID order. It may run only after
each has one exact AccountSnapshot with the same timestamp, granularity, output
currency, and calculation version. This dependency is declarative in 5K-A;
neither AccountSnapshot nor NetWorthSnapshot is written.

## Metadata and failure contract

Identifiers are nonblank and untrimmed. Currencies are exactly three uppercase
ASCII letters. All datetimes are naive, exact `TIMESTAMP(3)` values, and the
snapshot timestamp must align to minute, hour, day, Monday-based week, or
first-day month granularity. Calculation versions use positive PostgreSQL
INTEGER values. `is_recalculated` is true exactly for
`manual_recalculation`.

Equivalent account input permutations produce structurally equal plans.
Targets are ordered by account and membership identity, all structures are
frozen, and inputs are not mutated. Invalid or incomplete evidence raises:

```text
Snapshot refresh evidence cannot produce a complete plan.
```

The stable message exposes no user, account, membership, currency, timestamp,
or financial detail.

## Persisted 5K-B coverage

`SnapshotRefreshEvidenceService` requires an active caller-owned
`REPEATABLE READ` or `SERIALIZABLE` transaction. It verifies isolation before
reading, then explicitly loads the persisted User and every joined
Account/AccountMember row. The User is the sole source of output/base currency;
the membership is the sole source of role, relation, and acceptance evidence.
No caller may supply either persisted boundary.

Every current joined row is mapped to one 5K-A
`SnapshotRefreshAccountEvidence`. The service invokes
`build_user_snapshot_refresh_plan()` exactly once, preserving 5K-A as the only
owner of role classification, supported account types, archive behavior,
currency-difference classification, ordering, and plan counts.

The immutable plan is partitioned without reclassification. Owner, admin, and
editor targets remain mandatory future AccountSnapshot writer calls even when
a snapshot already exists. Viewer targets remain `reuse_only` and require one
exact persisted AccountSnapshot at the plan timestamp, granularity, User base
currency, and calculation version. Selection is one batched exact-key query
over viewer account IDs only; there is no latest-as-of, currency fallback, or
source priority.

The reused snapshot source and persistence timestamps are independently valid
persisted metadata and need not equal the new orchestration metadata. Thus a
scheduled snapshot may satisfy a manual dependency and a manual snapshot may
satisfy a scheduled dependency. 5K-B validates only identity and persistence
metadata, not financial fields. Complete financial AccountSnapshot validation
remains 5J-B's responsibility before the final NetWorthSnapshot is built.

5K-B owns no transaction, lock, retry, autoflush, or write and returns no ORM
object. `REPEATABLE READ`/`SERIALIZABLE` makes User currency, membership/account
coverage, and viewer snapshot selection one coherent persisted view.

## Pure 5K-C1 output-currency valuation

`build_account_snapshot_projection()` now preserves `account_currency` as
persisted Account metadata while independently accepting `output_currency` as
the denomination of every aggregate value. A difference between them is valid
pure evidence and does not itself require an FX row. Actual non-output
currencies in selected prices, Holding cost basis, cash balances, and the
single liability observation determine the required conversion pairs.

Only an exact caller-supplied direct `native -> output` rate is consumed.
Reverse rates are not inverted, intermediary pairs are not chained, and
Account currency is not used as a fallback conversion route. Every supplied
rate must be consumed. Consequently, an empty mixed-currency account needs no
synthetic rate, while any missing, reversed, chained, duplicate, future, or
unused evidence fails the complete projection.

Investment item values and cost bases are converted to output currency without
changing quantity, allocation, or native price/cost evidence. Cash and positive
liability scalars are converted the same way. Liability evidence remains in
the Account currency; its native breakdown preserves that currency even when
the scalar liability and negative total are expressed in output currency.
Every native breakdown remains grouped and sorted by its original evidence
currency, while all aggregate formulas use the requested output currency.

5K-C1 is pure: it selects no persisted rates, reads no database state, writes no
row, and changes no writer or public orchestration contract. The current
evidence service still derives output currency from `Account.currency`.
Persisted selection belongs to 5K-C2, physical mapping to 5K-C3, writer
identity/replay support to 5K-C4, and existing manual-service compatibility to
5K-C5. Coordinated execution remains 5K-D and public/import integration remains
5K-E.
