# Step 5K — Coordinated user snapshot refresh

Step 5K coordinates the existing account-snapshot and net-worth domains without
moving their calculation or persistence rules into an orchestration layer.

The roadmap is:

- **5K-A** — pure user snapshot refresh plan (implemented);
- **5K-B** — persisted refresh-target and existing-snapshot coverage selection
  (implemented);
- **5K-C1** — pure output-currency valuation contract (implemented);
- **5K-C2** — persisted output-currency and FX evidence selection
  (implemented);
- **5K-C3** — output-currency physical persistence projection (implemented);
- **5K-C4** — writer identity, locking, and replay extension (implemented);
- **5K-C5** — existing manual-orchestration compatibility (implemented);
- **5K-D1** — exact NetWorth AccountSnapshot dependency guard (implemented);
- **5K-D2** — coordinated refresh executor and resumable failure contract
  (implemented);
- **5K-E1** — authorized coordinated manual refresh endpoint
  (implemented after merge);
- **5K-E2** — import/post-processing integration (not implemented).

5J-A through 5J-E and 5K-A through 5K-D2 are complete. 5K-E1 adds only the
authenticated synchronous manual endpoint. No scheduling, import hook, queue,
worker, or background work exists.

## Pure 5K-A boundary

`snapshot_refresh` is a cross-domain orchestration-contract module.
`build_user_snapshot_refresh_plan()` accepts complete immutable user, account,
membership, and server-owned snapshot metadata. It returns immutable
declarative account targets plus one final net-worth target. It performs no
database access, ORM construction, transaction work, writer invocation, clock
read, UUID generation, FX lookup, or financial calculation.

All current active accounts must be represented. Broker, exchange,
crypto-wallet, credit-card, loan, and mortgage accounts are supported. One
active bank, cash, or savings account invalidates the complete plan rather than
being omitted. A consistently archived account is excluded; contradictory
archive state fails closed. An empty active account set is valid and still
produces one zero-source net-worth dependency target.

Owner, admin, and editor memberships produce `refresh` targets. A viewer
membership produces `reuse_only`: later evidence selection must prove an exact
existing AccountSnapshot, and the viewer may not trigger its creation or
replacement. Every active account has exactly one accepted membership, and
duplicate account or membership identities fail.

## Currency and dependency contract

The user's canonical base currency is the output currency for every planned
AccountSnapshot and the final NetWorthSnapshot. The account's main currency is
preserved separately. A mismatch sets `requires_fx_conversion`; 5K-A performs
no rate selection or conversion and does not reject an otherwise supported
mixed-currency account.

The AccountSnapshot writer can persist a caller-selected canonical output
currency. The existing manual operation accepts that currency only as an
optional explicit request value; omission still resolves to the Account's main
currency. Coordinated refresh must compose the planned User base currency in
5K-D.

The final net-worth target requires every active account ID, including
`reuse_only` targets, in deterministic account-ID order. It may run only after
each has one exact AccountSnapshot with the same timestamp, granularity, output
currency, and calculation version. This dependency is declarative in 5K-A;
neither AccountSnapshot nor NetWorthSnapshot is written.

## Metadata and failure contract

Identifiers are nonblank and untrimmed. Currencies are exactly three uppercase
ASCII letters. All datetimes are naive, exact `TIMESTAMP(3)` values, and the
snapshot timestamp must align to minute, hour, day, Monday-based week, or
first-day month granularity. Calculation versions use positive PostgreSQL
INTEGER values. `is_recalculated` is true exactly for
`manual_recalculation`.

Equivalent account input permutations produce structurally equal plans.
Targets are ordered by account and membership identity, all structures are
frozen, and inputs are not mutated. Invalid or incomplete evidence raises:

```text
Snapshot refresh evidence cannot produce a complete plan.
```

The stable message exposes no user, account, membership, currency, timestamp,
or financial detail.

## Persisted 5K-B coverage

`SnapshotRefreshEvidenceService` requires an active caller-owned
`REPEATABLE READ` or `SERIALIZABLE` transaction. It verifies isolation before
reading, then explicitly loads the persisted User and every joined
Account/AccountMember row. The User is the sole source of output/base currency;
the membership is the sole source of role, relation, and acceptance evidence.
No caller may supply either persisted boundary.

Every current joined row is mapped to one 5K-A
`SnapshotRefreshAccountEvidence`. The service invokes
`build_user_snapshot_refresh_plan()` exactly once, preserving 5K-A as the only
owner of role classification, supported account types, archive behavior,
currency-difference classification, ordering, and plan counts.

The immutable plan is partitioned without reclassification. Owner, admin, and
editor targets remain mandatory future AccountSnapshot writer calls even when
a snapshot already exists. Viewer targets remain `reuse_only` and require one
exact persisted AccountSnapshot at the plan timestamp, granularity, User base
currency, and calculation version. Selection is one batched exact-key query
over viewer account IDs only; there is no latest-as-of, currency fallback, or
source priority.

The reused snapshot source and persistence timestamps are independently valid
persisted metadata and need not equal the new orchestration metadata. Thus a
scheduled snapshot may satisfy a manual dependency and a manual snapshot may
satisfy a scheduled dependency. 5K-B validates only identity and persistence
metadata, not financial fields. Complete financial AccountSnapshot validation
remains 5J-B's responsibility before the final NetWorthSnapshot is built.

5K-B owns no transaction, lock, retry, autoflush, or write and returns no ORM
object. `REPEATABLE READ`/`SERIALIZABLE` makes User currency, membership/account
coverage, and viewer snapshot selection one coherent persisted view.

## Pure 5K-C1 output-currency valuation

`build_account_snapshot_projection()` now preserves `account_currency` as
persisted Account metadata while independently accepting `output_currency` as
the denomination of every aggregate value. A difference between them is valid
pure evidence and does not itself require an FX row. Actual non-output
currencies in selected prices, Holding cost basis, cash balances, and the
single liability observation determine the required conversion pairs.

Only an exact caller-supplied direct `native -> output` rate is consumed.
Reverse rates are not inverted, intermediary pairs are not chained, and
Account currency is not used as a fallback conversion route. Every supplied
rate must be consumed. Consequently, an empty mixed-currency account needs no
synthetic rate, while any missing, reversed, chained, duplicate, future, or
unused evidence fails the complete projection.

Investment item values and cost bases are converted to output currency without
changing quantity, allocation, or native price/cost evidence. Cash and positive
liability scalars are converted the same way. Liability evidence remains in
the Account currency; its native breakdown preserves that currency even when
the scalar liability and negative total are expressed in output currency.
Every native breakdown remains grouped and sorted by its original evidence
currency, while all aggregate formulas use the requested output currency.

5K-C1 is pure: it selects no persisted rates, reads no database state, writes no
row, and changes no writer or public orchestration contract.

## Persisted 5K-C2 output-currency evidence

`BuildAccountSnapshotEvidenceCommand.output_currency` is optional. `None`
preserves the existing writer and manual-service behavior by resolving output
currency from the exact persisted `Account.currency`. An explicit canonical
currency becomes the requested output currency, while the persisted Account
remains the sole source of account currency. Command metadata is validated
before the Account read; the service performs no user, membership, or
authorization lookup.

Required persisted pairs come only from actual selected price, Holding cost,
cash, liability, and historical metric currencies after removing output
currency. Account currency is never added merely because it differs. The
repository selects only direct `native -> output` rows through the snapshot
timestamp. Snapshot valuation uses the latest unambiguous eligible row through
that timestamp; each historical net-deposit, realized-P/L, fee, or tax item
uses the latest row through its own event timestamp. Reverse, chained, future,
missing, malformed, duplicate-ID, or latest-timestamp-ambiguous evidence fails
closed without source priority.

Credit-card, loan, and mortgage evidence remains one canonical latest-as-of
positive observation in Account currency. A distinct output currency requires
one direct Account-currency rate through the snapshot timestamp. Its selected
ID appears only in snapshot-rate audit evidence; historical IDs remain empty.
Native liability breakdown and liability observation identity remain intact.

The result validates that valuation currency equals the resolved output
currency and that selected snapshot-rate IDs exactly equal rates consumed by
5K-C1. Historical IDs come only from exact financial-metric consumption. The
service remains caller-transaction-owned and read-only: it creates no snapshot,
returns no ORM row, and adds no lock, flush, commit, rollback, or retry.

## Pure 5K-C3 physical persistence projection

`build_account_snapshot_persistence_projection()` maps the already validated
5K-C2 valuation currency directly to physical `AccountSnapshot.currency`.
Every scalar financial field is already denominated in that output currency.
The existing deterministic snapshot identity includes account, timestamp,
output currency, and granularity; item identities derive from that snapshot ID
and listing ID. Different output currencies therefore produce distinct
snapshot and item IDs without changing either UUID namespace.

Mixed-currency investment rows retain native `priceCurrency`,
`valueCurrency`, `nativeValue`, `nativeCostCurrency`, and
`nativeCostBasis`. Converted `value`, `costBasis`, and `costCurrency` use the
snapshot output currency. Native investment and financial-metric breakdowns
remain canonical fixed-scale JSON, and consumed snapshot rates retain the
version-1 `exchangeRates` audit shape.

Liability persistence requires one complete liability observation audit, no
items or prices, no historical FX, structural-zero financial metrics, and one
native positive liability breakdown. Same-currency evidence consumes no FX and
requires native amount equality. Mixed-currency evidence consumes exactly one
direct native-to-output rate and proves the converted positive liability plus
its negative total. An explicit zero native liability still requires that
direct rate when the currencies differ. The physical AccountSnapshot has no
native-liability-breakdown column, so the projection validates but does not
materialize that breakdown; the liability identity remains in the immutable
nonphysical audit.

5K-C3 performs no database access, ORM construction, transaction work, replay,
or locking and adds no migration. Writer identity/locking/replay support is
owned by 5K-C4, and existing manual-service compatibility by 5K-C5.

## Atomic 5K-C4 output-currency writer

`WriteAccountSnapshotCommand.output_currency` is optional. Command validation
accepts only `None` or an exact canonical currency before opening the
transaction. After locking and validating the Account, `None` resolves to the
persisted Account currency; an explicit value remains the output currency.
Account and output currencies stay separate.

The writer owns one outer transaction and uses the resolved output currency in
the complete physical identity `(account, timestamp, currency, granularity)`.
The same value scopes the existing SHA-256 transaction advisory lock, the
5K-C2 evidence command, the 5K-C3 projection identity check, and the
`FOR UPDATE` replay lookup. The projection must also match every command-owned
source, calculation-version, timestamp, and recalculation field before any
replay decision or insertion. Distinct output currencies can coexist and
replay independently; deterministic snapshot and item IDs already include
that distinction.

Investment accounts preserve the existing lock order: Account `FOR SHARE`,
snapshot identity lock, canonical ledger/Holding locks, then compatible
PriceSnapshot/ExchangeRate `SHARE` locks before one evidence build. Liability
accounts instead lock `LiabilityBalance` in `SHARE` mode before selection.
Mixed-currency liabilities also take the market-evidence lock before selecting
their direct FX rate. This blocks concurrent liability or FX mutations until
the coherent snapshot commits; a later retry with changed evidence conflicts
with the immutable existing row rather than repairing it.

Exact replay compares the complete snapshot and sorted item set and performs no
flush. Creation inserts, flushes, reloads, and verifies the complete graph.
Failures roll back the sole outer transaction. Bank, cash, and savings remain
unpersistable because explicit output currency does not change their
unsupported financial metrics. Coordinated execution remains 5K-D and
public/import integration remains 5K-E.

## Authorized 5K-C5 manual output-currency compatibility

The existing
`POST /api/v1/accounts/{account_id}/snapshots/recalculate` operation accepts an
optional JSON body containing only `outputCurrency`. A missing body, `{}`, JSON
`null`, or `{"outputCurrency": null}` preserves the pre-5K-C5
Account-currency path. An explicit value must be exactly three uppercase ASCII
letters and is forwarded unchanged to the 5K-C4 writer. Invalid or extra
public fields fail with transport validation before the application service.
The response shape is unchanged; its existing `currency` field reports the
actual persisted output currency.

The service revalidates direct internal commands before authorization without
trimming or normalizing currency. Persisted owner, admin, and editor remain the
only write roles; viewer, foreign, missing, and archived accounts retain the
same concealed boundary. The authorization read transaction is completed
before exactly one writer call on an idle session, and one captured
server-owned minute bucket supplies every timestamp.

No User lookup or `User.baseCurrency` fallback occurs. Omission resolves inside
the writer to persisted `Account.currency`; explicit Account currency replays
that same physical identity, while another output currency creates or replays
its separate identity. Missing or ambiguous FX remains a generic unavailable
conflict, and physical differences remain a generic snapshot conflict. The
endpoint exposes no rate, selected-evidence, or internal audit identity.

The complete 5K-C1 through 5K-C5 output-currency chain is implemented. The
coordinated User-base-currency executor remains 5K-D2, and its authorized
endpoint plus import/post-processing integration remain 5K-E. No scheduler,
worker, queue, or automatic refresh exists.

## Exact 5K-D1 NetWorth dependency guard

The internal NetWorth evidence and writer commands accept an optional exact
tuple of existing `SelectedAccountSnapshotIdentity` values. `None` preserves
the manual behavior that discovers every current active supported account and
selects its exact same-bucket snapshot. An explicit tuple is a fail-closed
dependency declaration; an explicit empty tuple means exactly zero active
accounts and is distinct from `None`.

Explicit identities must be immutable, unique by both account and snapshot ID,
nonblank, untrimmed, and already ordered by `(account_id, snapshot_id)`. The
evidence service still validates the persisted User and base currency and
loads every current Account/AccountMember access before comparing the exact
required account tuple. It then selects and fully validates the exact source
AccountSnapshots and requires their ordered account/snapshot identity tuple to
equal the guard. Caller identities never narrow or skip persisted discovery.

The NetWorth writer validates the guard before opening a transaction and passes
the unchanged canonical tuple into every bounded SERIALIZABLE attempt. Each
attempt rebuilds current persisted evidence, and the resulting physical
projection audit must contain the same identities before replay lookup,
deterministic-ID lookup, insertion, or flush. This prevents account addition,
removal, same-count substitution, or source-snapshot replacement from creating
or replaying a NetWorthSnapshot against a stale dependency set.

Real internal writer results return the selected immutable identity tuple for
5K-D2 comparison. The manual net-worth operation explicitly uses
`None`; its request and response schemas expose no dependency identities.
5K-D1 creates no job state, schema, endpoint, AccountSnapshot write, or import
hook. 5K-E remains the public/import integration boundary.

## Coordinated 5K-D2 executor

`UserSnapshotRefreshExecutor` validates one immutable server-owned command,
then owns a short initial coverage transaction whose first statement sets
`REPEATABLE READ`. Inside that coherent read it invokes 5K-B exactly once,
revalidates the complete immutable plan, refresh/reuse partition, counts,
metadata, and viewer snapshot identities, then commits the coverage transaction
before constructing any writer. Persisted User state remains the sole source
of the output currency.

Every owner/admin/editor `refresh` target is passed once, in deterministic plan
order, to the existing `AccountSnapshotWriter` with the plan output currency.
The executor never skips these targets because a row may already exist; exact
writer replay is the persisted resume proof. Viewer `reuse_only` targets never
invoke that writer and contribute only their exact 5K-B-selected snapshot
identity. The executor validates every writer result before continuing and
rejects duplicate accounts, duplicate snapshots, wrong physical keys, or
unexpected dispositions.

Created, replayed, and reused identities are combined in the plan's required
account order and passed unchanged to the 5K-D1 dependency guard on exactly one
`NetWorthSnapshotWriter` call. The returned net-worth identity, currency,
counts, disposition, and selected lineage must match exactly. Membership
addition, removal, or same-count substitution after coverage therefore fails
inside the final SERIALIZABLE writer and creates no NetWorthSnapshot.

There is deliberately no transaction spanning the whole workflow. Each
AccountSnapshot writer transaction commits independently, followed by the
bounded SERIALIZABLE NetWorth writer. A partial failure leaves valid completed
account rows intact; repeating the same command calls every refresh writer
again, receives exact replay for completed targets, and resumes from persisted
state. The executor performs no compensation delete, update, repair, job-state
write, retry loop, financial calculation, evidence selection, or ID generation.
Injected dependencies must return with the shared session idle; a leaked
transaction is rolled back and surfaced as an internal runtime failure.

Normal incomplete state maps to the stable generic execution-state error and
immutable row differences map to the stable execution-conflict error. No IDs,
currencies, timestamps, financial values, or internal causes enter those
messages. 5K-D2 adds no schema, migration, API, authorization adapter, import
hook, scheduler, queue, worker, or frontend. Those public and post-processing
entry points remain 5K-E.

## Authorized 5K-E1 manual endpoint

`POST /api/v1/snapshot-refresh/recalculate` accepts only `CurrentPrincipal`:
there is no body, user/account selector, output-currency selector, timestamp,
granularity, or lineage input. The application service validates the principal,
closes the authentication read transaction, verifies the shared session is
idle, reads one server clock value, and derives one naive UTC minute bucket.
AccountSnapshot and NetWorth calculation versions must agree; the bucket is
used unchanged for snapshot, calculated, and created timestamps.

The service invokes `UserSnapshotRefreshExecutor` exactly once. Persisted User,
membership, role, base-currency, viewer reuse coverage, financial evidence,
lineage, and writer behavior remain owned by 5K-B through 5K-D2. The public
response contains only the NetWorth snapshot identity/status, bucket metadata,
currency, and aggregate created/replayed/reused counts. It exposes no user,
account, membership, AccountSnapshot, lineage, FX, projection, or audit data.
Incomplete state maps to `snapshot_refresh_unavailable`; immutable conflicts
map to `snapshot_refresh_conflict`; both are generic HTTP 409 errors.

Each domain writer still commits independently. A later failure may therefore
leave completed AccountSnapshots intact, and repeating the request resumes by
exact replay before the final NetWorth write. Viewer accounts remain
`reuse_only`, unsupported active accounts fail the complete operation, and an
empty account set can create or replay one zero-account NetWorth snapshot.
5K-E1 adds no migration, persisted lineage, compensation, automatic retry,
background execution, scheduler, worker, or import hook. Import/post-processing
integration remains exclusively 5K-E2.
