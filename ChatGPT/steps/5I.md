# Step 5I — Account snapshots

## Roadmap and source-of-truth boundary

Account snapshots are derived point-in-time read models. They never replace or
repair canonical transactions, investment events, investment movements,
holdings, prices, or exchange rates.

Step 5I is split into:

- **5I-A** — pure account-snapshot valuation projection;
- **5I-B** — persisted evidence selection and historical financial metrics;
- **5I-C** — exact physical snapshot persistence projection;
- **5I-D** — atomic account-snapshot database writer;
- **5I-E** — authorization and public account-snapshot orchestration.
- **5I-L1** — canonical persisted liability-balance schema and read-only evidence
  selection;
- **5I-L2** — future atomic liability-balance write/import boundary and snapshot
  integration.

`NetWorthSnapshot` is not part of Step 5I. It is deferred to Step 5J.

## Physical AccountSnapshot audit

The inherited PostgreSQL/SQLAlchemy contract is:

```text
id                              TEXT primary key
accountId                       TEXT not null, FK Account, ON DELETE CASCADE
timestamp                       TIMESTAMP(3) not null
granularity                     SnapshotGranularity not null
source                          SnapshotSource not null
currency                        TEXT not null, default CZK
cashValue                       NUMERIC(18,6) not null
investmentValue                 NUMERIC(18,6) not null
investmentCostBasis             NUMERIC(18,6) not null, default 0
netDepositsValue                NUMERIC(18,6) not null, default 0
realizedPnlValue                NUMERIC(18,6) not null, default 0
unrealizedPnlValue              NUMERIC(18,6) not null, default 0
feesValue                       NUMERIC(18,6) not null, default 0
taxesValue                      NUMERIC(18,6) not null, default 0
liabilitiesValue                NUMERIC(18,6) not null
totalValue                      NUMERIC(18,6) not null
cashValueByCurrency             JSONB null
investmentValueByCurrency       JSONB null
investmentCostBasisByCurrency   JSONB null
netDepositsByCurrency           JSONB null
realizedPnlByCurrency           JSONB null
unrealizedPnlByCurrency         JSONB null
feesByCurrency                  JSONB null
taxesByCurrency                 JSONB null
exchangeRates                   JSONB null
isRecalculated                  BOOLEAN not null, default false
calculatedAt                    TIMESTAMP(3) not null
calculationVersion              INTEGER not null, default 1
createdAt                       TIMESTAMP(3) not null
UNIQUE(accountId, timestamp, currency, granularity)
```

The physical identity is
`(accountId, timestamp, currency, granularity)`. `currency` is the persisted
account main currency, never a hard-coded CZK value.

Related physical evidence is:

- `Account.type` distinguishes bank/cash/savings, investment, and liability
  accounts; `Account.currency` is the required snapshot/output currency.
- `Holding` is unique by `(accountId, listingId)` and supplies exact positive
  quantity, weighted-average price, and its cost currency. Its nullable current
  valuation columns are not trusted by 5I-A.
- `PriceSnapshot` is unique by `(listingId, timestamp, source)` and stores
  `price NUMERIC(28,10)`, currency, persisted asset/listing identity, source,
  and `TIMESTAMP(3)`.
- `ExchangeRate` is unique by `(fromCurrency, toCurrency, date, source)` and
  stores `rate NUMERIC(18,8)` plus `TIMESTAMP(3)`.
- `Transaction` stores signed/account-typed `NUMERIC(18,6)` evidence, but there
  is no canonical persisted account-balance aggregate.
- `LiabilityBalance` stores exact positive balance observations for
  credit-card, loan, and mortgage accounts. Ordinary `Transaction` rows remain
  insufficient to prove outstanding liability.
- the existing TypeScript snapshot service buckets in UTC (ISO Monday for
  weeks), treats allocation as 0–100, groups bank/cash/savings as cash accounts,
  groups credit-card/loan/mortgage as liabilities, and groups broker/exchange/
  crypto-wallet as investments. Its float arithmetic, avg-price fallback, and
  latest-price/FX selection are not adopted by this exact Python contract.

## Snapshot identity and granularity

The pure identity input is:

```text
account_id
snapshot_timestamp
granularity
source
account main/output currency
calculation_version
```

All timestamps are canonical naive UTC `TIMESTAMP(3)` values. The builder does
not normalize or shift buckets:

- minute: seconds and microseconds are zero;
- hour: minute, seconds, and microseconds are zero;
- day: `00:00:00.000`;
- week: Monday `00:00:00.000` (ISO week start);
- month: first day `00:00:00.000`.

Timezone-aware, sub-millisecond, or unaligned input fails closed.

## Price evidence

Every open Holding requires exactly one caller-selected price for the same
listing and asset. Price evidence includes persisted evidence ID, listing,
asset, symbol, positive `NUMERIC(28,10)` price, uppercase currency,
`PriceSource`, and a canonical as-of timestamp not later than the snapshot.

5I-A never selects a latest price, uses `Holding.avgBuyPrice` as a current
price, accepts a future price, omits an unpriced Holding, or applies a freshness
window. No maximum-age policy currently exists; freshness selection is deferred
to the future database adapter.

## FX evidence

The exact direction is:

```text
1 base_currency × rate = quote_currency
```

Every foreign native value requires one direct caller-selected
`base_currency -> snapshot currency` rate. Same-currency conversion is exactly
one and requires no FX row. Reverse-pair inference and live FX are forbidden.

Rates are positive finite `RATE = NUMERIC(18,8)` values with canonical
`ExchangeRateSource` and a timestamp not later than the snapshot. Duplicate,
conflicting, missing, future, wrong-direction, or unused evidence fails closed.
The projection exposes only the consumed rates, sorted by `(base, quote)`.

## Cash and liability boundaries

The current architecture groups account types as:

| Account type | Cash evidence | Holding evidence | Liability evidence |
| --- | --- | --- | --- |
| `bank`, `cash`, `savings` | allowed, including exact negative balances | forbidden | forbidden |
| `broker`, `exchange`, `crypto_wallet` | allowed, including exact negative balances | allowed | forbidden |
| `credit_card`, `loan`, `mortgage` | forbidden | forbidden | allowed as a positive magnitude |

Cash and liabilities are caller-supplied complete as-of balances grouped by
currency. 5I-A validates and converts them; it does not replay transactions.
Negative cash remains cash and is never silently reclassified as a liability.
Liability evidence must be strictly positive. Empty evidence means exact zero.

## Valuation and allocation

For each Holding:

```text
native_value = quantity × price_per_unit
value = direct_convert(native_value, price_currency, snapshot_currency)
native_cost_basis = quantity × average_buy_price
cost_basis = direct_convert(native_cost_basis, cost_currency, snapshot_currency)
```

Aggregates:

```text
investment_value = Σ item.value
investment_cost_basis = Σ item.cost_basis
cash_value = Σ converted cash balances
liabilities_value = Σ converted positive liability magnitudes
total_value = cash_value + investment_value − liabilities_value
allocation_pct = item.value / investment_value × 100
```

`PERCENTAGE = NUMERIC(8,4)` uses the existing 0–100 convention. A
non-representable allocation fails closed; there is no hidden last-item
remainder adjustment. Empty Holdings produce no items and exact zero investment
totals.

All inputs and results use finite `Decimal` values. `MONEY = NUMERIC(18,6)`,
`QUANTITY = NUMERIC(28,10)`, `RATE = NUMERIC(18,8)`, `PERCENTAGE =
NUMERIC(8,4)`, and `TIMESTAMP(3)` are read from the SQLAlchemy physical types.
Intermediate calculations use elevated precision and are never rounded or
truncated.

## 5I-A purity and fail-closed boundary

`build_account_snapshot_projection` performs no database access, price/FX
selection, current-time lookup, ID generation, serialization, ORM mutation, or
partial calculation. Inputs and outputs are frozen, outputs are deterministically
sorted, and input permutation has no effect.

One blank identity, foreign Holding, duplicate listing, relation mismatch,
missing/duplicate/future price, malformed numeric value, missing/duplicate/
future/wrong/unused FX evidence, invalid cash/liability evidence, arithmetic
overflow, or non-representable allocation invalidates the complete projection.

5I-A adds no repository, database writer, endpoint, authorization, scheduled
work, provider integration, Holding valuation update, `NetWorthSnapshot`,
migration, or schema DDL.

## 5I-B persisted evidence contract

5I-B is a read-only, caller-transaction-owned adapter. It loads one persisted
account, explicitly joins Holdings to Listing and Asset evidence, selects
persisted prices and direct FX, derives native balances, derives exact
investment-account historical flows, delegates all current valuation arithmetic
to 5I-A, and returns frozen non-ORM evidence with explicit metric completeness.
It never calls `commit`, `rollback`, `begin`, `begin_nested`, or `flush`, and
never writes snapshot rows.

### Selection order

For each open Holding, the eligible price set is
`PriceSnapshot.timestamp <= snapshot_timestamp`. The greatest timestamp wins
only when exactly one row exists at that timestamp. The project has no
documented cross-provider price precedence, so two sources at the selected
timestamp are ambiguous and fail closed; `id` is ordering evidence, never a
financial tie-breaker. No maximum price age is currently defined.

FX uses only a persisted direct pair:

```text
1 base currency × rate = account/output currency
```

Reverse inference, currency chains, and live rates are forbidden. The same
latest-unambiguous rule applies. `ExchangeRate.date` is a canonical naive
`TIMESTAMP(3)`, not a SQL `DATE`. Snapshot valuation selects as of the snapshot
timestamp. Net deposits, explicit realized P/L, fees, and taxes select
separately as of each event timestamp. The result preserves snapshot-rate IDs
and historical-rate IDs as separate deterministic tuples.

### Active history and balances

- `bank`, `cash`, and `savings` balances are the exact signed sum of all active
  canonical Transactions through the snapshot timestamp, grouped by currency.
  Income is positive, expense is negative, and only explicitly classified
  transfer rows are accepted. The physical Account model has no separate
  opening-balance field, so the canonical persisted balance contract starts at
  zero and every balance-changing amount is a Transaction. Archived, deleted,
  and future rows are excluded. Transaction has no pending or reversal state;
  such a state is therefore neither silently assumed nor filtered.
- `broker`, `exchange`, and `crypto_wallet` cash balances are the signed sum of
  active canonical cash, fee, and tax InvestmentMovements through the timestamp.
  Generic Transactions are not mixed into this ledger.
- `credit_card`, `loan`, and `mortgage` fail closed. The physical model has no
  opening balance, dedicated liability balance, or persisted rule proving that
  the absolute value of Transactions is the outstanding principal. The older
  TypeScript float-based treatment is not adopted.

For every supported non-liability account, `liabilities_value = 0` and the
native liability breakdown is empty because the account-type contract makes
liability evidence structurally impossible. That structural zero is different
from an unknown liability balance: unknown liability accounts fail before
Holding, price, FX, Transaction, ledger, 5I-A, or metric processing and never
produce a placeholder result. Liability support requires 5I-L and is not part
of the claim that the supported 5I account snapshots are complete.

An active InvestmentEvent means `archivedAt IS NULL` and `deletedAt IS NULL`;
all its loaded movements must have the same account and a unique persisted ID.
An event with no movement is corrupt.

### Historical financial metrics

The physical Transaction enums do not encode complete cash-account metric
evidence:

| Transaction evidence | Persisted meaning | 5I-B metric treatment |
| --- | --- | --- |
| `income` + `real_income` | ordinary signed income | cash balance only; not an external deposit |
| `expense` + `real_expense` | ordinary signed expense | cash balance only; not withdrawal, fee, or tax |
| `transfer` + `internal_transfer` | internal transfer | excluded from external net deposits |
| `transfer` + `investment_transfer` | investment transfer | excluded without persisted externality |
| `transfer` + `cash_exchange` | currency exchange | excluded from external net deposits |
| `transfer` + `credit_card_payment` | credit-card payment | excluded from deposit, fee, and tax |
| `transfer` + `loan_repayment` | loan repayment | excluded from deposit, fee, and tax |
| `loan_given`, `loan_received`, `refund`, `ignored`, `needs_review` | no complete external-capital/fee/tax contract | no exact cash-account metric mapping |

There is no explicit Transaction classification for external deposit, external
withdrawal, bank fee, tax, interest, or dividend. Description, counterparty,
note, category, amount sign, and account type are not substitute classification
evidence.

The 5I-B result therefore uses a tagged immutable union:

```text
ExactSnapshotMetric(value, breakdown)
UnsupportedSnapshotMetric(reason)
```

For `bank`, `cash`, and `savings`, net deposits, realized investment P/L, fees,
and taxes are explicitly unsupported. They are never returned as `Decimal(0)`
and an unsupported metric has no `value` or `breakdown` to serialize. Future
5I-C must fail rather than persisting an unsupported metric into a non-null
physical financial column. Realized P/L is not structural zero because the
physical schema does not constrain InvestmentEvent rows by Account type.

These cash-account values are structurally exact:

- `investment_value = 0`;
- `investment_cost_basis = 0`;
- unrealized investment P/L = 0.

The zeroes are valid because cash-account Holdings are forbidden by the 5I-A
account-type contract and 5I-B rejects any persisted Holding for these account
types. Ordinary income is not investment realized P/L, and absence of loaded
investment events is not treated as proof of lifetime realized P/L zero.

For `broker`, `exchange`, and `crypto_wallet`, metrics remain lifetime
cumulative through the snapshot timestamp:

- net deposits are explicit `cash_deposit` incoming cash less
  `cash_withdrawal` outgoing cash;
- buys, sells, dividends, interest, conversions, fees, and taxes are excluded
  from net deposits;
- asset transfers fail closed because the persisted event graph has no
  counter-account/externality identity and therefore cannot prevent internal
  transfer double-counting;
- realized P/L uses only the paired
  `InvestmentEvent.realizedPnl`/`realizedPnlCurrency` evidence;
- fee and tax movements must be outgoing and are stored as positive expense
  magnitudes;
- description text never classifies a fee, tax, or transfer.

All native breakdowns and converted aggregates must be exactly representable by
`MONEY`. No float, rounding, truncation, recomputation of missing realized P/L,
or placeholder value is allowed.

Current account-currency unrealized P/L is exactly:

```text
investment_value - investment_cost_basis
```

A native unrealized breakdown is emitted only when an item's native value
currency equals its native cost currency. If any item crosses currencies, the
account-currency aggregate remains exact but the native breakdown is `None`;
currencies are never subtracted from each other.

### Coherent-read contract for 5I-D

5I-B deliberately owns no write transaction or public lock orchestration. Its
caller must provide a coherent database view. The implemented 5I-D lock order
is:

1. the Account row `FOR SHARE`;
2. an identity-scoped snapshot transaction advisory lock;
3. the same sorted account/source canonical-history advisory locks used by
   posting and Holding rebuild;
4. active canonical Event/Movement rows and current Holding rows `FOR UPDATE`;
5. explicit Listing and Asset evidence `FOR UPDATE`;
6. compatible `SHARE` table locks on `PriceSnapshot` and `ExchangeRate`;
7. 5I-B evidence selection and 5I-C projection;
8. existing AccountSnapshot identity and items `FOR UPDATE`.

The writer deliberately retains PostgreSQL `READ COMMITTED`. A waiting writer
must see a snapshot committed by the preceding identity-lock holder so it can
perform exact replay; starting `REPEATABLE READ` before that wait would retain
the pre-commit view. The canonical advisory/row locks prevent mixed ledger and
Holding history. The two compatible market-evidence `SHARE` locks prevent a
price or FX insert/update from appearing between 5I-B's separate queries while
allowing concurrent snapshot readers. Database authorization and public
orchestration remain 5I-E.

## 5I-C physical persistence projection

`build_account_snapshot_persistence_projection` is a pure adapter from one
`CompleteAccountSnapshotEvidence` plus explicit persistence metadata to frozen
expected `AccountSnapshot` and `AccountSnapshotItem` rows. It accepts no
session, performs no I/O, constructs no ORM object, and does not detect replay.
Every non-null physical financial column must be backed by an
`ExactSnapshotMetric`; any unsupported net-deposit, realized/unrealized P/L,
fee, or tax metric rejects the whole projection with one generic error.
Consequently, current `bank`, `cash`, and `savings` evidence remains useful for
read-only valuation but is not physically persistable.

The snapshot identity is UUIDv5 over the canonical tuple
`(account_id, timestamp-at-milliseconds, currency, granularity)`. Each item ID
is UUIDv5 over `(snapshot_id, listing_id)`. Fixed project namespaces and NUL
delimiters make equal inputs produce equal IDs without accepting caller IDs or
using current time. Items are sorted by listing ID.

All physical `MONEY`, `QUANTITY`, `PERCENTAGE`, and `TIMESTAMP(3)` values are
revalidated against the SQLAlchemy types without rounding. The adapter also
checks total value, unrealized P/L, item value and cost-basis sums, unique
listing identities, and exact 100-percent allocation for a nonempty investment
set. `isRecalculated` must be true exactly for
`manual_recalculation`; `calculatedAt` and `createdAt` are explicit
millisecond-exact naive timestamps.

Currency-breakdown JSONB uses sorted uppercase currency keys and fixed-scale
decimal strings: scale 6 for physical money breakdowns and scale 10 for native
investment value/cost evidence. An exact empty breakdown is `{}`. A
mathematically exact aggregate whose native decomposition is unavailable, such
as mixed-currency unrealized P/L, remains JSON `null`, never `{}`.

`exchangeRates` is a versioned object:

```text
{
  "version": 1,
  "snapshotRates": [
    {
      "rateId": "...",
      "from": "EUR",
      "to": "CZK",
      "rate": "25.00000000",
      "timestamp": "2026-07-27T00:00:00.000",
      "source": "ecb"
    }
  ],
  "historicalRateIds": ["..."]
}
```

Snapshot rates and IDs are sorted and deduplicated. Selected price IDs cannot
be stored in the current physical schema, so the immutable projection retains
them only in non-row audit metadata. Historical FX values are likewise not
fabricated: only the IDs selected by 5I-B are persisted alongside full
snapshot-rate evidence. The schema has no liability-breakdown column; 5I-C
validates that valuation evidence but maps only the physical aggregate.

## 5I-D atomic database writer

`AccountSnapshotWriter` accepts one frozen command with account identity,
snapshot identity, calculation version, and explicit millisecond-exact
persistence timestamps. It requires an idle `AsyncSession`, opens exactly one
outer transaction, composes 5I-B once and 5I-C once, and either inserts one
complete snapshot graph or returns an exact read-only replay. It never updates,
deletes, upserts, or repairs an existing snapshot.

The snapshot advisory scope is the NUL-delimited tuple
`snapshots:account`, account ID, millisecond timestamp, output currency, and
granularity. Its signed 64-bit lock ID is the first eight bytes of SHA-256,
matching the repository lock convention while retaining a distinct namespace.
Different identities do not share this lock; same-account writers may still
serialize on canonical source locks when necessary for coherent history.

After both physical flushes, the writer reloads the snapshot and its items in
deterministic `(listingId, id)` order and revalidates every column. Exact replay
rebuilds current expected evidence before comparing every snapshot and item
field, including JSONB structures, explicit metadata, deterministic IDs, and
item multiplicity. Any difference is a generic conflict and causes no repair.
Unsupported 5I-B/5I-C evidence, constraint failure, or reload mismatch rolls
back the complete outer transaction.

The writer creates only `AccountSnapshot` and `AccountSnapshotItem`. It does
not mutate Holding, canonical history, prices, FX, account metadata, or logs.
It has no HTTP or authorization dependency.

## 5I-E authorized manual orchestration

The public manual operation is:

```text
POST /api/v1/accounts/{account_id}/snapshots/recalculate
```

It accepts no request body. The authenticated principal may invoke it only
through a persisted `owner`, `admin`, or `editor` membership. Viewer,
non-member, missing-account, and archived-account paths share the existing
generic `account_not_found` response so account existence is not disclosed.

The server owns all writer metadata. It captures the injected UTC clock once
and uses the start of that minute as `snapshot_timestamp`, `calculated_at`, and
`created_at`, with `granularity=minute`, `source=manual_recalculation`,
`is_recalculated=true`, and calculation version 1. Calls in the same minute
therefore share one deterministic physical identity and exact replay; the next
minute creates a distinct snapshot.

Authentication and membership lookup autobegin a short read transaction on the
request session. The application service completes that transaction before
calling `AccountSnapshotWriter` exactly once, and verifies that the session is
idle. The writer continues to own its single atomic persistence transaction.
The writer re-locks and revalidates the Account, so an account archived after
authorization fails without a snapshot.

Membership authorization follows the existing request-time authorization
contract. A membership revoked in the narrow interval after the authorization
transaction and before the writer commits is not atomically revalidated in
5I-E; eliminating that race requires a shared authorization/writer transaction
contract and is explicitly deferred rather than weakening 5I-D.

Created and exact-replay results both return HTTP 200 with only snapshot ID,
account ID, created/replayed status, item count, bucket timestamp, granularity,
and currency. Unsupported or incomplete evidence and writer state errors map to
one generic 409; persisted physical conflicts map to a separate generic 409.
No financial evidence, selected market-data identity, ORM state, or internal
failure reason is exposed.

Steps 5I-A through 5I-E are implemented. Step 5I-L1 adds canonical persisted
liability evidence but deliberately does not enable liability snapshot
creation. The write/import boundary and snapshot integration remain 5I-L2,
and `NetWorthSnapshot` remains Step 5J.

## 5I-L1 canonical liability-balance evidence

`LiabilityBalance` is an append-style balance observation tied to exactly one
`Account`. It is valid only for `credit_card`, `loan`, and `mortgage` accounts.
The database cannot express that cross-table account-type rule as an honest
`CHECK`, so the read boundary validates it fail closed. Bank, cash, savings,
broker, exchange, and crypto-wallet accounts are rejected.

All balance components are positive amounts owed and use canonical
`NUMERIC(18,6)`:

```text
totalOutstanding =
    outstandingPrincipal
  + accruedInterest
  + feesOutstanding
```

Each component and the total are nonnegative. A fully repaid liability is an
explicit persisted zero observation; missing evidence is never converted to
zero. `currency` is canonical uppercase text and must equal `Account.currency`.
`effectiveAt` and `createdAt` are exact naive `TIMESTAMP(3)` values. The
dedicated source enum is `manual | statement | provider | import | migration`.
The physical identity prevents duplicate `(accountId, effectiveAt, source)`
observations and duplicate non-null `(accountId, source, externalId)`
identities.

The caller-transaction-owned evidence service loads the Account, rejects
archived or unsupported accounts, selects all observations with
`effectiveAt <= snapshot_timestamp`, and considers only the greatest eligible
timestamp. Exactly one observation at that timestamp is required. Multiple
sources at the same latest timestamp are ambiguous and fail closed; there is no
source priority. A malformed latest row also fails instead of falling back to
an older valid row. The service returns a frozen domain value, performs no
write or lock, and never begins, commits, or rolls back a transaction.

5I-L1 does not change 5I-A/5I-B liability-account behavior: public liability
snapshot creation remains disabled until a future 5I-L2 writer/import boundary
and complete end-to-end integration are proven.
