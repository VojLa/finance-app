# Step 5I — Account snapshots

## Roadmap and source-of-truth boundary

Account snapshots are derived point-in-time read models. They never replace or
repair canonical transactions, investment events, investment movements,
holdings, prices, or exchange rates.

Step 5I is split into:

- **5I-A** — pure account-snapshot evidence and valuation calculation contract;
- **5I-B** — exact physical snapshot persistence projection;
- **5I-C** — atomic account-snapshot database writer;
- **5I-D** — authorization and public account-snapshot orchestration.

`NetWorthSnapshot` is not part of Step 5I. It is deferred to Step 5J.

## Physical AccountSnapshot audit

The inherited PostgreSQL/SQLAlchemy contract is:

```text

investmentCostBasis             NUMERIC(18,6) not null, default 0
netDepositsValue                NUMERIC(18,6) not null, default 0
realizedPnlValue                NUMERIC(18,6) not null, default 0
unrealizedPnlValue              NUMERIC(18,6) not null, default 0
feesValue                       NUMERIC(18,6) not null, default 0
taxesValue                      NUMERIC(18,6) not null, default 0
liabilitiesValue                NUMERIC(18,6) not null
totalValue                      NUMERIC(18,6) not null
cashValueByCurrency             JSONB null
investmentValueByCurrency       JSONB null
investmentCostBasisByCurrency   JSONB null
netDepositsByCurrency           JSONB null

unrealizedPnlByCurrency         JSONB null

taxesByCurrency                 JSONB null

calculatedAt                    TIMESTAMP(3) not null
calculationVersion              INTEGER not null, default 1
createdAt                       TIMESTAMP(3) not null
UNIQUE(accountId, timestamp, currency, granularity)
```

The physical identity is
`(accountId, timestamp, currency, granularity)`. `currency` is the persisted
account main currency, never a hard-coded CZK value.

Related physical evidence is:

- `Account.type` distinguishes bank/cash/savings, investment, and liability
  accounts; `Account.currency` is the required snapshot/output currency.
- `Holding` is unique by `(accountId, listingId)` and supplies exact positive
  quantity, weighted-average price, and its cost currency. Its nullable current
  valuation columns are not trusted by 5I-A.
- `PriceSnapshot` is unique by `(listingId, timestamp, source)` and stores
  `price NUMERIC(28,10)`, currency, persisted asset/listing identity, source,
  and `TIMESTAMP(3)`.
- `ExchangeRate` is unique by `(fromCurrency, toCurrency, date, source)` and
  stores `rate NUMERIC(18,8)` plus `TIMESTAMP(3)`.
- `Transaction` stores signed/account-typed `NUMERIC(18,6)` evidence, but there
  is no canonical persisted account-balance aggregate.
- there is no separate Loan, Mortgage, CreditCard, or liability-balance table;
  liability semantics currently come from `Account.type`.
- the existing TypeScript snapshot service buckets in UTC (ISO Monday for
  weeks), treats allocation as 0–100, groups bank/cash/savings as cash accounts,
  groups credit-card/loan/mortgage as liabilities, and groups broker/exchange/
  crypto-wallet as investments. Its float arithmetic, avg-price fallback, and
  latest-price/FX selection are not adopted by this exact Python contract.

## Snapshot identity and granularity

The pure identity input is:

```text
account_id
snapshot_timestamp
granularity
source
account main/output currency
calculation_version
```

All timestamps are canonical naive UTC `TIMESTAMP(3)` values. The builder does
not normalize or shift buckets:

- minute: seconds and microseconds are zero;
- hour: minute, seconds, and microseconds are zero;
- day: `00:00:00.000`;
- week: Monday `00:00:00.000` (ISO week start);
- month: first day `00:00:00.000`.

Timezone-aware, sub-millisecond, or unaligned input fails closed.

## Price evidence

Every open Holding requires exactly one caller-selected price for the same
listing and asset. Price evidence includes persisted evidence ID, listing,
asset, symbol, positive `NUMERIC(28,10)` price, uppercase currency,
`PriceSource`, and a canonical as-of timestamp not later than the snapshot.

5I-A never selects a latest price, uses `Holding.avgBuyPrice` as a current
price, accepts a future price, omits an unpriced Holding, or applies a freshness
window. No maximum-age policy currently exists; freshness selection is deferred
to the future database adapter.

## FX evidence

The exact direction is:

```text
1 base_currency × rate = quote_currency
```

Every foreign native value requires one direct caller-selected
`base_currency -> snapshot currency` rate. Same-currency conversion is exactly
one and requires no FX row. Reverse-pair inference and live FX are forbidden.

Rates are positive finite `RATE = NUMERIC(18,8)` values with canonical
`ExchangeRateSource` and a timestamp not later than the snapshot. Duplicate,
conflicting, missing, future, wrong-direction, or unused evidence fails closed.
The projection exposes only the consumed rates, sorted by `(base, quote)`.

## Cash and liability boundaries

The current architecture groups account types as:

| Account type | Cash evidence | Holding evidence | Liability evidence |
| --- | --- | --- | --- |
| `bank`, `cash`, `savings` | allowed, including exact negative balances | forbidden | forbidden |
| `broker`, `exchange`, `crypto_wallet` | allowed, including exact negative balances | allowed | forbidden |
| `credit_card`, `loan`, `mortgage` | forbidden | forbidden | allowed as a positive magnitude |

Cash and liabilities are caller-supplied complete as-of balances grouped by
currency. 5I-A validates and converts them; it does not replay transactions.
Negative cash remains cash and is never silently reclassified as a liability.
Liability evidence must be strictly positive. Empty evidence means exact zero.

## Valuation and allocation

For each Holding:

```text
native_value = quantity × price_per_unit
value = direct_convert(native_value, price_currency, snapshot_currency)
native_cost_basis = quantity × average_buy_price
cost_basis = direct_convert(native_cost_basis, cost_currency, snapshot_currency)
```

Aggregates:

```text
investment_value = Σ item.value
investment_cost_basis = Σ item.cost_basis
cash_value = Σ converted cash balances
liabilities_value = Σ converted positive liability magnitudes
total_value = cash_value + investment_value − liabilities_value
allocation_pct = item.value / investment_value × 100
```

`PERCENTAGE = NUMERIC(8,4)` uses the existing 0–100 convention. A
non-representable allocation fails closed; there is no hidden last-item
remainder adjustment. Empty Holdings produce no items and exact zero investment
totals.

All inputs and results use finite `Decimal` values. `MONEY = NUMERIC(18,6)`,
`QUANTITY = NUMERIC(28,10)`, `RATE = NUMERIC(18,8)`, `PERCENTAGE =
NUMERIC(8,4)`, and `TIMESTAMP(3)` are read from the SQLAlchemy physical types.
Intermediate calculations use elevated precision and are never rounded or
truncated.

## 5I-A purity and fail-closed boundary

`build_account_snapshot_projection` performs no database access, price/FX
selection, current-time lookup, ID generation, serialization, ORM mutation, or
partial calculation. Inputs and outputs are frozen, outputs are deterministically
sorted, and input permutation has no effect.

One blank identity, foreign Holding, duplicate listing, relation mismatch,
missing/duplicate/future price, malformed numeric value, missing/duplicate/
future/wrong/unused FX evidence, invalid cash/liability evidence, arithmetic
overflow, or non-representable allocation invalidates the complete projection.

5I-A adds no repository, database writer, endpoint, authorization, scheduled
work, provider integration, Holding valuation update, `NetWorthSnapshot`,
migration, or schema DDL.
