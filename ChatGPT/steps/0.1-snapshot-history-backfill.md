# Version 0.1 snapshot-history and backfill remediation

## Objective

Implement ADR 0016 without weakening the completed R12 current-publication
boundary. The visible result is an atomically published portfolio history from
the first canonical financial event, corrected after late imports, captured
periodically and compacted into bounded Prague-local resolution layers.

This is an XL epic. Each item below is a separate design -> implementation ->
test -> verification loop. No item may claim PASS from documentation or unit
tests alone.

## Status

- H0 architecture and ADR: complete
- H1 through H13: planned, not implemented
- Final acceptance: not started; no PASS claimed

## Non-negotiable acceptance invariants

- Canonical finance remains the only historical source of truth.
- Dirty history begins at the earliest unprocessed `financialTimestamp`.
- The public reader sees one complete generation, never a partially replaced
  suffix.
- R12 anchors, D1 baselines and current snapshots are neither reused as
  generation work rows nor removed by compaction.
- A point never consumes price or FX evidence newer than itself.
- History arithmetic uses exact Decimal boundaries and existing snapshot
  rounding policy; the browser performs no financial calculation.
- Europe/Prague defines wall-clock and calendar buckets; PostgreSQL stores UTC.
- One user has at most one running history mutation job.
- Current portfolio publication and history rebuild have separate public
  states.

## H1 - Semantic closure

Define exact as-of behavior for bank, cash, savings, investment and liability
accounts; transaction versus investment-movement cash ownership; archived
roots; same-timestamp ordering; initial boundary; source freshness; missing
evidence; current-membership MVP scope; and safe public rebuild states.

Acceptance requires parity fixtures for all supported account types. Complete
Raiffeisenbank/net-worth history remains blocked while bank/cash/savings as-of
valuation is not representable.

## H2 - History schema

Add one Alembic revision and exact SQLAlchemy/schema-ownership parity for:

- `PortfolioHistoryJob`;
- `PortfolioHistoryDirtyRange`;
- `PortfolioHistorySchedule`;
- `PortfolioHistoryGeneration` and `PortfolioHistoryPublication`;
- `PortfolioHistoryGenerationAccount`;
- `PortfolioHistoryPoint` and `PortfolioHistoryAccountPoint`;
- normalized price and FX use lineage.

Required constraints include one running job per user, generation-local point
identity, positive resolution/sample counts, exact close financial identity,
bounded JSON and error data, and valid generation/publication states. Clean
bootstrap, populated upgrade, schema artifact, Alembic check and SQLAlchemy
parity must pass.

Generation rows also persist a database-checked build cause
(`rebuild|capture|compaction`), exact nullable dirty-epoch/build-from shape,
parent publication id+version fence and SHA-256 of the full frozen canonical
input. Capture/compaction never delete dirty state; publication re-freezes the
canonical input, including exact alias provider/symbol, before pointer swap.

## H3 - Dedicated durable jobs

Implement claim, fenced lease, heartbeat, checkpoint, automatic retry,
authorized status and explicit retry for history jobs without changing the R12
import job contract. Cover concurrent claims, lost lease, expired recovery,
attempt exhaustion and process shutdown.

## H4 - Prague buckets and retention

Implement pure deterministic bucket functions for the approved lattice:

```text
30m -> 2h -> 6h -> 12h -> 1d -> 2d -> 4d -> 8d -> 16d -> 32d
```

Test CET/CEST transitions, leap years, month/year range boundaries, parent
containment, retention cutoffs and the 480-point public target. Rollups retain
first open, actual high/low and last close; they never average net worth.

## H5 - Chronological replay

Create a pure/repository-separated replay that loads canonical roots once,
orders them deterministically and advances account state incrementally through
requested buckets. Reuse existing canonical Holding/cost-basis and snapshot
arithmetic rather than create a second domain definition. Cover backdated
deposits, trades, fees, dividends, withdrawals, partial disposal, liabilities,
archival and same-timestamp events.

## H6 - Historical market providers

Add bounded range/batch ports and parsers for the configured Yahoo Finance,
CoinGecko and Twelve Data price/FX policy. Fetch once per exact provider
identity and range, persist observations through the existing append-only
market writer, and select only evidence at or before each bucket. Test provider
limits, pagination/chunking, weekends, holidays, delisted/missing symbols,
malformed responses, cancellation and bounded concurrency.

## H7 - Generation build and publication

Freeze membership/account/currency/canonical manifests, copy only a compatible
prefix, rebuild from the job-fenced `buildFrom`, generate retention-appropriate layers,
persist account sums and market lineage, and validate the whole private
generation. Publication must re-lock and compare the invalidation revision and
all manifests before atomically switching the user pointer. Drift schedules a
new attempt and leaves the old generation public.

## H8 - Import and canonical invalidation

Under the existing R12 account/member completion locks, upsert dirty ranges and
history jobs for every current member of every affected account before import
targets publish and the job completes. Do not make the long rebuild part of the
R12 lease transaction. Add the same invalidation boundary to every manual
canonical writer and to membership, archive, account-currency and user-base-
currency changes. Exact duplicates must not cause an unnecessary rebuild.

## H9 - Scheduler and capture

Run a short scheduler tick under a PostgreSQL advisory lock and enqueue exact
30-minute Prague slots idempotently. Capture appends only when the publication
and canonical manifests remain current. A dirty/building user defers. Missing
slots after downtime become an incremental historical rebuild, not a synthetic
current point.

## H10 - Compaction and audit

Materialize and verify parent rollups before deleting expired history detail.
Keep a rollback generation for at least seven days. Never delete canonical,
market, R12 or D1 evidence. The audit checks coverage, duplicate buckets,
account/user sums, close identities, lineage, publication pointer and retention
policy, and emits only safe operational counts/errors.

## H11 - API contract

Extend history ranges with `1D`, `5Y` and `10Y`. The server selects one
resolution and returns at most 480 points plus explicit resolution, coverage
and `building|ready|failed|empty` state. While rebuilding, the last complete
generation may remain visible. Generate TypeScript types from OpenAPI; do not
hand-author contract drift.

## H12 - Browser behavior

Update the thin Next adapter, strict contract parser, portfolio page and chart
controls. Display current-import completion separately from history rebuild
progress/failure. Account selection remains presentation-only unless a later
API explicitly adds account-scoped history. The browser does not average,
convert, merge or synthesize points.

## H13 - Final acceptance

Required real-environment scenarios:

| Scenario                  | Required result                                             |
| ------------------------- | ----------------------------------------------------------- |
| First five-year import    | Published history begins at first canonical event           |
| Five-day late import      | Only the affected suffix changes after atomic swap          |
| Five-year forgotten file  | Earlier years appear and later years are corrected          |
| Exact duplicate           | No new canonical rows or unnecessary rebuild                |
| Concurrent late imports   | `dirtyFrom` stays earliest; stale build never publishes     |
| Worker crash/lease expiry | Idempotent resume without partial public generation         |
| Shared account            | Every current member receives the correct user generation   |
| Membership change         | Explicit current-membership full-history rule is enforced   |
| DST/weekend/holiday       | Prague buckets and prior-only evidence remain correct       |
| Provider failure          | Old generation stays public and retry state is safe         |
| Compaction                | Display closes remain equal and protected evidence survives |
| `1D` through `ALL`        | Correct layer, order, uniqueness and at most 480 points     |
| Raiffeisenbank account    | Cash/net-worth history agrees with canonical transactions   |

Run focused tests first, then complete backend, PostgreSQL migration/schema,
OpenAPI, frontend type/test/lint and browser gates. Final audit is read-only and
may claim PASS only after every row above has executable evidence.
