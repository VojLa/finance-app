# 5G-B2 – Conservative asset and listing resolution

## Metadata

- Milestone: `0.1 - Architecture Locked`
- Parent: `5G-B - canonical investment posting foundation`
- Dependency: Step 5G-B1, merged as `89d1bd37e5aeabd6a06c06060e70766755f0a43f`
- Size: M
- Source of truth: `InvestmentAssetResolutionPlan`, canonical SQLAlchemy asset models and inherited database constraints

## Goal

Add a caller-transaction-owned resolver that consumes one immutable
`InvestmentAssetResolutionPlan` and returns one exact canonical `Asset` plus one exact
provider `AssetListing`.

The resolver must:

1. serialize all competing provider-symbol and ISIN identities before lookup or creation;
2. prefer an exact compatible provider listing;
3. otherwise reuse one unique compatible ISIN asset and create only the missing listing;
4. otherwise create one new asset/listing pair only when canonical evidence is sufficient;
5. reject ambiguous, contradictory or under-specified identity without mutation;
6. support deterministic replay and concurrent retry;
7. never commit, roll back, create investment events or change import rows/batches.

B2 is database persistence, but only for global asset identity. Investment event/movement
persistence remains 5G-B3.

## Input contract

The resolver accepts one B1 `InvestmentAssetResolutionPlan`.

Every field is already typed, normalized and bounded by B1, but persisted/caller values
must still be treated as untrusted at the service boundary. Reject malformed values using
`ImportPostStateError`.

Required non-blank values:

```text
symbol
provider_symbol
exchange
```

Required enums:

```text
asset_type
provider
```

Optional canonical values:

```text
isin
name
listing_currency_hint
asset_currency_hint
```

Provider and exchange must remain one of the B1 mappings:

```text
PriceSource.broker   + exchange=trading212
PriceSource.exchange + exchange=anycoin
```

Any other pair fails closed.

## Result contract

Add a frozen result equivalent to:

```text
ResolvedInvestmentAsset
  asset: AssetModel
  listing: AssetListingModel
  asset_created: bool
  listing_created: bool
```

The result must always contain both an asset and a listing. B3 must never need to infer a
listing later.

Exact replay of the same plan in a later session must return the same asset/listing IDs with
both created flags false.

## Inherited database constraints

The current schema provides:

```text
Asset.isin                       nullable, non-unique
Asset.symbol                     indexed, non-unique
AssetListing(assetId,symbol,exchange,currency) unique
AssetListing(symbol,exchange,currency)         unique
AssetListing(provider,providerSymbol,currency) unique
```

Therefore:

- global symbol alone is never a merge key;
- ISIN ambiguity must be detected in application code;
- provider identity must be serialized before lookup/creation;
- listing currency is required for creation;
- existing conflicting rows must not be repaired or overwritten.

## Advisory lock contract

Use PostgreSQL transaction advisory locks.

Build deterministic signed 64-bit lock IDs using SHA-256, matching the established import
lock style.

Acquire locks before any identity lookup and hold them until caller commit/rollback.

Required logical scopes:

```text
assets:provider:<provider>:<provider_symbol>
assets:isin:<isin>                     # only when ISIN is present
```

Do not include listing currency in the provider lock. Currency-less resolution must
serialize against currency-specific creation for the same provider symbol.

When both locks exist:

1. derive both signed lock IDs;
2. remove accidental duplicate IDs;
3. sort numerically;
4. acquire in sorted order.

This deterministic ordering is mandatory to prevent deadlocks when concurrent requests use
the same ISIN with different provider symbols.

The resolver must not use session-level advisory locks.

## Resolution algorithm

Run the following algorithm only after advisory locks are held.

### Phase 1 – exact provider listing

Query provider listings by:

```text
provider = plan.provider
providerSymbol = plan.provider_symbol
```

When `listing_currency_hint` is present, also require exact currency.

Lock returned listing/asset rows for update.

Outcomes:

- zero candidates: continue;
- one candidate: validate exact compatibility and return it;
- more than one candidate: fail closed as ambiguous.

A currency-less plan may reuse a provider symbol only when exactly one listing exists across
all currencies. It must not choose arbitrarily.

### Exact listing compatibility

The listing must satisfy:

```text
listing.provider = plan.provider
listing.provider_symbol = plan.provider_symbol
listing.symbol = plan.symbol
listing.exchange = plan.exchange
```

When the plan has a listing currency hint:

```text
listing.currency = plan.listing_currency_hint
```

The linked asset must satisfy:

- if both plan and asset ISIN are non-null, they are equal;
- if plan asset type is not `other`, existing asset type equals plan asset type;
- if plan asset type is `other`, an existing more specific type is acceptable;
- if `asset_currency_hint` is present, existing asset currency equals it;
- Anycoin plans always resolve to an existing crypto asset.

A plan ISIN may match an existing null ISIN under exact provider identity. Do not update the
asset to add the ISIN in B2.

Any contradiction fails closed. Never modify canonical history to make it match.

### Phase 2 – ISIN asset reuse

Run only when no exact provider listing exists and plan ISIN is present.

Query all assets with exact canonical ISIN and lock them for update.

Outcomes:

- zero assets: continue to creation;
- exactly one asset: validate compatibility;
- more than one asset: fail closed, even if only one appears otherwise compatible.

ISIN asset compatibility:

- plan ISIN equals asset ISIN;
- plan asset type `other` may accept an existing specific type;
- otherwise asset type must equal plan asset type;
- when `asset_currency_hint` is present, asset currency must equal it.

Asset symbol equality is not required for ISIN reuse because provider listing symbols can
differ. The new listing still uses the B1 plan symbol/provider symbol.

After selecting the asset, create a listing only when listing creation evidence is
sufficient and no conflicting listing identity exists.

### Phase 3 – new asset/listing pair

Run only when:

- no exact provider listing exists;
- no ISIN asset exists;
- listing creation evidence is sufficient.

Create:

```text
AssetModel
  id = new repository-standard string UUID
  symbol = plan.symbol
  isin = plan.isin
  name = plan.name
  asset_type = plan.asset_type
  currency = plan.asset_currency_hint
  updated_at = current naive UTC timestamp

AssetListingModel
  id = new repository-standard string UUID
  asset_id = new asset ID
  symbol = plan.symbol
  exchange = plan.exchange
  mic = null
  currency = plan.listing_currency_hint
  country = null
  provider = plan.provider
  provider_symbol = plan.provider_symbol
  is_primary = false
  updated_at = same current naive UTC timestamp
```

Do not create an alias.

Do not search or merge by global `Asset.symbol` before creation.

## Sufficient creation evidence

Creating any listing requires both:

```text
listing_currency_hint is non-null/non-blank
asset_currency_hint is non-null/non-blank
```

This permits:

- Trading212 buy/sell with explicit listing currency;
- Anycoin crypto trades/transfers/rewards with symbol currency;
- other B1 plans carrying explicit price/listing currency evidence.

This rejects creation for under-specified plans such as:

- dividend with no existing provider listing;
- non-crypto transfer/reward with no listing currency evidence.

The resolver may still reuse an already existing exact provider listing for those plans.

No fallback from payout currency, asset name, ISIN prefix or free text is allowed.

## Listing conflict checks before creation

Before adding a listing, query and lock both inherited unique identities:

```text
provider + provider_symbol + listing_currency
symbol + exchange + listing_currency
```

Expected state after provider/ISIN locks:

- neither identity exists: create listing;
- both identities reference the same exact compatible listing: return it;
- either identity references another listing or another asset: fail closed;
- multiple rows for a query: fail closed.

Do not mutate an existing listing with null/different provider metadata.

## Caller-owned transaction

The resolver may:

- execute advisory locks and `SELECT ... FOR UPDATE`;
- add one asset and one listing;
- flush once after creation;
- return existing or newly added models.

It must not:

- call `commit()`;
- call `rollback()`;
- begin an independent nested transaction to hide errors;
- change import rows or batches;
- create logs per resolution;
- catch and silently retry integrity errors.

A caller rollback must remove every newly created asset/listing.

## Idempotence

For the same plan:

1. first committed call may create one asset/listing pair;
2. a later independent-session call must resolve the exact provider listing;
3. IDs and canonical fields remain unchanged;
4. global counts remain one asset and one listing;
5. no update statement is issued.

For a unique existing ISIN asset without the provider listing:

1. first committed call creates only the listing;
2. replay returns the same asset and listing;
3. asset count remains unchanged.

## Concurrency

Real PostgreSQL tests must prove:

### Same provider identity

Two independent sessions resolve the same previously absent plan concurrently.

Expected:

- one transaction creates the asset/listing;
- the other waits on the advisory lock and then resolves the committed listing;
- exactly one asset and one listing remain;
- both callers receive the same IDs;
- no unique-constraint exception escapes.

### Same ISIN, different provider symbols

Two independent sessions use the same ISIN but different provider symbols/listings.

Expected:

- the ISIN lock serializes asset selection/creation;
- exactly one asset remains;
- two compatible listings are created;
- each listing has its own exact provider symbol;
- no duplicate ISIN asset is created.

Use explicit synchronization so the test proves overlap rather than sequential calls.

## Ambiguity and corruption policy

Use generic:

```text
ImportPostStateError
code = import_post_state_invalid
status = 409
message = The import batch is not available for posting.
```

Do not expose symbols, ISINs, provider symbols, listing currencies or database IDs in the
error message.

Fail closed for at least:

- multiple provider listings when currency hint is absent;
- multiple assets with the same ISIN;
- exact provider listing with symbol/exchange/currency conflict;
- exact provider listing linked to incompatible asset;
- ISIN asset with incompatible type/currency;
- provider unique identity and market unique identity pointing to different listings;
- missing creation currency evidence;
- unsupported provider/exchange pair;
- blank identity values;
- Anycoin resolving to non-crypto.
