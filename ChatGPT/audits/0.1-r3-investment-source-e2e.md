# 0.1-R3 investment-source fixture E2E audit

## Verdict

**PASS**

The committed Trading212 and Anycoin fixtures pass the public Python staged
import API through canonical investment evidence, holdings, coordinated
snapshots, and both exact read models. Production semantics, frontend import
code, generated OpenAPI, schema, migrations, packages, and workflows are
unchanged.

## Scope and fixtures

The four committed CSV files are fully synthetic and preserve only supported
provider export shapes:

- Trading212 `activity.csv`: deposit, buy, and tax-exempt dividend.
- Trading212 `activity_issues.csv`: unsupported/linked cash actions, missing
  fields, invalid Decimal, incomplete conversion, invalid fee currency, blank
  row, and column mismatch.
- Trading212 zero-fee evidence uses the real provider headers
  `Currency conversion fee` and `Currency (Currency conversion fee)`.
- Anycoin `history.csv`: one grouped EUR payment, BTC fill, and EUR refund.
- Anycoin `history_issues.csv`: incomplete and contradictory groups,
  multi-currency groups, `zero_group_net` from nonzero constituent rows,
  conflicting identity, `unsupported_anycoin_fiat_transfer`,
  `invalid_anycoin_row`, blank row, and column mismatch. Every fixture row uses
  an exact supported provider type: `deposit`, `withdrawal`, `trade payment`,
  `trade fill`, or `trade refund`.

Identifiers use `T212-FAKE-*`, `AC-FAKE-*`, `TEST00000001`, `TSTETF`, and
`BTC`. No personal data, real account/portfolio/order identity, address,
credential, or user-owned security identifier is present.

## Parser and normalization evidence

`PARSER_REGISTRY` continues to map Trading212 and Anycoin to the generic strict
CSV parser. Trading212 then uses its existing schema-version-2 normalizer;
Anycoin uses its existing deterministic batch grouping.

Trading212 main counts are 3 parsed, 3 normalized, 3 unique, 3 classified, and
3 imported. The exact canonical events are one cash deposit, one buy, and one
dividend. Their provider IDs, event dates, source lineage, asset identity,
signed cash directions, quantity `2`, price `100 EUR`, total `200 EUR`, and
dividend `5.25 EUR` are asserted. No canonical `Transaction` is created.

Anycoin main counts are 3 parsed, 1 normalized canonical anchor plus 2 skipped
members, 1 unique, 1 classified, 1 imported, and 2 skipped. The fill is the
deterministic anchor. Payment and refund rows retain exact `anchor_row_id`,
member role, and null canonical IDs. The event is one buy with quantity
`0.01 BTC`, total `490 EUR`, derived price `49000 EUR`, incoming asset movement,
and outgoing cash movement. No canonical `Transaction` is created.

Every physical issue row remains persisted failed or review evidence. Issue
fixtures create no event, movement, holding, or transaction. Assertions bind
the zero-net order and the standalone fiat/invalid source rows to their exact
error codes, rather than checking only aggregate error-code presence.

## Replay, isolation, and corruption evidence

An exact same-content upload is rejected at batch creation by the existing
checksum contract, including under a renamed filename. BOM and reordered-row
variants reach row deduplication and create no additional event, movement set,
or holding. Replaying `/post` retains exact canonical IDs. The same provider
identities on another account create an independent account-scoped canonical
set.

The required PostgreSQL matrix also covers concurrent deduplication,
rollback/retry, posting-intent tampering, persisted event and movement
corruption, holding corruption, and listing/price relation validation. The
R3 tests do not create replacement evidence when a fail-closed check rejects
state.

## Holdings, prices, and snapshots

Trading212 holdings are exactly `2 TSTETF` at cost basis `200 EUR`. Explicit
test price evidence of `110 EUR` produces cash `805.25 EUR`, investments
`220 EUR`, total `1025.25 EUR`, net deposits `1000 EUR`, and unrealized P/L
`20 EUR`.

Anycoin holdings are exactly `0.01 BTC` at cost basis `490 EUR`. Explicit test
price evidence of `60000 EUR` produces cash `-490 EUR`, investments `600 EUR`,
total `110 EUR`, net deposits `0 EUR`, and unrealized P/L `110 EUR`.

The price rows are deterministic persisted test evidence only. They are not a
price-provider implementation, provider refresh, external HTTP call, live
price, buy-price fallback, or completion of R5. Without a current price, import
posting succeeds but coordinated refresh reports unavailable and creates
neither `AccountSnapshot` nor `NetWorthSnapshot`. After the exact price row is
inserted, refresh succeeds. No `ExchangeRate` row is inserted and snapshot
lineage contains empty snapshot and historical rate ID sets.

## Exact read parity

For each source, the five-field manifest is copied only from the successful
refresh response and remains unchanged through:

- `POST /api/v1/portfolio/snapshot`
- `POST /api/v1/dashboard/snapshot`

Both reads match the manifest timestamp, granularity, EUR currency,
calculation version, account set, and snapshot ID. Portfolio and dashboard
match on total, cash, investments, liabilities, position count, and account
count. Persisted holdings match portfolio positions and dashboard top
positions. Liabilities are zero. No latest lookup, account discovery, query
selector, caller-added account, FX fallback, or frontend aggregation is part
of the evidence.
