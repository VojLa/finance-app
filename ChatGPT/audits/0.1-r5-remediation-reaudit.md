## Exact identity and inventory

CoinGecko onboarding and the CoinGecko provider share
`parse_coingecko_asset_identity`. It permits only a single exact ASCII ID for
a crypto Asset and rejects whitespace repair, control characters, list/URL
delimiters, and invented mappings. `bitcoin` is supplied explicitly in the
acceptance; it is not derived from `BTC`.

Twelve Data onboarding and the provider share
`parse_twelve_data_quote_identity`. It accepts only byte-exact canonical JSON
with ordered keys `symbol`, `mic_code`, and only for stock, ETF, bond,
commodity, or other Assets. Crypto and cash are rejected. There is no broker
symbol, ISIN, Listing MIC, exchange, or first-alias fallback.

The inventory uses `REPEATABLE READ, READ ONLY`, selects only nonzero Holdings
whose Asset type is compatible with the chosen provider, excludes already
resolved Assets, and deterministically orders Assets and Listings. Listings
are context only; no external ID is recommended. PostgreSQL acceptance covers
zero Holdings, resolved Assets, CoinGecko exclusion of stock, Twelve Data
exclusion of crypto/cash, and deterministic multiple-Listing order.

## Writer identity, state, and retry

The immutable identities are:

```text
(asset_id, provider)
(provider, external_id)
deterministic alias ID
```

The deterministic ID contract is UUIDv5 namespace
`b1d66d76-35f0-4db0-b1d9-0f5452d4a27c` with payload:

```text
asset_id + NUL + provider.value
```

One writer-owned `SERIALIZABLE` transaction attempt acquires canonical sorted
advisory locks for both logical identities. Tests cover:

- create;
- exact replay without changing `createdAt`;
- historical non-deterministic ID replay;
- same Asset/provider with a different external identity;
- provider/external identity owned by another Asset;
- multiple same Asset/provider rows;
- deterministic-ID collision;
- historical replay plus foreign deterministic-ID collision;
- malformed/corrupt physical state;
- flush/reload failure;
- same-command concurrency: one created, one replayed, one physical row;
- conflicting-command concurrency: one winner, one conflict, no partial state.

Conflicts and corruption cause no update, delete, repoint, or compensating
insert, and leave the session idle. Retry is limited to three complete
transaction attempts for SQLSTATE `40001`, `40P01`, and `23505`.
Validation/conflict/state failures and non-retryable SQL errors are not
retried.
