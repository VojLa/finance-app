# 0.1-R10 final scope re-audit

## Verdict

**VERSION 0.1 FINAL VERDICT: NOT READY**

- Exact base: `65c79e16dbe05c38f05b4fe64dc28a5a96678dd3`
- Branch: `audit/0.1-r10-final-scope`
Final audited tree: the commit containing this report, recorded exactly by the
draft PR `headRefOid`.

The strict D1/D2 financial engine is implemented, but the active authenticated
portfolio and dashboard HTTP endpoints cannot use it. Principal resolution and
the current-value service share one cached SQLAlchemy session. The principal
lookup opens a read transaction; the D1 selector requires an idle session so it
can establish its own validated transaction boundary. Both endpoints therefore
return safe `409 current_value_unavailable` even with a complete valid baseline.

Required remediation:

**0.1-R10-E1 — current-value authenticated session/transaction composition**

R10-E1 must close or isolate the principal-resolution transaction without
weakening D1 consistency, and add authenticated PostgreSQL acceptance for both
current endpoints. This audit does not change production behavior.

## Release blockers and technical debt

### Release blocker

The real FastAPI dependency graph is:

```text
Bearer JWT
  -> get_current_principal(get_db_session)
  -> SELECT User (session transaction begins)
  -> current endpoint(CurrentValueService using cached get_db_session)
  -> DailySnapshotBaselineService.select_latest_valid()
  -> rejects non-idle session
  -> safe 409 current_value_unavailable
```

`backend/python/tests/test_r10_final_scope_reaudit_integration.py` proves all of
the following against PostgreSQL:

1. valid D1 evidence exists;
2. the production D2 service returns exact current finance with an idle session;
3. the real authenticated `/api/v1/portfolio/current` returns 409;
4. the real authenticated `/api/v1/dashboard/current` returns 409;
5. the error is safe and contains a request ID;
6. neither read mutates AccountSnapshot or NetWorthSnapshot row counts.

### Non-blocking technical debt

- Several older PostgreSQL integration files still encode pre-R10-B1 or
  pre-market-orchestration assumptions and fail when run as one broad ad hoc
  set. The current release-contract subset is zero-skip, but those historical
  tests should be aligned or retired separately.
- Generic full-suite PostgreSQL tests remain environment-gated; dedicated
  release acceptance is run explicitly.
- `npm audit` reports 12 dependency findings: 1 low, 1 moderate, 9 high and 1
  critical. They include current Next.js/NextAuth development baseline findings.
  No automatic or breaking update was attempted. For this internal architecture

### Explicitly out of scope

Rust production execution, budgets, advanced reporting, workers, deployment and
production scaling are not Version 0.1 blockers.

## Architecture ownership

The active intended architecture is:

```text
browser
  -> Next.js UI + NextAuth + thin same-origin adapters
  -> fresh server-only internal JWT
  -> Python FastAPI
  -> PostgreSQL
```

Python owns accounts, imports, canonical posting and lineage, Holdings, market
evidence, persisted snapshots, D1 daily baselines, D2 current projection,
portfolio, dashboard, and history. Alembic owns migrations; Prisma is a schema
compatibility/client layer and is not used by the active finance paths.

Registered legacy account/import/portfolio/dashboard/rates routes remain in the
repository. Source and browser cutover guards classify them as compatibility or
test-only for the main finance path. The active portfolio/dashboard adapters do
not call `/api/rates`, Prisma finance, the legacy finance endpoints, or
`snapshot-refresh/recalculate`. No active Next finance calculation was found.

The architecture ownership is correct, but the Python session composition bug
makes the main current HTTP boundary unusable, so ownership alone cannot earn a
release PASS.

## Authentication and accounts

NextAuth owns the browser session. Thin routes derive the exact user ID and mint
a fresh short-lived internal JWT without exposing it to the browser. Python
validates the principal and persisted account membership. Caller-controlled
financial user IDs, account sets, baselines, snapshot IDs, currencies, price/FX
evidence, revisions and calculation versions are not accepted.

Python supports create/list/update/archive/restore and validates all Version 0.1
account types: bank, cash, savings, broker, exchange, crypto wallet, credit card,
loan and mortgage. Account currency is required. Foreign and archived account
nondisclosure passes. D1 invalidates a baseline when account set, archive state,
account type/currency or user base currency drifts.

Authentication itself is valid; its transaction side effect on the current
endpoint session is the blocker described above.

## Imports and supported sources

The active path is:

```text
browser upload
  -> thin Next adapter
  -> Python create/upload/parse/normalize/deduplicate/classify/canonical-post
  -> one request-level multi-file finalization
  -> canonical lineage / Holdings / coordinated snapshot phases
```

Raiffeisenbank, Trading212 and Anycoin have source-format fixture-derived Python
E2E evidence. The focused PostgreSQL matrix covers parsing, normalization,
classification, posting and resulting canonical finance. Trading212 and Anycoin
use exact operator-owned provider aliases. Unsupported rows remain batch-linked
parse/review issues; malformed uploads fail safely.

R10-A's multi-file coordinator preserves per-file ImportBatch rows but performs
one logical finalization. Duplicate and zero-import outcomes converge without
uncontrolled finance. Canonical post, finalization failure and retry semantics
are persisted and truthful.

The clean R8 scenario was recreated through the official migration/bootstrap
path and passed after two audit-test-only corrections for current primary versus
companion snapshot selection and the current `aggregatePositions` response key.
It proves the three-source persisted finance graph, but cannot prove the active
authenticated D2 read because that boundary is blocked.

## Ledger, lineage, Holdings and cash

Transactions preserve account, signed amount, currency, classification and
financial timestamp. InvestmentEvent plus its exact InvestmentMovement set is
one canonical root. LiabilityBalance is replacement-point evidence.

`AccountCanonicalState` and append-only `AccountCanonicalChange` allocate one
commit-ordered account revision under lock. Exact replay consumes no revision;
rollback exposes neither root nor journal state. Investment writes advance the
investment revision while Holding rebuild atomically stamps the exact
`holdingRevision`.

Holdings are persisted full-history projections covering buys, sells, partial
and full close, transfers, fees/dividends, exact quantities and cost basis.
Native cash remains an exact signed per-currency breakdown for bank and
investment cash legs. No synthetic zero or forced CZK normalization is used.

## Prices and FX

Python owns provider composition:

- Twelve Data for exact listing identities;
- CoinGecko for exact crypto IDs;
- CNB for authoritative foreign-to-CZK observations.

PriceSnapshot and ExchangeRate are append-only persisted market evidence.
Missing, stale, future, conflicting or wrong-identity evidence fails closed.
No frontend provider lookup or `/api/rates` fallback is active.

Current same-currency conversion is identity. Foreign-to-CZK is direct;
CZK-to-foreign and foreign-to-foreign presentation use exact persisted CNB legs
through the R10-B1 CZK pivot without a synthetic cross-rate row or intermediate
rounding. Historical deposits, realized P/L, fees and taxes retain event-date FX;
current cash, investments and liabilities use current-as-of FX.

## Persisted snapshots and D1 baseline

The persisted engine retains AccountSnapshot, AccountSnapshotItem and
NetWorthSnapshot with exact Decimal, market lineage, breakdowns, replay and
concurrency contracts. Mixed-currency accounts have primary User.baseCurrency
and presentation Account.currency snapshots calculated from one canonical state;
same-currency accounts reuse one identity. NetWorth consumes primaries only.

D1 physically persists:

- `AccountCanonicalState`;
- `AccountCanonicalChange`;
- `AccountSnapshotCanonicalBoundary`;
- `DailySnapshotBaseline`;
- `DailySnapshotBaselineAccount`.

The manifest proves exact active account set, primary/presentation identities,
canonical cutoff, Holding watermark, liability lineage, calculation version and
NetWorth identity. Backfilled post-cutoff roots invalidate the newest baseline;
there is no older fallback. Dedicated D1 PostgreSQL coverage is included in the
zero-skip release subset.

## D2 current value and persistence

The implemented service contract is:

```text
server-owned minute-aligned asOf
  -> newest valid D1 daily baseline
  -> exact post-cutoff canonical roots through asOf
  -> current persisted price/FX evidence
  -> one reconstructed account state
  -> User.baseCurrency primary + Account.currency presentation
  -> ephemeral current portfolio
  -> dashboard projection from the same state
```

Cash advances baseline native balances with forward Transactions. Investments
advance daily AccountSnapshot items with forward events/movements and the same
canonical quantity/cost policy; production does not use current Holding or a
full-history replay as a shortcut. Historical cumulative metrics add event-date
FX deltas; unrealized P/L uses reconstructed state and current market evidence.
Liability uses the latest exact eligible replacement observation.

The complete-recompute oracle passes for controlled equivalent datasets. Normal
service reads do not mutate AccountSnapshot, AccountSnapshotItem, boundaries,
NetWorthSnapshot, DailySnapshotBaseline, canonical finance or Holding rows; only
approved market evidence may persist. History remains persisted NetWorthSnapshot
history without an ephemeral fake current point.

The engine is therefore physically implemented. The active authenticated HTTP
composition cannot reach it successfully, so the authoritative current-value
requirement is not delivered end to end.

## Portfolio, dashboard and history

Active Next routes call Python `/api/v1/portfolio/current` and
`/api/v1/dashboard/current`; a new frontend source guard proves the old minute
refresh is absent from those workflow functions. Runtime validators require
canonical MONEY/quantity/percentage/currency/timestamp strings and exact account
sets. The browser does no FX, financial aggregation or reconstruction.

The portfolio model supports aggregate User.baseCurrency finance, local account
selection in Account.currency, cash/net-deposit breakdowns, total, investment
value/cost basis, positions and realized/unrealized P/L. Dashboard derives from
the same current portfolio state and provides base-currency summary/allocation/
top positions plus account-currency cards and exact deposited values.

History is a separate Python read of persisted NetWorthSnapshot with stable
ordering/range behavior. It gets no synthetic D2 current point.

All these projection and frontend tests pass. The current portfolio/dashboard
pages still cannot receive successful finance because both authenticated Python
current endpoints return 409.

## Security, errors and observability

Foreign principal and archived account paths fail without disclosure. Upload
security covers traversal, malformed and oversized content and checksum
mismatch. Browser callers cannot select financial lineage or provider identity.

Missing/corrupt/backfilled baseline, configuration drift, missing companion,
bad market evidence, corrupt canonical roots and replay mismatch fail closed.
The blocker itself returns a stable safe envelope rather than SQL or traceback.
Import status, parse issues and stage errors are queryable from Python.
