# 0.1-R5 final audit

## Verdict

**R5 FINAL VERDICT: NOT READY**

Audited base: `f67fd8615e423c7af851522e623e7db32481427e`

The coordinated market-evidence implementation, both public boundaries, the
provider adapters, two-phase persistence, replay, concurrency, and public
contracts pass their audited evidence. Release readiness is nevertheless
blocked by `R5-ALIAS-01`: there is no production-supported workflow that can
create or reconcile the exact CoinGecko or Twelve Data alias required by those
flows. Existing provider E2E setup inserts aliases directly with test-only ORM
helpers. That is valid provider-flow setup and invalid onboarding proof.

The detailed matrix contains 40 `PASS`, 0 `PARTIAL`, 1 `MISSING`, 0
`CONTRADICTED`, and 0 `OUT_OF_SCOPE` rows. The `MISSING` row is release
blocking and is not ignored.

## Scope and method

This PR is an audit step. It adds release-audit tests, makes existing
PostgreSQL provider-flow test cleanup independent, creates this report and the
R5 requirement matrix, and records the evidence-based remediation status. It
does not change production code, endpoints, providers, financial logic,
frontend behavior, schema, migrations, retry, cache, scheduler, worker, or
background-task behavior.

Evidence came from:

- production-source inventory with `rg` and AST guards;
- focused unit and static audit tests;
- clean PostgreSQL 16.10 public endpoint and coordinator acceptance using
  mocked HTTP transports;
- existing provider parser/transport failure tests;
- OpenAPI/generated-client drift gates and full repository gates.

## Transaction ordering and persistence

The coordinator and both boundaries enforce:

```text
idle session
-> planner read transaction
-> idle session
-> provider HTTP
-> atomic market writer transaction and commit
-> idle session
-> snapshot executor transaction and commit
-> idle session
-> boundary audit/response
```

The import path additionally proves that canonical posting commits before a
conditional Holdings rebuild commit, and both precede the market stage.
Provider mocks assert that HTTP runs while `session.in_transaction()` is
false. Known dependency leaks are rolled back and become runtime state errors;
the next dependency and audit write do not run on the damaged session.

Market and snapshots are intentionally separate committed phases. Market
failure prevents snapshot execution. Snapshot failure after a successful
market writer preserves valid append-only PriceSnapshot/ExchangeRate rows and
does not compensate them. Empty market requirements continue to snapshot
execution. No coordinator creates retry, cache, task, scheduler, queue, or
worker behavior.

## Provider identity

CoinGecko accepts exactly one persisted
`AssetAlias(provider=coingecko).externalId` as its CoinGecko ID. Production
contains no symbol inference, name lookup, `/coins/list`, first-alias fallback,
or hard-coded BTC mapping.

Twelve Data accepts only canonical alias JSON such as
`{"symbol":"AAPL","mic_code":"XNAS"}`. It does not fall back to Trading212
symbol, ISIN, Listing MIC, exchange, country, or noncanonical JSON.

CNB supports only direct `foreign currency -> CZK` evidence. There is no
inverse, cross-rate, foreign-to-non-CZK, ECB, or manual fallback.

Provider responses cannot change Asset or Listing identity. Strict parsers
reject wrong symbol, MIC, coin identity, currency, timestamps, stale evidence,
and malformed or unrepresentable values.

## Alias-onboarding hard gate

The required inventory:

```text
rg -n \
  "AssetAliasModel\\(|AssetAliasRepository|AssetAlias.*Service|alias.*reconcile" \
  backend/python/app
```

finds only the `AssetAliasModel` definition in production. AST inspection finds
no production `AssetAliasModel(...)` construction and no alias writer,
creation service, repository writer, reconciliation workflow, or internal
administrative API.

Direct `AssetAliasModel(...)` calls exist in test setup, including the
CoinGecko/Twelve Data support modules and market-backed manual/import
integration tests. Those calls establish variant A—the provider flow with an
already persisted exact alias. They cannot satisfy variant B—the production
onboarding flow starting without an alias.

Public no-alias variants prove:

- the manual endpoint fails before all provider HTTP and creates no market or
  snapshot graph;
- a fully staged Trading212/Anycoin import preserves canonical posting and
  Holdings, returns `unavailable`, performs zero provider calls, and creates
  zero snapshots;
- no timestamp, ticker, broker symbol, ISIN, MIC, name, or BTC mapping is used
  to repair the absence.

Therefore:

```text

R5 FINAL VERDICT = NOT READY
```

## Clean PostgreSQL acceptance

The dedicated database was initialized from the repository baseline and
upgraded to Alembic head `3h0001twdata`. PostgreSQL reported version `16.10`.
All provider network access used `httpx.MockTransport`.

### Manual input

`test_production_mixed_provider_endpoint_e2e_and_replay` calls only public
`POST /api/v1/snapshot-refresh/recalculate`. With exact persisted aliases it
proves exact Twelve Data symbol/MIC, exact CoinGecko ID, exact CNB dates, HTTP
outside transactions, market rows before snapshots, selected price and
historical/snapshot FX IDs, AccountSnapshot/NetWorthSnapshot lineage,
portfolio/dashboard parity, and deterministic replay. The response contains
no market metadata.

The separate alias-failure test starts with missing or ambiguous identity and
proves fail-before-HTTP behavior. It does not insert an alias to conceal the
onboarding blocker.

### Raiffeisenbank

The staged cash-only CZK import executes create, upload, parse, normalize,
deduplicate, classify, and post through public routes. Its empty market plan
makes no price or FX request, creates AccountSnapshot and NetWorthSnapshot,
matches exact cash and portfolio/dashboard reads, and replays without new
physical rows. No market or snapshot row is directly inserted by the test.

### Trading212 and Anycoin

Provider-flow variants use explicit test setup for exact Twelve Data and
CoinGecko aliases. The staged imports create canonical events and movements,
rebuild exact Holdings, request the exact alias identities through mocked
HTTP, persist market evidence before snapshots, verify exact lineage and
reads, and replay without duplicates.

The no-alias variants use only the production staged import workflow after
seeding Asset/Listing identity. Post-processing returns `unavailable` before
HTTP. Posting and Holdings remain; PriceSnapshot, ExchangeRate,
AccountSnapshot, and NetWorthSnapshot case-local row counts remain zero. This
is the evidence for the release blocker, not a provider-flow failure.

### Test isolation

The R5-B3A committed E2E graphs originally retained globally unique
`AAPL/XNAS` and `bitcoin` aliases after a test completed. When all prescribed
acceptance files shared one clean database, later independent import cases
correctly hit the database uniqueness constraint. The audit adds test-only
graph cleanup after each R5-B3A case. This changes no assertion or production
behavior and allows the combined acceptance command to prove isolation.

- Principal identity comes from authentication, never request payload.
- Foreign account/import access preserves scoped nondisclosure.
- Import files cannot supply a hidden provider alias field.
- Provider credentials remain server-side secret settings and headers.
- Base URLs reject embedded credentials/query/fragment configuration.
- Exceptions, responses, and import audits contain no key, URL, raw provider
