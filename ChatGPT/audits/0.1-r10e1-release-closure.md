## E1 root cause and exact fix

Before E1:

```text
verified JWT
  -> request-scoped AsyncSession
  -> get_current_principal SELECT User
  -> SQLAlchemy autobegin remains active
  -> same session injected into CurrentValueService
  -> D1 selector rejects non-idle session
  -> safe 409 current_value_unavailable
```

After E1:

```text
verified JWT (before database dependency)
  -> request-scoped AsyncSession is required idle
  -> persisted User lookup owns one implicit read transaction
  -> ORM identity values copied into AuthenticatedPrincipal
  -> explicit read commit
  -> session is verified idle
  -> CurrentValueService owns D1 planning / market / final read boundaries
  -> real portfolio and dashboard endpoints return 200
```

`get_current_principal()` now implements the repository's established explicit
commit convention for an authentication read. It rejects an unexpected
pre-existing transaction without querying, committing or rolling it back. A
missing user rolls back only the lookup transaction and preserves
`invalid_session_token`. SQLAlchemy lookup/commit failures become the existing
safe `authentication_unavailable` family. No ORM User object escapes; the
principal contains only copied user ID, email, name and token session ID.

No second database session or engine was added. D1's idle-session precondition,
D2 REPEATABLE READ/READ ONLY ownership and fail-closed behavior are unchanged.

## Authentication behavior

- missing bearer token: unchanged `401 authentication_required`;
- malformed, bad signature/issuer/audience or expired JWT: rejected before a
  database dependency is opened;
- missing persisted subject: `401 invalid_session_token` after closing the auth
  read;
- valid persisted user: immutable AuthenticatedPrincipal and idle session;
- unexpected caller-owned transaction: safe `503 authentication_unavailable`
  without destroying caller state.

Unit evidence asserts `session.in_transaction() is False` after successful
principal resolution and observes no database scalar call for invalid token
verification.

### Mixed currency

The authenticated mixed scenario uses User.baseCurrency CZK, Account.currency
EUR, a liability replacement from EUR 100 to EUR 75, and exact persisted
EUR-to-CZK current evidence. Both service dependencies observe the shared
session idle after authentication.

- account/card authority: EUR 75;
- account output currency equals Account.currency;
- no primary relabelling or frontend conversion occurs.

The same response exposes the remaining blocker: its global MONEY string is
`1800.00000000000000`, which fails the active six-decimal browser MONEY regex.
The account identity value serializes as `75.000000` because it requires no
composed conversion.
