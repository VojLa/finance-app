# 0.1-R10-B account-currency presentation audit

## Verdict

**R10-B VERDICT: NOT READY**

The representability gate fails before any public API or frontend change. The
current production snapshot graph cannot produce every required account-level
value in `Account.currency` without either inventing a foreign-to-foreign FX
conversion or reading evidence that is not physically persisted.

This is an evidence-only result. R10-B changes no production Python, frontend,
OpenAPI, generated TypeScript, schema, migration, provider, snapshot formula,
history contract, or R10-A behavior.

Base: `5e9c82ddbd3da0590e3e82545cb52a649d9b28d5`

## Scope

Authoritative requirement:

> Each account has a main currency. Account-level portfolio and dashboard
> views display their primary values in the account's main currency.

The aggregate portfolio, global dashboard, NetWorthSnapshot, and history remain
owned by `User.baseCurrency`. R10-C deposited presentation and R10-D current
value semantics are not part of this audit.

## Current production path

The current path is:

```text
Account.currency
User.baseCurrency
        |
        v
AccountSnapshotProjectionInput(
    account_currency=Account.currency,
    output_currency=User.baseCurrency,
)
        |
        v
AccountSnapshot scalars in output currency
        |
        v
portfolio account.summary in output currency
        |
        +--> selected portfolio account formatted as output currency
        |
        +--> dashboard account card formatted as output currency
```

`Account.currency` is validated as account metadata and constrains the native
currency of a liability balance. `build_account_snapshot_projection()` returns
`currency=output_currency`; every persisted scalar and every
`AccountSnapshotItem.value/costBasis` is converted directly to that output
currency.

The current UI therefore does not relabel a CZK number as EUR: it explicitly
formats account summaries with the snapshot output currency. That behavior is
financially truthful but does not satisfy the account-currency presentation
requirement.

## Physical evidence inventory

`AccountSnapshot` stores output/user-base scalars and selected native
breakdowns. A native breakdown is evidence in each original currency; it is
not an account-currency scalar.

| Account-level value   | Output scalar         | Native breakdown                            | Direct account-currency scalar | Exact general reconstruction from current persisted evidence |
| --------------------- | --------------------- | ------------------------------------------- | ------------------------------ | ------------------------------------------------------------ |
| cash                  | `cashValue`           | `cashValueByCurrency`                       | no                             | no for mixed native currencies                               |
| investment value      | `investmentValue`     | `investmentValueByCurrency`                 | no                             | no for foreign native positions                              |
| investment cost basis | `investmentCostBasis` | `investmentCostBasisByCurrency`             | no                             | no for foreign native cost currency                          |
| liabilities           | `liabilitiesValue`    | calculated and validated, but not persisted | no                             | no                                                           |
| total                 | `totalValue`          | no complete total breakdown                 | no                             | no                                                           |
| net deposits          | `netDepositsValue`    | `netDepositsByCurrency`                     | no                             | no for mixed currencies                                      |
| realized P/L          | `realizedPnlValue`    | `realizedPnlByCurrency`                     | no                             | no for mixed currencies                                      |
| unrealized P/L        | `unrealizedPnlValue`  | nullable `unrealizedPnlByCurrency`          | no                             | no when native evidence is absent or mixed                   |
| fees                  | `feesValue`           | `feesByCurrency`                            | no                             | no for mixed currencies                                      |
| taxes                 | `taxesValue`          | `taxesByCurrency`                           | no                             | no for mixed currencies                                      |

`AccountSnapshot.exchangeRates` stores exact snapshot rate values only for
rates consumed by the output-currency valuation. Historical metric evidence
stores historical rate IDs rather than a complete second valuation. The
portfolio reader currently decodes only `cashValueByCurrency` and
`netDepositsByCurrency`; it does not read snapshot FX or the other native
breakdowns.

## Representability scenarios

### Account A — CZK cash, user output CZK

PASS. The native and output currencies are identical. No FX is needed and the
persisted scalar is already an exact account-currency scalar.

### Account B — EUR-native broker, user output CZK

PARTIAL. The writer persists exact EUR native investment/cost evidence and
CZK scalars using direct `EUR -> CZK`. The physical contract still has no
explicit EUR presentation summary, but a restricted all-EUR case contains
enough native components for some values.

This restricted case is not sufficient to establish the general contract.

### Account C — EUR broker with a USD position, user output CZK

BLOCKER. Production output valuation consumes direct `USD -> CZK` and, where
needed, `EUR -> CZK`. An EUR presentation would require direct `USD -> EUR`
evidence. Deriving it from the two CZK rates would be a cross/inverse FX
algorithm, which R10-B explicitly forbids.

The production ČNB adapter supports only `foreign currency -> CZK`. It cannot
produce the required direct foreign-to-EUR observation. The production
projection fails closed when asked to value the account in EUR with only the
currently selected CZK evidence.

### Account D — EUR liability, user output CZK

BLOCKER. Snapshot calculation produces and validates
`liabilities_value_by_currency=(EUR, native amount)` and converts the scalar
through direct `EUR -> CZK`. Persistence audits that breakdown but
`ExpectedAccountSnapshotRow`, `AccountSnapshotModel`, and the physical table
have no `liabilitiesValueByCurrency` field. The portfolio read cannot recover
the native liability amount from persisted AccountSnapshot evidence.

Dividing the CZK scalar by a rate at read time would be a new inverse
calculation and is forbidden.

## Executable evidence

`backend/python/tests/test_r10b_account_currency_representability.py` proves:

- same-currency cash is exactly representable;
- an EUR-native account still persists CZK output scalars;
- mixed USD/EUR native evidence contains only direct-to-CZK rates;
- requesting an EUR valuation without direct USD-to-EUR evidence fails closed;
- the liability native breakdown exists in calculation but not persistence;
- the portfolio read contract lacks the remaining native/FX evidence needed
  for a complete presentation summary.

`backend/python/tests/test_r10b_account_currency_representability_integration.py`
bootstraps PostgreSQL 16 and persists four production-projected AccountSnapshot
rows. It physically proves:

- Account A: `Account.currency=CZK`, `AccountSnapshot.currency=CZK`;
- Accounts B/C/D: `Account.currency=EUR`,
  `AccountSnapshot.currency=CZK`;
- Account C snapshot rates are only `EUR -> CZK` and `USD -> CZK`;
- no selected snapshot rate targets EUR;
- Account D stores the converted CZK liability scalar;
- the physical table has no `liabilitiesValueByCurrency` column.

## Public and frontend decision

No `AccountCurrencySummary` response is added. Adding the shape before all
values are representable would invite either missing fields, synthetic zeros,
native-currency dropping, or relabeling output values.

The selected portfolio account and dashboard account cards remain explicitly
formatted in the existing output currency. Aggregate portfolio/dashboard and
history behavior are unchanged. No frontend FX, Decimal-to-number conversion,
request-on-selection, live rate read, or legacy fallback is introduced.

## Smallest required backend remediation

Plan:

`0.1-R10-B1 — persisted account-currency valuation evidence and FX capability decision`

That step must define and implement, before R10-B resumes:

1. a complete immutable account-currency summary persisted at snapshot-write
   time, including liability native evidence and all required metrics;
2. exact selected direct native-to-account-currency FX evidence for every
   required component, or an explicit architecture decision authorizing a
   server-side deterministic derivation contract;
3. a production provider capability for required non-CZK targets if direct
   evidence remains mandatory;
4. replay, corruption, lineage, and PostgreSQL acceptance for the additional
   evidence without changing aggregate user-base semantics.

R10-B must not choose one of those financial contracts implicitly in a
presentation PR.
