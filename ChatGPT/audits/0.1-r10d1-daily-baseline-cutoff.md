## Physical schema

Five normalized server-only objects were added:

1. `AccountCanonicalState` — one row per Account, with `lastRevision`,
   `lastInvestmentRevision`, and nullable `holdingRevision`.
2. `AccountCanonicalChange` — append-only root metadata keyed by
   `(accountId, revision)` with a unique `(kind, entityId)` identity.
3. `AccountSnapshotCanonicalBoundary` — one immutable boundary per physical
   day AccountSnapshot.
4. `DailySnapshotBaseline` — one root per exact day NetWorthSnapshot.
5. `DailySnapshotBaselineAccount` — the complete active account set and exact
   primary/presentation snapshot lineage for a root.

Foreign keys, uniqueness, nonnegative/order checks, day-only granularity, and
selection indexes physically constrain the identities. Alembic remains the
owner; SQLAlchemy metadata and the Prisma compatibility mirror contain the same
36-table schema. No public endpoint or public response exposes these objects.

## Canonical revision contract

Canonical revision and financial timestamp are independent. Every new
Transaction, InvestmentEvent root, or LiabilityBalance locks its exact
`AccountCanonicalState`, validates replay identity, inserts the authoritative
finance root and one journal row, and advances state in the same transaction.
Revision numbers therefore describe committed inclusion order, not economic
date order.

- Transaction: one revision; `entityId = Transaction.id` and
  `financialTimestamp = Transaction.date`.
- InvestmentEvent plus its complete atomic InvestmentMovement set: one
  investment revision, never one revision per movement.
- LiabilityBalance: one revision; it remains a replacement observation and is
  not converted into an additive delta.
- Exact replay validates the physical journal and consumes no revision.
- Rollback exposes no root, journal row, or state update.
- BIGINT exhaustion and corrupt/missing state fail closed.

Concurrent writers serialize on the account-state row and obtain contiguous
committed revisions. An account insert trigger initializes the required zero
state, while code never silently invents a missing state during a finance
write.

## Historical upgrade policy

Pre-D1 roots did not retain their true commit order. Migration `3i0001d1base`
therefore assigns a deterministic migration-only total order per account by:

```text
createdAt -> canonical kind -> entity ID
```

The migration explicitly does not claim that this reconstructs historical
commit order. This is safe because no D1 baseline existed before the migration.
Finance values and root rows are unchanged. Existing Holdings receive no
unproved watermark, and existing AccountSnapshot/NetWorthSnapshot rows are not
promoted into D1 manifests.

## Holding watermark

Investment projection freshness is exact rather than timestamp-derived.
Holding rebuild locks canonical state, validates that the complete active
InvestmentEvent root set equals the investment journal, rebuilds Holdings from
the stable movement graph, atomically replaces the projection, and stamps:

```text
holdingRevision = lastInvestmentRevision
```

A later InvestmentEvent advances `lastInvestmentRevision` but not
`holdingRevision`, making the projection observably stale. A Transaction or
LiabilityBalance revision does not unnecessarily stale Holdings. A day
investment snapshot cannot acquire a valid D1 boundary until the investment
watermarks match.

## AccountSnapshot boundary

Day snapshot creation captures canonical state while holding the canonical
account lock. Primary and optional account-currency companion projections are
built from that one stable state and are persisted with their boundaries in
the AccountSnapshot writer transaction.

- Cash/bank/savings: canonical revision, no Holding or liability lineage.
- Broker/exchange/crypto wallet: canonical, investment, and Holding revisions;
  investment and Holding revisions must match.
- Credit card/loan/mortgage: canonical revision and exact selected
  LiabilityBalance ID.

For liability accounts, the writer also validates the selected physical
balance against its exact `liability_balance` journal row, including Account,
effective timestamp, creation timestamp, and inclusion revision. It does not
re-query a second latest liability after projection.

A mixed-currency primary and companion pair has the same Account, day
timestamp, source, granularity, calculation version, canonical cutoff, Holding
watermark, and selected liability identity. The snapshots retain distinct
currency-specific IDs when currencies differ. Existing rows missing a boundary
are not repaired with a current revision; immutable replay must match all
snapshot, item, and boundary evidence exactly.

## Daily baseline manifest

The day executor persists a manifest only after exact AccountSnapshot and
NetWorthSnapshot phases have succeeded. A graph without a manifest is not an
eligible D1 baseline, but retry can replay immutable snapshots and create or
replay the manifest without claiming that earlier committed phases rolled
back.

The root records the exact user, NetWorthSnapshot, timestamp, day granularity,
User base currency, calculation version, source, and creation time. Each child
records Account type/currency, exact primary and presentation IDs, canonical
cutoff, applicable investment/Holding watermark, and selected liability. The
exact current active supported account set must appear once and only once.
NetWorth lineage contains only primary identities; companions never increase
its account count.

Manifest persistence validates physical User, Account membership/configuration,
NetWorth and AccountSnapshot roots, day identity, matching boundaries, fresh
Holdings, and liability journal inclusion. Same-currency accounts reuse one
physical primary/presentation ID; mixed-currency accounts require distinct
identities with equal boundaries.

## Selector and invalidation

`DailySnapshotBaselineService.select_latest_valid(user_id, through)` is an
internal `REPEATABLE READ, READ ONLY` boundary. The caller cannot choose a
baseline ID, snapshot IDs, account set, revision, version, currency, liability,
Holding watermark, or change range.

It selects the newest persisted candidate at or before `through` and validates
it against current User base currency, active Account set, Account type,
Account currency, archive status, calculation version, physical snapshots,
boundaries, canonical state, contiguous journal, Holdings, and liability
roots. If that newest candidate is corrupt, incomplete, or configuration-stale
the selector fails. It never falls back to an older or nearest baseline.

For every journal root after an account cutoff:

```text
revision > baseline canonical revision
and financialTimestamp > baseline timestamp
    -> exact forward-change metadata for future D2

revision > baseline canonical revision
and financialTimestamp <= baseline timestamp
    -> backfill; baseline unavailable
```

This closes the R10-D backfill ambiguity without performing financial
arithmetic. A later liability point remains a replacement observation; D1 only
classifies its lineage.

## Atomicity, replay, and concurrency

- Canonical finance and revision metadata commit atomically.
- Holding replacement and watermark commit atomically.
- Primary/companion snapshots, items, and D1 boundaries commit atomically in
  the established AccountSnapshot writer phase.
- Baseline manifest persistence is a later established phase. Failure does not
  misrepresent already committed snapshots as rolled back.
- Exact replay changes no physical row counts.
- Concurrent identical manifest creation converges to one deterministic root.
- Concurrent canonical changes produce unique contiguous revisions without a
  deadlock or partial lineage.
