## Why IMP-06 was not satisfied

Before R10-A, `handleImportPost()` iterated files and called
`runImportWorkflow()` for every item. That helper ended by calling the existing
`/{batch_id}/post` route, whose service combined canonical posting, Holdings
rebuild, market evidence, and snapshot refresh. A three-file request therefore
had three separate post-processing boundaries even though the response was
aggregated.

The earlier tests proved sequential multi-file transport and per-file
summaries, but they did not instrument Holdings or market-backed refresh call
counts across one multi-file request. The R9 PASS was therefore historically
truthful to its evidence but incomplete for the explicit `IMP-06` scope
invariant.

## Old and new call graphs

Old:

`N browser files -> N complete workflows -> N canonical posts -> up to N
Holding rebuilds -> up to N market/snapshot refreshes`

New:

`N browser files -> N canonical workflows -> N persisted ImportBatch rows ->
one Python finalization -> zero-or-one Holding rebuild -> one market-backed
refresh -> one current snapshot graph`

Single-file requests use the same path with `N=1`; there is no separate
single-file business implementation.

## Per-file ImportBatch and canonical posting ownership

Every file still owns one physical `ImportBatch`, raw upload, staged rows,
status, counters, and `completedAt`. R10-A adds no persisted logical group.

`ImportBatchPostingService` remains the only canonical posting owner. The new
`canonical-post` route projects its immutable persisted result without
Holdings or snapshot work. Finalization replays that same service for each
terminal batch to validate canonical persisted state. It does not duplicate
Transaction or InvestmentEvent posting logic.

## Logical finalization command

The immutable command contains only:

- the authenticated principal;
- the account path identity;
- a nonempty, unique, sorted tuple of at most ten batch IDs.

Python validates that every physical batch is terminal, was created by the
same principal, belongs to the exact account, and has the same persisted
source. A foreign principal or batch produces generic nondisclosure before
posting replay, Holdings, provider HTTP, or snapshots.

The browser cannot provide user ID, source override, Holding selector, account
selector, market requirements, snapshot timestamp, calculation version, or
output currency. The empty HTTP batch set used for an all-checksum-duplicate
request is handled as a Python-owned `not_required` transport result before a
financial command is constructed.

## Deterministic final bucket

Finalization computes:

`final_completed_at = max(persisted completed_at)`

and:

`snapshot_bucket = canonical_import_snapshot_bucket(final_completed_at)`

No first-file timestamp, browser timestamp, provider timestamp, request clock,
or second system clock is used. The result is independent of submitted file
order.

## Holdings, market, and snapshot call counts

If every persisted posting result has `rows_imported == 0`, finalization is
`not_required`; Holdings, market refresh, and snapshot execution are not
called.

If imported rows exist but no investment events exist, Holdings is skipped and
the market-backed service is called once. If at least one batch imported an
investment event, one account-level Holding rebuild runs after all canonical
posts. The R5-B3A coordinator is then called exactly once and remains the sole
owner of market-before-snapshot order.

## Failure, partial state, and recovery

- Upload, parse, normalize, deduplicate, classify, or canonical-post failure in
  any file prevents request-level finalization.
- Earlier committed canonical batches remain persisted and are returned in a
  safe partial browser summary with request-level status `not_run`.
- Checksum duplicates are nonfatal and do not block finalization of other
  successfully persisted batches.
- Known Holding, market, or snapshot failure returns the existing
  `unavailable` or `conflict` status without claiming canonical rollback.
- Retrying the exact batch set revalidates/replays canonical posting, rebuilds
  or replays Holdings, and completes or replays market/snapshot identities.
- A dependency transaction leak is rolled back and raised as an internal
  runtime state error before the next phase.

There is no cross-phase compensation, automatic retry loop, worker, queue,
scheduler, background task, or response cache.

## Concurrency

Two concurrent finalizations over the same terminal batch set use the existing
posting, Holding, market-writer, AccountSnapshot, NetWorthSnapshot, and audit
locking/replay contracts. PostgreSQL acceptance runs two explicit concurrent
replays and proves one physical Holding, AccountSnapshot, and NetWorthSnapshot
with two `replayed` outcomes and no deadlock or partial graph.

## Public contract

OpenAPI adds:

- `POST /api/v1/accounts/{account_id}/imports/{batch_id}/canonical-post`
- `POST /api/v1/accounts/{account_id}/imports/finalize`

Generated TypeScript is regenerated and used by the server-only transport.
The same-origin browser result preserves all per-file summaries and adds only
`snapshotRefreshStatus`. A failed pre-finalization request uses `not_run`.
Neither Python nor Next exposes snapshot IDs, market IDs, selected accounts,
rates, provider identities, raw rows, SQL, credentials, tokens, or backend
URLs.

The existing per-batch `/{batch_id}/post` endpoint remains compatible for
single-batch callers and now uses the same shared finalization implementation.

## Executable IMP-06 evidence

The Python unit suite constructs three immutable terminal posting results and
asserts:

- three canonical persisted-state validations;
- one Holding service construction/call;
- one market-backed execution;
- exact maximum-`completedAt` bucket;
- cash-only and zero-import behavior;
- mixed-source and foreign-principal rejection before post-processing;
- market failure and recovery;
- transaction-leak rollback.

The Next route suite submits multiple files and asserts `N`
`runImportCanonicalWorkflow` calls followed by one `finalizeImportBatches`
call. It separately proves later-file failure prevents finalization, duplicate
files do not block valid batches, all-duplicate input asks Python for
`not_required`, and finalization transport failure retains a safe canonical
partial summary.
