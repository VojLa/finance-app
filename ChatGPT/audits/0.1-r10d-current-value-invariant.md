# 0.1-R10-D current-value snapshot invariant audit

## Verdict

`R10-D audit completed — NOT READY`

Decision class: **NOT READY — strict invariant is not representable from
current evidence**.

The literal Version 0.1 requirement is not implemented by the active current
portfolio/dashboard flow. The observed current-minute complete refresh is not
semantically equivalent to selecting a latest daily baseline and applying only
post-baseline canonical events. The current physical model also lacks the
lineage needed to implement that strict contract without ambiguity. No
production behavior or authoritative requirement was changed in this audit.

## Authoritative requirement

> Current/today/live portfolio value is based on the latest daily snapshot and
> events after that snapshot.

The audit treats this as a required architecture contract, not a performance
hint and not wording that may be redefined to match current code.

## Observed active call graph

```text
portfolio/dashboard page
  -> authenticated thin Next route
  -> runPortfolioSnapshotWorkflow / runDashboardSnapshotWorkflow
  -> POST /api/v1/snapshot-refresh/recalculate
  -> ManualUserSnapshotRefreshService
  -> server current UTC clock
  -> canonical minute bucket
  -> MarketBackedSnapshotRefreshService
  -> current market evidence
  -> UserSnapshotRefreshExecutor
  -> complete primary + required account-currency companion AccountSnapshots
  -> primary-only NetWorthSnapshot
  -> exact returned account snapshot manifest
  -> POST /api/v1/portfolio/snapshot or /api/v1/dashboard/snapshot
  -> exact manifest-backed REPEATABLE READ
```

The browser supplies only authenticated workflow intent. It does not supply a
timestamp, granularity, currency, account set, calculation version, snapshot
IDs, market requirements, or event range. The exact read uses only the manifest
returned by the immediately preceding refresh.

The seven expected current-state facts are true: current reads trigger refresh;
manual granularity is minute; the bucket comes from the server clock; exact
manifest identity is forwarded; no daily baseline is selected; no post-daily
event delta is applied; and no active frontend, Prisma, legacy, or `/api/rates`
implementation supplies the missing contract.

## Daily baseline representability

`AccountSnapshot(accountId, timestamp, currency, granularity)` can physically
store day rows, including an account-currency companion. That is insufficient
to identify the authoritative baseline:

- no persisted object records the exact complete active account set selected by
  a NetWorthSnapshot;
- the physical NetWorthSnapshot row does not retain its selected primary
  AccountSnapshot IDs;
- snapshots have no canonical event/transaction/movement watermark or included
  ID set;
- no persisted configuration identity proves account membership, archive
  state, user base currency, account currency, and calculation version at the
  cutoff as one complete baseline contract;
- no current production selector distinguishes latest valid complete set from
  merely latest, nearest, incomplete, mixed-version, or mixed-source rows.

A future strict selector must fail closed for no daily set, partial account set,
changed active accounts, changed user/account currency, changed calculation
version, missing companion, corruption, or ambiguity. R10-D implements no such
selector.

## Canonical event boundary

Current snapshot evidence queries transactions, investment events, and
movements using only an upper financial-time bound (`<= current bucket`). It
also reads current Holding. There is no persisted lower-bound cursor inherited
from a baseline.

The PostgreSQL backfill scenario proves the blocker: after a daily snapshot was
committed, a transaction was inserted with a financial date before the daily
cutoff. The next production current request included it because it recomputed
complete history. A strict `event timestamp > daily cutoff` delta would miss it,
while there is no baseline inclusion watermark that can establish whether the
event was already represented. Import completion time is lineage, not a valid
financial cutoff substitute.

## Account-type and financial evidence findings

| Account/evidence                       | Current source                                               | Daily + delta representability                                                                   |
| -------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| Bank/cash/savings                      | Full active Transaction sum through bucket                   | Blocked by absent inclusion watermark and backdated inserts                                      |
| Broker/exchange/crypto wallet quantity | Current Holding rebuilt from full InvestmentMovement history | Holding bypasses required delta lineage; snapshot item has no movement cursor                    |
| Investment cost basis                  | Current Holding average price and quantity                   | Snapshot item has aggregate/native basis but no canonical rebuild cursor or transfer/lot lineage |
| Investment cash                        | Full InvestmentEvent/Movement history                        | Same missing cutoff; multi-currency ordering must remain canonical                               |
| Realized P/L                           | Persisted event values over complete history                 | Delta events exist, but baseline inclusion and event-date FX delta lineage do not                |
| Fees/taxes/net deposits                | Complete historical metric projection                        | Same cutoff blocker; cannot use snapshot-time FX                                                 |
| Credit card/loan/mortgage              | Latest eligible LiabilityBalance point                       | No liability delta/event chain; baseline row does not persist selected balance lineage           |

AccountSnapshotItem stores quantity, price, native value, value, native cost
basis, and output cost basis. It does not store the event cursor or complete
state needed to prove which buys, sells, transfers, fees, and realized results
are already represented. Using current Holding may yield present quantity but
is a full-history materialization, not the required baseline-plus-delta proof.

Cash supports exact signed and multi-currency transactions, but event ordering
alone cannot resolve a later-ingested backfill. No synthetic zero or missing
currency fallback is acceptable.

LiabilityBalance records an immutable effective-at state observation with
principal, interest, fees, and total. Snapshot calculation selects the unique
latest eligible point. It has no `deltaAmount`, preceding-balance identity, or
canonical liability event stream. Silently retaining the daily liability would
be wrong; replacing it with a later point is not daily-value-plus-event-delta.

## Prices and FX

The existing market-backed coordinator safely acquires and persists exact
Twelve Data, CoinGecko, and CNB evidence before complete snapshot creation. It
does not provide a separate current-market projection over a daily-derived
state.

A strict implementation must specify a server-owned current as-of boundary for
position prices and snapshot-time FX. It must fail closed for missing, stale,
future, wrong-identity, or conflicting evidence and must not invent “latest
available” semantics. Provider calls remain outside DB transactions.

Historical net deposits, realized P/L, fees, and taxes must continue selecting
event-date FX for each post-baseline event. Current cash, investment value, and
liability require current as-of FX. R10-B1 CZK-pivot composition may project one
canonical reconstructed state into both User.baseCurrency and Account.currency,
but it must consume exact persisted direct legs and never create synthetic
ExchangeRate rows or read-time cross rates.

## Primary, companion, NetWorth, and history

Current R10-B1/B2 behavior remains correct for the observed minute contract:
mixed-currency refresh atomically writes a primary and companion; NetWorth uses
only primary IDs; exact reads use primary for global finance and companion for
account presentation.

A strict engine should reconstruct one canonical account state and project both
denominations from the same cutoff and evidence set. Independently advancing
primary and companion scalars would risk divergence. No account-currency value
may be relabelled from a primary scalar.

Current NetWorth is a persisted minute row built from the exact runtime primary
manifest, although that manifest is not retained in its physical row. History
is a separate read-only path over persisted NetWorthSnapshot points and performs
no event, price, or FX reconstruction. R10-D adds no synthetic current history
point. A future design must decide explicitly whether current daily+delta output
is ephemeral or persisted; if ephemeral, displayed current value may differ
from the latest history point and needs independent lineage. If persisted, its
history inclusion semantics must be specified.

## PostgreSQL observations

The dedicated PostgreSQL 16.10 database was recreated and bootstrapped from the
canonical schema.

1. With valid canonical cash state and no daily snapshot, the public current
   refresh succeeded and persisted one minute AccountSnapshot and one minute
   NetWorthSnapshot.
2. With a day baseline and a later event, the public current refresh preserved
   the day rows and created a complete minute graph (`100.000000` ->
   `150.000000`), returning only the minute manifest.
3. A transaction inserted after the baseline with a pre-baseline financial date
   changed the full minute recomputation (`100.000000` -> `125.000000`), proving
   the absence of a baseline inclusion watermark.
4. A liability changed from a daily `100.000000` point to a later `140.000000`
   point; production selected the replacement point and wrote a minute graph,
   not a persisted liability delta.
5. The mixed-provider current endpoint retained two primary plus two companion
   snapshots, exact provider evidence, replay, and R10-B presentation behavior.

Dedicated R10-D: `4 passed, 0 failed, 0 skipped, 0 xfailed`. Combined current
refresh/mixed-currency regression: `6 passed, 0 failed, 0 skipped, 0 xfailed`.

## Security and fail-closed requirements for remediation

A future strict implementation must derive everything server-side. The browser
must not choose baseline snapshot, cutoff timestamp, account set, calculation
version, currency, primary/companion IDs, price/FX evidence, or event range.

It must fail closed for missing/incomplete/corrupt baseline, mixed versions,
changed account/configuration identity, missing companion, missing market
evidence, absent liability delta evidence, ambiguous event inclusion, or
concurrent conflicting state. It must not fall back to some older snapshot,
current Holding, a primary scalar relabel, live/read-time FX, or legacy finance.

## Remediation boundary

The smallest safe dependency graph is:

1. **0.1-R10-D1 — persisted daily baseline manifest and canonical cutoff**
   - persist the exact primary account set and companion requirements;
   - persist a canonical transaction/event/movement inclusion watermark or
     equivalent immutable version contract;
   - define account/configuration change invalidation and liability lineage;
   - define exact daily baseline creation and selection failure rules.
2. **0.1-R10-D2 — strict daily-baseline current-value engine**
   - load one exact D1 baseline;
   - select only provable post-baseline canonical changes;
   - project current cash, positions, metrics, and liabilities;
   - acquire current price/FX and historical event-date FX evidence;
   - project primary and companion from one canonical state;
   - define ephemeral versus persisted NetWorth/current-history behavior;
   - converge replay/concurrency without latest/nearest fallback.
3. **0.1-R10 final scope re-audit** after D1 and D2 pass.

Implementing D2 before D1 would make backfill, account-set, liability, replay,
and concurrency behavior unprovable. R10-D therefore implements neither.
